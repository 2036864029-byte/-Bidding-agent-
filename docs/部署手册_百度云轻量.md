# 部署手册 · 百度云轻量应用服务器

> 目标环境：百度云**轻量应用服务器**（无 GPU）+ 已有 `openagent-lab.top` 静态站与 SSL 证书。
> 部署形态：**CPU 全托管 + 外部 API**（embedding/rerank 走 SiliconFlow，LLM 走 DeepSeek，PDF 解析走 MinerU API）。
> 预估：**2–2.5 个工作日**（含等待），首次部署按 3 天排。

---

## 0. 先做机型判断

现有组件常驻内存估算：

| 组件 | 内存 | 是否必需 |
| --- | --- | --- |
| Milvus standalone + etcd + MinIO | 1.5–2.5 GB | **必需**（法规知识库 RAG） |
| MySQL 8 (`ztb_clean`) | 300–500 MB | **必需** |
| 后端 FastAPI + LangGraph（uvicorn 单 worker） | 400–600 MB | **必需** |
| Redis（缓存/限流/文件存储） | 30–60 MB | 必需 |
| PostgreSQL（会话检查点） | 80–150 MB | 必需 |
| nginx + 系统 | 250–400 MB | 必需 |
| Langfuse（可观测，可选） | 1.5 GB+ | **建议关掉** |
| **合计（不含 Langfuse）** | **≈ 3–4 GB** | |

| 机型 | 结论 |
| --- | --- |
| 2C2G | ❌ 跑不动。Milvus 单独就要 1.5G+ |
| 2C4G / 4C4G | ⚠️ 可行但紧，按 §1.3 调小内存参数，且必须关 Langfuse |
| 4C8G 及以上 | ✅ 舒服，按现有 compose 直接跑 |

**磁盘**：镜像约 5–6 GB + MySQL 数据 1.2 GB + Milvus 卷 0.5 GB + 备份 → **建议 ≥ 40 GB**。

## 1. 服务器初始化

### 1.1 基础环境

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y curl git nginx unzip

# Docker（国内源）
curl -fsSL https://get.docker.com | sudo sh -s -- --mirror Aliyun
sudo systemctl enable --now docker
docker version
```

### 1.2 防火墙

百度云轻量的**防火墙要在控制台改**（不是 ufw）：

- 放行 `80` / `443`
- **不要放行 `3306` / `19531` / `8000`** —— 后端与中间件都只听回环

### 1.3 小内存机型调参（2C4G 必做）

```bash
# MySQL：compose 里 innodb 默认 512M，4G 机器改 256M
sed -i 's/--innodb-buffer-pool-size=512M/--innodb-buffer-pool-size=256M/' \
  docker/mysql/docker-compose.yml
```

若仍吃紧，给系统加 2G swap：

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

## 3. 后端

### 3.1 准备 .env

```bash
cp .env.example .env && vim .env
```

生产必须改的项（其余保持 SiliconFlow / DeepSeek 配置即可，**不需要 GPU 服务**）：

```ini
# —— 中间件指回宿主（容器内 127.0.0.1 是容器自己）——
MILVUS_HOST=host.docker.internal
MILVUS_PORT=19531
MYSQL_HOST=host.docker.internal
MYSQL_PORT=3306
CACHE_REDIS_URL=redis://host.docker.internal:6380/0
CHECKPOINTER_POSTGRES_URL=postgresql://ztb:ztb_dev_pw@host.docker.internal:5433/ztb_checkpoints

# —— 外部 API（沿用现有值，密钥建议换新的）——
DEEPSEEK_API_KEY=<新 key>
EMBEDDING_BASE_URL=https://api.siliconflow.cn/v1
EMBEDDING_API_KEY=<新 key>
SILICONFLOW_API_KEY=<新 key>

# —— PDF 解析：见 §3.3 ——
PDF_PARSE_BASE_URL=<MinerU 服务地址>

# —— 多 worker 时必须是 1（MemorySaver 不跨进程；已切 postgres 可 >1）——
API_WORKERS=1
```

### 3.2 构建并启动

```bash
# 服务器连不上 Docker Hub，必须走镜像源
docker compose -f deploy/api/docker-compose.yml up -d --build \
  --build-arg BASE_IMAGE=docker.m.daocloud.io/library/python:3.11-slim
```

构建约 10–20 分钟（依赖走阿里云 pypi，已内置）。完成后：

```bash
curl -s http://127.0.0.1:8000/health
# {"status":"ok","agent_ready":true}
```

### 3.3 PDF 解析（本方案走 MinerU 官方 API）

⚠️ **只改 `PDF_PARSE_BASE_URL` 是不够的**。三档路由关闭（默认）时工厂返回的是
`MinerUParser` —— 本地 `magic-pdf` CLI，`PDF_PARSE_BASE_URL` **完全不参与**，
在没装 MinerU 的 CPU 机器上会报「未找到 magic-pdf 命令」。

正确做法是切**解析后端**（改一行 .env，代码零改动）：

```ini
PDF_PARSE_BACKEND=official        # local(默认) | official | selfhosted
MINERU_API_TOKEN=<mineru.net 申请的 token>
# 可选微调
MINERU_OFFICIAL_MODEL_VERSION=pipeline   # pipeline(快) | vlm(准、慢)
MINERU_OFFICIAL_POLL_TIMEOUT=600
```

| 后端 | 实现 | 适用 |
| --- | --- | --- |
| **official** | MinerU 官方 API（mineru.net，异步提交 → 轮询 → zip 取 full.md） | **本方案**，CPU 机器无需 GPU |
| selfhosted | 自建 `/parse` 服务（`deploy/mineru/`） | 另有一台 GPU 机器时 |
| local | 本地 `magic-pdf` CLI | 本地开发（默认值，行为不变） |

**送进官方 API 的不是整本文档**：三档路由只把被判为复杂的**连续页**切成子 PDF
（`write_subpdf`）再上传；纯文本页由本地 PyMuPDF 处理、完全不出网。所以单次请求
通常只有几页到几十页，官方 **≤200MB / ≤600 页** 的限制基本触不到，每账号每天
2000 页的高优额度也远用不完（只统计真正外发的复杂页）。

单次延迟一般是几秒到几十秒（异步：提交 → 排队 → 解析 → 下载 zip），不是分钟级。
同一份子 PDF 重复解析会命中本地缓存（`DATA/raw_data/_mineru_cloud_cache/`），不再计费。

⚠️ **页范围不下发**。子 PDF 里已经只含目标页，若再把源 PDF 的 `page_ranges` 传给
官方 API，会被当作相对**子 PDF** 的页码二次裁剪 → 内容错位或空返回。代码已按此
处理（与自建服务一致：`deploy/mineru/service/app.py` 也只把 page_range 用在缓存键上）。

**除文件解析外，其余功能都不需要 GPU** —— embedding/rerank 走 SiliconFlow，LLM 走 DeepSeek。

### 3.4 飞书机器人（可选，独立服务）

飞书入站机器人是 **compose 里的第二个服务**（`deploy/api/docker-compose.yml` 的 `feishu`），
和 `api` 用同一个镜像、不同 entrypoint。跟着 `up -d` 一起起、`restart: unless-stopped` 保活。

**为什么不做进 api 进程**（不是疏忽）：

1. 飞书用**出站 WebSocket 长连接**（`lark_oapi.ws.Client`），`ws.start()` 是阻塞调用且 SDK
   **没有 `stop()`** —— 放进 FastAPI lifespan 无法优雅关停，`--reload` 还会反复建连；
2. `API_WORKERS>1` 时每个 worker 都会各起一条长连接，事件被分摊，某个 worker 重启的窗口里消息会丢；
3. 通道只通过 HTTP 调后端 `/chat`，**不在进程内再起一张 AgentGraph**（见
   `channels/feishu/backend.py` 的设计说明）。

**必须确认的三项**（缺任何一项该服务会 `exit(2)`，配了 restart 就是重启循环）：

```ini
FEISHU_ENABLED=true
FEISHU_APP_ID=<飞书应用 app_id>
FEISHU_APP_SECRET=<飞书应用 app_secret>
```

`FEISHU_BACKEND_BASE_URL` 由 compose 覆盖为 `http://api:8000`（**不能**写 127.0.0.1 ——
容器里的回环是它自己）。若后端开了 `API_KEYS` 鉴权，还要给机器人配
`FEISHU_BACKEND_API_KEY`。

**端口**：一个都不用开。长连接是出站，只需容器能访问 `open.feishu.cn`。

**验收**：

```bash
docker ps --format '{{.Names}}\t{{.Status}}'          # 期望 ztb-feishu 为 healthy
docker compose -f deploy/api/docker-compose.yml logs -f feishu
#   期望看到：飞书通道已启动 / connected to wss://msg-frontier.feishu.cn/ws/v2
curl -s http://127.0.0.1:9100/metrics | grep feishu_   # 指标端口（默认只绑回环）
```

**排错顺序**：健康检查失败 → 先看心跳文件
`DATA/feishu_heartbeat.json` 的 `state` 与 `updated_at`
（`python -m channels.feishu.telemetry --check <path>` 会直接告诉你原因：
文件缺失 / 状态 stopped|failed / 心跳过期）。心跳过期但进程还在，就是长连接僵死。

## 4. 前端
```bash
cd frontend
npm ci
npm run build            # 含 tsc -b，类型错误会直接阻断构建
# 产物在 frontend/dist（约 1.8 MB）
```

构建期变量由 **`frontend/.env.production`（已入库）**提供，不要依赖 `.env.local`：

| 变量 | 值 | 为什么 |
| --- | --- | --- |
| `VITE_CHAT_MODE` | `api` | 缺省时对话栏走**内置演示数据**，上线看着像能用、其实是假数据 |
| `VITE_API_BASE` | **不设** | 缺省即同域 `/api`，由 nginx 反代；若设成 `http://127.0.0.1:8000` 会被烘进 bundle，**用户浏览器去连自己本机** |

> ⚠️ `frontend/.env.local` 被 gitignore，服务器上拿不到。修复前在服务器构建出来的产物里
> `chat` 会退化成 `"mock"`（实测：env 为空时产物是运行时三元表达式
> `(...VITE_CHAT_MODE)==="api"?"api":"mock"`，求值为 mock）。现在由入仓的
> `.env.production` 固定为 `api`，本地与服务器构建结果一致。
>
> `VITE_API_BASE` 也**不要写成空值**：代码是 `VITE_API_BASE ?? '/api'`，`??` 只在
> null/undefined 时回退，空字符串会让 BASE 变成 `''`，所有请求丢掉 `/api` 前缀。

### 4.1 发布静态文件 + nginx

```bash
sudo mkdir -p /var/www/ztb
sudo cp -r frontend/dist/* /var/www/ztb/

# 配置（仓库已备好）
sudo cp deploy/web/nginx.conf /etc/nginx/conf.d/ztb.conf
sudo vim /etc/nginx/conf.d/ztb.conf      # 改证书路径 / 域名
sudo nginx -t && sudo systemctl reload nginx
```

> 该配置只**新增**一个 server 块，不影响你现有的 `openagent-lab.top` 静态站。
> 关键点：`location /api/` 里 `proxy_pass http://ztb_api/;` 的尾斜杠会剥掉 `/api` 前缀，
> 且必须 `proxy_buffering off` 才能流式输出。
> 另外 `ztb.conf` 里已显式配置 **gzip**（`gzip_types` 含 `application/javascript`）——
> Debian/Ubuntu 的 nginx 默认只压缩 `text/html`，不补这几行，入口 chunk 会以
> 未压缩的 ~800 KB 传输（gzip 后 ~244 KB）。

### 4.2 DNS 与证书

- 加一条 A 记录：`ztb` → 服务器公网 IP
- 证书：现有证书若只签了主域，需给子域单独签一张（`certbot certonly -d ztb.openagent-lab.top`），或换通配符

## 5. 数据迁移

两条路，**推荐第 2 条**（服务器带宽通常只有 3–6 Mbps，传 1.2 GB 的 MySQL 数据要 30 分钟以上）。

### 路线 A：传快照（快但吃带宽）

```bash
# 本地导出（示例）
mysqldump -h127.0.0.1 -P3306 -uroot -p --single-transaction ztb_clean > ztb_clean.sql

# 上传后导入服务器
docker exec -i ztb_mysql mysql -uroot -p'<pwd>' ztb_clean < ztb_clean.sql

# Milvus 卷（460 MB）：停容器 → tar → 上传 → 解压回 milvus/volumes-v26/
```

### 路线 B：用交付包在服务器重建（推荐）

```bash
# 上传 delivery_package/（约 130 MB 的 jsonl）
# 按 mysql_schema.sql 建表，再用内置 loader 导入
docker exec -i ztb_mysql mysql -uroot -p'<pwd>' ztb_clean < delivery_package/mysql_schema.sql
python delivery_package/reference_loader.py --help
```

> **注意**：Milvus 那 460 MB 向量卷**没法用这条路重建** —— 需要在服务器上重跑一次知识库入库
> （`python -m public_kb --init --pdf-dir raw_pdfs`），但这需要 PDF 原文和 MinerU，耗时 10–20 分钟起。
> 所以**向量库建议走路线 A 直接传卷**，MySQL 走路线 B 重建，两者组合最省时间。

## 7. 已知的坑（都是实际踩过的）

1. **服务器连不上 Docker Hub** → 构建必须传 `--build-arg BASE_IMAGE=docker.m.daocloud.io/library/python:3.11-slim`
2. **容器里的 `127.0.0.1` 是容器自己** → Milvus/MySQL/Redis/PG 一律用 `host.docker.internal`，compose 里已加 `extra_hosts: host-gateway`
3. **pypi 跨境 36–60 KB/s** → Dockerfile 里已配阿里云镜像，别删
4. **HuggingFace 不可达** → 只有自建模型服务才需要；本方案用 SiliconFlow，不受影响
5. **SSE 被 nginx 缓冲** → `proxy_buffering off`，否则表现为"卡很久然后一次性全出来"
6. **Milvus 卷版本不匹配** → v2.6 数据必须用 v2.6 镜像挂载
7. **CDN 缓存 `/api`** → 若套了 CDN，必须把 `/api/*` 设为不缓存
8. **`API_WORKERS > 1` 需先切检查点后端** → 本项目已支持 postgres，但文件存储/任务队列仍走 Redis，多 worker 前要确认 `CACHE_REDIS_URL` 指对
9. **PDF 解析后端没切** → 上传文档报「未找到 magic-pdf 命令」。默认 `PDF_PARSE_BACKEND=local`
   走本地 CLI，服务器上必须设成 `official`；**只填 `PDF_PARSE_BASE_URL` 完全无效**（见 §3.3）
10. **前端构建出 mock 版** → 对话栏显示内置演示样例，功能看着正常但全是假数据。
    `VITE_CHAT_MODE` 是**构建期**变量，服务器上没有 `.env.local` 时缺省为 `mock`。
    已用入仓的 `frontend/.env.production` 固定，构建后可用下面这条自检：
    ```bash
    grep -o 'chat:"[a-z]*"' dist/assets/index-*.js   # 必须是 chat:"api"
    ```
