# 资源实测方案 · 2C4G 到底够不够

> 目标环境：2 核 4G / 80G 盘，`openagent-lab.top` 已备案，应用挂子域名 `ztb.openagent-lab.top`。
> 本文只回答一个问题：**这台机器能不能跑完整栈**，以及**不能的话到底差多少**。
> 配套脚本：`deploy/ops/mem_probe.py`（采样 + 判定）。

---

## 0. 结论先行

**先按现有 compose 原样部署，用约 1 小时采集两组数据，再决定升降配。**

不要在没有数据的情况下先改「瘦身版 compose」：加 swap、砍 Postgres、压 MySQL buffer 这一套
改完仍然是「能不能跑」的猜测，而一旦出问题，排查的是「我改的哪一项」，不是「容量够不够」——
把变量减到最少，比提前优化更省时间。

判定只需要两组事实：

| # | 数据 | 从哪来 | 耗时 |
|---|---|---|---|
| 1 | 空载时 `MemAvailable` 最低点 + 有无容器重启 | `mem_probe.py` 30 分钟 | 30 min |
| 2 | 5 并发下 `MemAvailable` 最低点 + 重启计数 + p95 | `mem_probe.py` + `load_test_chat.py` | 15 min |

数据到手后再动第二件事（§6 瘦身 or 升配）。**在此之前不改任何内存参数。**

---

## 1. 为什么必须上服务器实测

三个「本地看不出、只有 4G 机器才会暴露」的点：

1. **本地内存充足 → 永远测不出「余量」**。容器 RSS 在本地和服务器上是一样的，但本地 32G 里
   剩 20G 和剩 200MB 是两种完全不同的系统行为。真正决定成败的是 `MemAvailable` 的低点。
2. **瞬时快照会骗人**。Milvus 的内存峰值出现在**启动 + 首次加载 segment** 阶段，之后会回落；
   `docker stats` 只看一眼，很可能正好落在回落后的安静期，得出「才用 2G，没问题」的错误结论。
3. **OOM 的表现不是「崩」，是「偶发 502」**。内核杀掉 Milvus 或 api 后，`restart: unless-stopped`
   会把它拉起来，用户看到的是「第一次能用、第二次 502」。所以要看的是 **`RestartCount` 有没有涨**，
   这比任何瞬时内存数字都硬。

## 2. 前置：把栈起全（但只起必需的）

按 `docs/部署手册_百度云轻量.md` §1–§3 执行，三处刻意的偏离：

- ✅ 起：Milvus v2.6 栈（standalone + etcd + MinIO）、MySQL、Redis、PostgreSQL、api 容器
- ❌ **先不装 Langfuse**（它一个人 1.5G+，会直接污染这次测量）
- ❌ **先不接 CDN、不改内存参数**（否则测的是改后的配置，不是真实需求）

验收：

```bash
docker ps --format '{{.Names}}\t{{.Status}}'          # 全部 healthy
curl -s http://127.0.0.1:8000/health                  # {"status":"ok","agent_ready":true}
free -m                                               # 先看一眼，别急着下结论
```

## 3. 第 1 步：空载基线（30 分钟）

**关键时序**：采样必须从 **Milvus 启动那一刻**开始，因为首次加载 segment 就是内存峰值。
最省事的做法是起栈的同一个终端会话里，先把采样挂上去再 `compose up`：

```bash
# 终端 A：先挂采样（30 分钟），它会立刻开始记
python3 deploy/ops/mem_probe.py --duration 1800

# 终端 B：起栈（顺序按手册：Milvus → MySQL → Redis/PG → api）
docker compose -p milvus-v26 -f milvus/docker-compose-v26.yml up -d
```

采集期间**不要压测、不要解析 PDF、不要跑批量入库** —— 这一档要的是「什么都没干」的下限。
报告落在 `deploy/ops/reports/probe-*.jsonl`，终端会直接打印判定。

### 判定表（空载）

| 可用内存最低点 | swap 峰值 | 重启计数 | 结论 | 下一步 |
|---|---|---|---|---|
| ≥ 800 MB | < 200 MB | 0 | 🟢 有余量 | 进 §4 压测 |
| 300–800 MB | 任意 | 0 | 🟡 能启动但无缓冲 | 可压测，但预期会打到红线；同时准备 §6 |
| < 300 MB | 任意 | 0 | 🔴 贴上限 | **跳过压测**，直接 §6 |
| 任意 | 任意 | > 0 | 🔴 OOM 已发生 | **跳过压测**，直接 §6 |

> 800 / 300 MB 这两条是经验阈值（4G 机器 `MemTotal` 实测约 3.7–3.9 GB，内核和保留区先吃掉一截）。
> 脚本里是常量 `HEADROOM_GREEN_MB` / `HEADROOM_YELLOW_MB`，有实测依据后可以改。

## 4. 第 2 步：压测（仅当基线为绿/黄）

三档并发，每档 3–4 分钟，档间歇 30 秒等内存回落。**采样和压测必须同时开**（两个终端）。

```bash
# ── 档位 1：单并发（等价「一个人在用」）──────────────────────────
python3 deploy/ops/mem_probe.py --duration 240 --out load_c1.jsonl &
python3 scripts/load_test_chat.py --concurrency 1 --total 4 --endpoint stream
wait

# ── 档位 2：3 并发（作品页被转发后的小高峰）────────────────────
sleep 30
python3 deploy/ops/mem_probe.py --duration 240 --out load_c3.jsonl &
python3 scripts/load_test_chat.py --concurrency 3 --total 12 --endpoint stream
wait

# ── 档位 3：5 并发（判定线）────────────────────────────────────
sleep 30
python3 deploy/ops/mem_probe.py --duration 240 --out load_c5.jsonl &
python3 scripts/load_test_chat.py --concurrency 5 --total 20 --endpoint stream
wait
```

三个必须注意的细节（都踩过）：

1. **`--clients` 保持默认 100**。入口限流按客户端键限流（默认 burst=20 / 60 每分钟），
   同机压测若不区分客户端，第一个档位就会被 429 淹没 —— 测到的是限流器，不是容量。
2. **`--endpoint stream` 而不是 `chat`**。作品页访客走 SSE（前端默认流式），长连接 + 逐帧
   token 的内存占用比一次性返回更高，也更接近真实体验。
3. **每档之间要等内存回落**。不等的话第三档测的是前两档的残留。

### 判定表（压测）

| 5 并发下的观测 | 结论 |
|---|---|
| p95 ≤ 15s、无 503、重启计数不变、可用内存 ≥ 300 MB | 🟢 容量够，按现状上线 |
| p95 明显劣化（> 20s）或 503 明显增多 | 🟡 能扛但体验差 —— 先看 §8 的 CPU 墙 |
| 任意档位重启计数增长 | 🔴 容量不足，§6 |
| 可用内存 < 100 MB 且 swap 持续增长 | 🔴 已在靠 swap 续命，延迟会毛刺，§6 |

> 压测会真实调用 DeepSeek 与 SiliconFlow，**产生费用**。上面三档合计 36 次请求，
> 成本是「几毛钱」量级；别把 `--total` 加到几百再抱怨账单。

## 5. 重跑一次看稳定性（可选，20 分钟）

`--duration 1200` 空载跑 20 分钟，确认没有**缓慢爬升**（内存泄漏特征：`MemAvailable` 单调下降
而不回落）。这一档能抓出「启动看起来没问题、跑一小时才 OOM」的形态。

---

## 6. 判红之后的动作顺序（先做便宜的三件事，再决定买大的）

按「改动小 → 收益大」排序，做完重跑 §3 的 30 分钟基线，而不是直接升配：

| # | 动作 | 省下 | 代价 |
|---|---|---|---|
| 1 | 关掉 Langfuse（本次测量已排除，若已装则停容器） | 1.5 GB+ | 无可观测面板（排查时靠日志） |
| 2 | `CHECKPOINTER_BACKEND=redis`，停掉 PostgreSQL | 100–150 MB | 会话检查点存 Redis，重启不保证持久 |
| 3 | MySQL `--innodb-buffer-pool-size=256M` + 2G swap | 250 MB + 抗峰 | swap 会让延迟出现毛刺 |
| 4 | 给 Milvus 加 `mem_limit: 2g` | 防止拖死 api | 超限时 Milvus 自己 OOM 重启（比整机崩好） |

第 4 项的写法（`milvus/docker-compose-v26.yml` 的 `standalone` 服务下）：

```yaml
    # Milvus 是内存大户。给上限的意义：OOM 落在它自己身上，
    # 而不是内核去挑 api（api 被杀 = 全站 502，Milvus 被杀 = 只能查知识库）
    mem_limit: 2g
```

> **做完 1–4 项重跑基线，若 `MemAvailable` 仍 < 800 MB，就升 4C8G。**
> 到这一步继续优化是在给一台不达标的机器做无用功，且每多一项调整，未来排查就多一层变量。

磁盘侧（80G 够，但必须配轮转，否则日志能吃满盘）——写 `/etc/docker/daemon.json`：

```json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "20m", "max-file": "3" }
}
```

（改完 `systemctl restart docker`，需要重起容器生效。）

## 8. 两个容易误判的点

**① 2 核 CPU 是另一面墙，而且表现不像内存问题。**
Milvus 启动、PDF 解析、embedding 批量请求都会把两个核吃满。症状是 **p95 抖动、请求超时**，
而内存看起来还有余量 —— 很容易被误判成「网络慢」。所以采样时一并记 `cpu_pct_sum`：
**长期贴着 200% 就是 CPU 瓶颈**，加内存解决不了。

**② `docker stats` 的 CPU% 是累计平均值，不是瞬时值。**
用它看趋势足够，不要拿它当精确值（精确值看 `top` 或 `cgroup` 的 `cpu.stat`）。
真正可信的是它报的 **内存**（那是绝对量）和 **RestartCount**（那是事故事实）。
