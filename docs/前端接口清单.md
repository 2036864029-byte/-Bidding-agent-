## 0. 通用约定

### Base URL 与鉴权

```
Base:  http://<host>:8000          # 容器内监听 0.0.0.0:8000
鉴权:  X-API-Key: <key>            # 优先
       或  Authorization: Bearer <key>
```

> ⚠️ `API_KEYS` 为空时**完全免鉴权**（本地开发默认）。**对公网暴露前必须设置。**

### 登录 / 租户方案（2026-09-14 决策，前端按此实现）

**当前：匿名优先，无登录、无多租户。** 前端不需要做登录页。

| 项 | 现状与边界 |
|---|---|
| **用户** | 没有"用户"概念。每个请求一个**随机 `session_id`**（首轮响应回传，前端存 localStorage）即是一个独立会话世界 |
| **隔离** | 匿名用户之间**天然互相看不见**（文件/检查点/对话按 `tenant::session` 存，隔离靠随机不可猜的 id，不靠租户）——**多用户同时提问是容量问题，已实测 100 并发 0 失败，与租户无关** |
| **租户** | `X-Tenant-ID` 头目前是**客户端自报**的前缀（缺省 `default`），用于内部命名空间，**不是认证绑定的多租户**。前端**不要**传它（缺省即单租户） |
| **登录** | 工业级路径 = **匿名优先 + 可选登录**：登录只解锁能力（保留时长/多设备/历史），不强制。**什么时候才做**（触发式）：① 需要保留超 1h/24h 且跨设备；② 需要按用户做权限/配额/留痕；③ 需要按租户隔离或计量。三者都未出现 → 匿名够用 |
| **将来演进** | 后端加登录/多租户是**在现有 session 层之上加一层**（认证 → 推导租户），**前端最多加一个登录页**，现有调用零改动——前端不需要为此预留任何东西，只存 `session_id`（+ 将来的 token）即可 |

**前端要处理的唯一鉴权边界**：`API_KEYS` 设置后，未带 key 的请求返 401 `biz_1006`——按"未授权提示"处理（**没有登录页可跳**，见 §3.3）。


### 会话（`session_id`）

| 规则 | 说明 |
|---|---|
| 首次可不传 | 服务端生成并**随响应回传** `session_id` |
| 后续必须带回 | 不带回 = 新会话 → **多轮上下文丢失** |
| 用途 | 多轮对话上下文、上传文件的归属 |
| 服务端 TTL | 会话 24h（`SESSION_TTL_SECONDS`）；上传文件记录 **1h**（`file_store`） |

**前端约定**：把首轮响应的 `session_id` 存下来（内存或 localStorage），后续所有请求（含上传）都带上。

### 错误信封（非 200 时）

```json
{ "error": { "code": "sys_2003", "message": "请求过于频繁，请稍后重试。", "category": "system", "request_id": "..." } }
```

`/chat` 的**业务错误**不走 HTTP 错误码，而是 HTTP 200 + `error_code` 字段（见 §3）。
`/chat` 的**过载/系统错误**才走 HTTP 4xx/5xx。

### 限流与并发（前端必须处理）

| 机制 | 行为 | 前端应对 |
|---|---|---|
| 按客户端限流 | 60 次/分、突发 20 → **429 `sys_2003`** | 退避重试；**同一用户快速连续操作会撞上**，多文件上传要串行或加间隔 |
| 全局并发闸门 | 同时在飞 > **128** → 等待 5s，超时 **503 `sys_2004`** + `Retry-After` | 按 `Retry-After` 退避重试；提示"当前请求较多" |
| 轮询端点 | `GET /files/{id}/status` **已豁免限流** | 可放心按 1~2s 轮询 |

> 闸门是**进程级**的：`API_WORKERS=N` 时总在飞上限 ≈ `N × 128`。

## 2. 文件上传

### 2.1 `POST /files/upload`（同步）

**请求** `multipart/form-data`

| 字段 | 位置 | 必填 | 说明 |
|---|---|---|---|
| `file` | form | ✅ | 文件本体 |
| `session_id` | **query** | ❌ | ⚠️ **是查询参数，不是表单字段** |

**限制**
- 大小上限 **20 MB**（`MAX_UPLOAD_MB`），超出 → **413**
- 扩展名白名单（**代码内固定，非 env**，`Settings.allowed_upload_exts`）：
  `.pdf .csv .txt .md .markdown .png .jpg .jpeg .bmp .tif .tiff .webp`，不符 → **400**

**响应 200**
```json
{
  "file_id": "a1b2c3...",          // 32 位 hex，后续传给 /chat 的 file_ids
  "source_name": "a.pdf",
  "source_format": "pdf",
  "preview": "前 600 字...",
  "chunk_count": 22,
  "session_id": "5ce3a9c6..."      // 未传则服务端生成，务必保存
}
```

**行为**：解析**在当前请求内完成** → 用户需等待。30 页电子版 PDF 约 **3 秒**；大文件/扫描件可达分钟级。
> 大文件一律用 §2.2 异步端点。

### 2.2 `POST /files/upload/async`（推荐）

**请求**：同 §2.1（`session_id` 同样是 **query** 参数）

**响应 200（立即，实测 0.12s）**
```json
{
  "file_id": "a1b2c3...",
  "session_id": "5ce3a9c6...",
  "status": "pending",
  "message": "解析中，轮询 GET /files/{file_id}/status 获取结果"
}
```

### 2.3 `GET /files/{file_id}/status`

**请求**

| 参数 | 位置 | 必填 | 说明 |
|---|---|---|---|
| `session_id` | query | ❌ | **可不传**（`file_id` 本身即能力凭据） |

**响应 200**
```json
// 解析中
{ "file_id": "...", "status": "pending",    "session_id": "..." }
{ "file_id": "...", "status": "processing", "session_id": "..." }

// 完成（字段与同步上传一致）
{ "file_id": "...", "status": "done",
  "source_name": "a.pdf", "source_format": "pdf",
  "preview": "前 600 字...", "chunk_count": 22, "session_id": "..." }

// 失败
{ "file_id": "...", "status": "error", "error": "异常类型: 详情", "session_id": "..." }
```

**响应 404**
```json
{ "detail": "任务或文件不存在（或已过期）" }
{ "detail": "任务已完成，但文件记录已过期" }   // 上传记录 TTL 1 小时
```

**前端建议**：上传后每 **1~2s** 轮询一次，拿到 `done` 后把 `file_id` 传给 `/chat` 的 `file_ids`；
`error` 时提示可重传；**轮询上限建议 ~5 分钟**后提示超时。

## 3. `POST /chat`

**请求** `application/json`

```json
{
  "question": "招标方式有哪些？",     // 必填，1~2000 字
  "session_id": "5ce3a9c6...",      // 可选（首轮不传）
  "stream": false,                   // 走 /chat 时必须 false，true 会 400
  "file_ids": ["a1b2c3..."]          // 可选：上传的文件 id（doc_qa 消费）
}
```

**响应 200**

```json
{
  "answer": "根据参考资料，招标方式主要分为……",
  "reply_type": "kb_answer",         // 见下表
  "intent": "knowledge_qa",          // 路由器判定
  "citations": [ /* 见 §3.1，仅 kb_answer 非空 */ ],
  "data": { /* 见 §3.2，按 reply_type 不同 */ },
  "latency_ms": 2840,
  "session_id": "5ce3a9c6...",
  "error_code": null                 // 非 null 见 §4
}
```

### 3.1 `citations[]`（知识问答引用）

```json
{
  "context_index": 1,          // 对应回答里的 【来源1】，从 1 起
  "chunk_id": 12345,           // Milvus 主键（可 null）
  "chunk_uid": "ck-0a1545...", // 内容稳定标识
  "doc_name": "招标投标法律解读与风险防范实务 (白如银)",
  "chapter": "第一章 总则 > 第一条",
  "chunk_index": 3,
  "text": "原文片段（完整 chunk）",
  "score": 0.9775,             // 相关度
  "metadata": { }              // source_file / publish_date 等
}
```

**前端用法**：回答文本里含 `【来源N】` 标记 → 用 `context_index` 匹配到 `citations[N-1]`，做悬浮/点击展开原文。

> ⚠️ `citations[]` **只对 `kb_answer`（knowledge_qa）非空**。其它分支的引用/来源在 `data` 里，
> 形状不同（`doc_qa` 看 `data.sources`；`deep_agent` 看 `data.trace.steps[].sources`，见 §3.4）。

### 3.2 `data` 按 `reply_type` 的形状

| `reply_type` | `data` 形状 | 前端渲染 |
|---|---|---|
| `kb_answer` | `{"sources": [...], "citation_validation": {…}}` | 正文 + 引用卡片（`citations[]`） |
| `price_records` | `{"records": [...], "tables": [...], "intent": {"sub_route","query_type","semantic_keywords"}}` | **表格**（records 是行） |
| `doc_qa` | `{"status": "success"\|"no_doc_attached"\|"failed", "mode": "retrieval"\|"fulltext", "sources": [...], "attached_docs": [...], "retrieval": {"mode","blocks","truncated","notes"}}` | 正文 + **来源列表**（§3.3） |
| **`deep_agent`** | `{"trace": {…}, "draft_answer": "…"}` | 正文 + **多步检索轨迹**（§3.4） |
| `chat` | `null` 或无 | 纯文本气泡 |
| `safety` | `{"status": …}`（拒答/边界引导） | 正文（安全提示样式可选） |
| `fallback` | `null` 或无 | 降级提示文案 |

> ⚠️ `data` 是**通用容器**，不同分支键不同。前端应按 `reply_type` 分支渲染，**不要假设固定字段**。

### 3.3 `doc_qa` 的 `sources` 与 `retrieval`（长文档检索模式）

带文件提问时 `doc_qa` 有两种模式，由 `data.mode` 区分：

| `mode` | 何时 | `sources` | `retrieval` |
|---|---|---|---|
| `retrieval` | 文档较长（块数 > 12） | **有值**：检索到的段落 | `{mode:"retrieval", blocks:N, truncated:false, notes:[]}` |
| `fulltext` | 小文档 / 未建索引 | `[]` | `{mode:"fulltext", blocks:0, truncated:bool, notes:[…]}` |

`sources[]` 每项：

```json
{
  "doc": "智慧园区智慧化改造项目招标文件.pdf.md",
  "chapter": "… > 第四章 评标办法",     // 章节路径，可用于展示"依据哪一章"
  "chunk_index": 4,
  "content_snippet": "本项目采用综合评分法。评标委员会由七名成员组成…",
  "score": 0.647                        // 余弦相关度（0~1）
}
```

**`retrieval.notes[]`**：后端给出的**显式提示**，建议直接展示给用户（第 3 项 C2 兜底）：
- 命中相关度低于阈值 → `"⚠️ 在《X》中未检索到与问题高度相关的段落（最高相关度 0.42），以下回答仅供参考。"`
- 全文模式被截断 → `"⚠️ 文档内容较长（共 N 字符），本次仅使用了前 M 字符…"`
- `truncated: true` 表示上下文确实被截断（配合上一条文案）

### 3.4 `deep_agent` 的 `trace`（多步检索轨迹）

**什么时候会落到它**：**上传了文件** 且 问题含跨源信号（合规/依据/处罚/记录…）——即
"要拿文件内容去跟法规或业务数据比对"的问题（后端闸门判定，配置在
`orchestration/routing_rules.yaml` 的 `agent_gate` 段）。纯文件问题仍走 `doc_qa`（更快）。

```json
{
  "trace": {
    "mode": "plan_and_solve_reflect",
    "rounds": 1,
    "plan":    [ {"id":1, "objective":"查法规依据", "tool":"kb_search_tool", "query":"…", "depends_on":[]} ],
    "steps":   [ { /* 见下 */ } ],
    "reflection": {"verdict":"adequate|revised|gap", "notes":"…", "revised_answer":"…"}
  },
  "draft_answer": "反思前的草稿（answer 是最终答案，可能已被 revised 覆盖）"
}
```

`steps[]` 每项：

```json
{
  "step_id": 1,
  "tool": "read_file | kb_search_tool | price_query",
  "query": "实际传给工具的查询",
  "status": "ok | empty | error",
  "observation_head": "该步观察摘要（截断）",
  "records_count": 6,
  "latency_ms": 657,
  "sources": ["某标书.pdf｜招标文件 > 第三章 投标保证金", "…"]
}
```

**前端建议**：
- `sources[]` 就是**可核验的引用来源**（`doc_name｜chapter`）——想做"依据来自哪一章"的展开，用它；
  注意它是**每步**的来源，与最终回答里实际被引用的可能不完全一致（后端有"引用覆盖率"指标在盯这个）
- 用 `steps[].status` 展示"检索了几步、哪步空了"——**这是 agent 路径唯一的进度信息**
  （整条链路不可中断、无中间事件；要真进度需 SSE，见 §4）
- `latency_ms` 单步耗时可用于排查"为什么这次慢"

### 3.3 业务错误（HTTP 200 + `error_code`）

| `error_code` | 含义 | 前端文案建议 |
|---|---|---|
| `biz_1002` | 无有效实体（如问"有哪些公司中标"但没给公司名） | "请补充更具体的公司名称/项目" |
| `biz_1003` | 检索为空（知识库无相关内容） | "知识库中没有找到相关内容" |
| `biz_1004` | 引用护栏未通过 | 正常展示答案即可（内部质量标记） |
| `biz_1005` | 能力边界（问到了不支持的功能） | 展示答案（内含引导） |
| `biz_1006` | 未授权（`API_KEYS` 已设置但请求未带/带错 key） | **提示未授权**——当前**没有登录页可跳**（匿名优先，见 §0 登录/租户方案）；提示"请配置访问密钥或联系管理员" |
| `sys_2003` | 被限流 | 退避重试 |
| `sys_2004` | 服务过载（闸门打满） | 按 `Retry-After` 重试 |
| `sys_2500` | 内部错误 | "服务异常，请重试" |
| `model_3001/2/3` | LLM / Embedding / Reranker 调用失败 | "模型服务暂时不可用" |
| `dep_4001/4002` | Milvus / MySQL 不可用 | "依赖服务暂时不可用" |

## 4. `POST /chat/stream`（SSE）

**请求**：同 `/chat`，但 `"stream": true`（否则降级为普通响应）

**响应** `text/event-stream`，事件序：

| 事件 | data | 说明 |
|---|---|---|
| `session` | `{"session_id": "..."}` | **首个事件**，前端应立刻保存 |
| `token` | `{"delta": "根据"}` | 增量 token，**逐帧追加展示** |
| `result` | `ChatResponse` + `session_id` | **终态权威结果**（含 citations/data） |
| `error` | 统一错误信封 | 出错时 |
| `done` | `{}` | 流结束 |

**前端约定**
- 用**累积的 token** 做打字机效果；收到 `result` 后用 `result.answer` **覆盖**（权威）
- 必须处理"只有 `error` + `done`"的情况（如闸门打满时直接返 503 信封）
- SSE 建议用 `EventSource`（注意：`EventSource` 只支持 GET，**本端点是 POST** → 需用 fetch + ReadableStream 或 `@microsoft/fetch-event-source`）

## 5. 建议的前端调用流程

```
① 首轮提问
   POST /chat {question}                        → 保存 session_id

② 多轮追问
   POST /chat {question, session_id}            → 上下文自动延续

③ 上传文件
   POST /files/upload/async?session_id=<sid>    → 立即拿 file_id
   轮询 GET /files/{file_id}/status (1~2s)      → status=done
   POST /chat {question, session_id, file_ids:[file_id]}
     → reply_type="doc_qa"     纯文件问题（快，1~2s）
     → reply_type="deep_agent" 带文件 + 跨源问题（**9~15s**，需 loading 与进度感知）
     ⚠️ 不带 file_ids 时服务端也会**自动附着本会话最近 1 个文件**（弱信号，L1 规则优先）

④ 流式展示（推荐）
   POST /chat/stream {question, session_id, stream:true}
   逐 token 渲染 → result 覆盖 → done 收尾
   ⚠️ agent 路径**只在 SYNTHESIZE 阶段产 token**（规划/检索期间无 token）
   → 前 5~10s 界面无输出属正常，建议先显示"正在检索并核对依据…"的占位
```

## 6. 前端必须处理的边界

| 场景 | 触发 | 处理 |
|---|---|---|
| **限流 429** | 同一用户快速连续请求（如连传多个文件） | 退避 + 提示；上传建议串行 |
| **过载 503** | 同时请求 > **128** | 读 `Retry-After` 退避重试 |
| **上传 413 / 400** | 超 20MB / 扩展名不符 | 前端先校验，给明确提示 |
| **刷新后上下文丢失** | `session_id` 没持久化 | 存 localStorage |
| **文件过期 404** | 上传后超 1 小时才提问 | 提示重新上传 |
| **答案引用** | 正文含 `【来源N】` | 用 `citations` 渲染可点击来源 |
| **`data` 形状不定** | 不同 `reply_type` | 按 `reply_type` 分支渲染；**别忘了 `deep_agent`** |
| **agent 路径慢（9~15s）** | 带文件 + 跨源问题 | 必须给 loading / 占位文案；流式下前 5~10s 无 token 属正常 |
| **扫描件 PDF 慢** | 无文本层 → 走 MinerU | 进度提示；异步端点下用户无感（提交仅 0.12s） |

## 7. 实测性能参考（用于设计 loading 与超时）

| 操作 | 实测 |
|---|---|
| 提问（知识问答 `kb_answer`） | p50 **2.2~3.0s**、p95 **3.2~3.5s** |
| 提问（纯文件 `doc_qa`） | **0.6~2.1s**（小文档全文模式更快，长文档检索模式约 2s） |
| **提问（`deep_agent`，带文件 + 跨源）** | **9~15s**（实测 8.9 / 9.0 / 9.4 / 15.5s；随工具步数与检索耗时浮动） |
| 异步上传提交响应 | **0.12s** |
| 30 页电子版 PDF 解析 | **5~10s**（后台） |
| 扫描件 PDF 解析 | 分钟级（需 MinerU） |
| 并发能力 | 16/40 并发实测 100% 成功；闸门上限 **128**（进程级），超出返 503 |

**建议前端超时**：`/chat` ≥ 60s（**agent 路径 15s+ 属正常，别按 30s 掐**）；
`/chat/stream` ≥ 120s；轮询单次 ≥ 10s。

> ⚠️ **`deep_agent` 的 9~15s 是设计取舍**：它要多轮 LLM + 工具调用，换来的是
> "能答出只有检索才能得到的条款、且带可核验引用"（实测：不可猜跨源题答案命中
> 43% → 100%）。前端不要试图用短超时把它掐掉 —— 掐掉等于退回到"答不出依据"。
