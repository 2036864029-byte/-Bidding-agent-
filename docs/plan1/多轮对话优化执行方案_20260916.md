## §0 背景与根因（本次要解决的问题）

现象：主对话"招标方式有哪些？"正常回答；追问"具体介绍一下？"返回拒答；整体耗时 4~8s。

根因（代码定位，2026-09-16 审计）：

1. **省略式追问未被改写**：`agent/nodes/rewrite.py:67` `looks_like_followup` 只认 16 个指代线索词
   （`rewrite.py:37-40` 那/这/它/该/其/换/继续…）。"具体介绍一下？"是**零代词省略式追问**，
   不命中 → 不改写。这正是 `rewrite.py:13-16` 注释里写明的已知限制。
2. **检索只读最后一条消息**：`agent/nodes/knowledge_qa/subgraph.py:159`
   `question = str(messages[-1].content)` —— 拿原始"具体介绍一下？"做 Milvus 语义检索，
   无命中 → `_route_after_retrieve` refuse 分支 → `subgraph.py:38` 拒答文案。
3. **路由的理解被丢弃**：`agent/router.py:76-83` `RouterDecision` 只有 `{intent, reason}`，
   从历史判断出的指代对象没有物化给下游（`resolved_question` 不存在）。
4. **耗时**：`.workbuddy/backend_8000.log` 实测 router L3 单次 LLM 1.1~1.3s、价格链路整链
   1.8~2.5s；知识链路还要叠加 embedding+Milvus+rerank+生成+护栏，且**拒答路径也全额付检索成本**
   （`kb_search_expanded` 在 base 为空时仍跑子句补检，`public_kb/tools.py:332` `len(docs)=0<20` 恒真）。

## §1 方案总览（工业五层 → 落地五个 Phase）

| 工业层 | 落地 Phase | 风险 | 依赖 |
|---|---|---|---|
| L0 评测基座 | **Phase 0** 多轮金标 + 闸门 | 低 | 无 |
| L1 查询改写 | **Phase 1** 改写触发放宽 | 低 | Phase 0 |
| L3 路由即规划（合并 rewrite+route） | **Phase 2** 会话理解节点 | 中 | Phase 1 |
| L4 澄清式反问 | **Phase 3** clarify 三档兜底 | 中 | Phase 2 |
| L5 检索/观测/成本 | **Phase 4** 观测字段 + 空检短路 | 低 | — |
| L2 结构化会话状态（DST） | **Phase 5**（远期，仅预留） | 高 | 后续 |

**原则**：小步、可回滚（每个新行为带配置开关）、每 Phase 先补测试再改代码、金标跑稳再进下一步。

**核心决策**（Phase 2 的中心思想）：把"改写"与"路由"合并为**一次** LLM 结构化调用，输出
`{intent, resolved_question, needs_clarification, candidates}`，`resolved_question` 原位替换
`messages[-1]` 物化进 state —— 下游检索直接用改写后问题。一次调用同时修正确性与延迟
（追问轮从"改写+路由=2 次 LLM"降为"恒 1 次"）。

## §3 Phase 1 —— 改写触发放宽（止血，低风险）

### 目标
"具体介绍一下？"类省略追问能触发改写；自包含问题零成本直通；不新增问候类误伤。

### 改动 `agent/nodes/rewrite.py`
- `looks_like_followup` 逻辑升级（保留原接口签名，调用方零改动）：
  - 现有线索词命中 → True（保持现状行为）。
  - **新增省略式判据**：≥2 条用户轮次 **且** 末条问题去空白后 ≤12 字 **且** 不含话题词/疑问词
    （`什么/如何/哪些/多少/谁/吗/是不是/招标/投标/采购/公司/项目/处罚/金额/价/资质…`）→ True。
  - **新增问候排除**：末条 ∈ {你好,您好,hi,hello,再见,谢谢,你能做什么…} → False
    （避免 supervisor L1 快路径之前白付一次 LLM）。
- 新设置 `multiturn_rewrite_trigger: "heuristic"|"hints"|"always"`（`core/config/settings.py`，
  env 覆盖 `MULTITURN_REWRITE_TRIGGER`，风格与现有 field 一致），默认 `heuristic`；
  `always` = 2 轮起全部走改写（安全但每次 +1 次 LLM，留给"宁多勿漏"场景）。
- `rewrite_question` 增加 span 埋点：`span("node.rewrite")` + `ztb.rewrite.original/.resolved`
  （复用 `core.observability.tracing.observation_io`），trace 可见改写前后对照。

### 测试 `test/agent/test_rewrite_node.py`（扩展，不删旧断言）
- `"具体介绍一下？"`（前置 1 轮）→ True
- `"大概多少钱？"`（前置价格轮）→ True
- `"什么是公开招标？"`（前置 1 轮）→ **False**（原断言保持）
- `"你好"`（前置 1 轮）→ False
- 首问 `"你好"` → False

### 验收
- 单测全绿；复现用例 R1 turn2 日志出现 `查询改写: '具体介绍一下？' -> '...'`。
- 回滚：`MULTITURN_REWRITE_TRIGGER=hints` 恢复现状。

## §4 Phase 2 —— 会话理解节点（合并 rewrite+route，治本 + 省一次 LLM）

### 目标
一次 LLM 结构化调用同时产出意图与消解后问题；`resolved_question` 物化进 state，
下游检索直接用改写后问题。**改提示词 = 改路由行为，须重跑 router golden 并重新冻结真值**。

### 4a 决策模型扩展 `agent/router.py`
- `RouterDecision` 增加可选字段：
  ```python
  resolved_question: Optional[str] = Field(None, description="追问时输出消解后的自包含问题；自包含留空")
  needs_clarification: bool = Field(False, description="无法消解时置 True（Phase 3 用）")
  candidates: list[str] = Field(default_factory=list, description="澄清候选，≤3 条")
  ```
- `ROUTER_USER_TEMPLATE` 增指令："若当前问题是追问（指代/省略上文实体），先输出
  `resolved_question` 为去掉指代、补齐实体的独立问题；**再基于改写后的问题**选择 intent。
  自包含问题 `resolved_question` 留空。"（`with_structured_output` 下 optional 字段自动跳过）。
- `router_node`：当 `resolved_question` 非空且 ≠ 原文 → 返回
  `{"router_intent": intent, "messages": [HumanMessage(content=resolved_question, id=messages[-1].id)]}`
  —— 同 id 原位替换，`add_messages` 合并，业务节点看到归一化问题（与现 rewrite 节点同机制，
  `rewrite.py:124`）。
- `looks_like_followup` 保留作**经济预判**：首问/自包含（False）无需改写，走单次结构化调用且
  `resolved_question` 恒 None，不产生额外成本。

### 4b 单图接线 `agent/graph.py`
- 删除入口 `rewrite` 节点（职责并入 router_node）：`START → router → 业务节点`。
- 条件边新增 `clarify` 目标（本 Phase 先接 stub 节点或仅预留边；Phase 3 填实）。
- 开关 `understand_merged: bool = True`（env `UNDERSTAND_MERGED`）；`False` 时回退旧拓扑
  （保留 `rewrite` 节点代码与接线）。

### 4c supervisor 接线 `orchestration/supervisor.py` + `main_graph.py`
- `route_question` 返回值从 `str` 改为 dataclass `RouteResult(intent, resolved_question=None,
  needs_clarification=False, candidates=[])`。
- `supervisor_node`（`supervisor.py:326-334`）：拿到 `RouteResult` 后，若 `resolved_question`
  非空 → 原位替换 `messages[-1]`；设 `supervisor_route=route.intent`。
- 主图 `main_graph.py:182-185`：删除入口 rewrite 节点；supervisor 条件边加 clarify。
- **L1/L2 仍跑原始问题**（快路径：问候/项目编号类零 LLM）；只有 L3 是合并调用 —— 这样
  "你好"先被 L1 拦截，不会为改写白付 LLM。

### 测试
- `test/agent/test_router*.py`、`test/test_sub_route.py`：mock LLM 返回含 `resolved_question`
  的决策 → 断言 `state.messages[-1]` 被原位替换、意图正确；自包含 → 不替换。
- `test/agent/test_rewrite_node.py` 保持不动（rewrite 模块保留作回退路径）。
- supervisor 测试：注入假 `llm_router` 返回 `RouteResult` → 断言替换生效、`supervisor_route` 正确。

### 验收
- R1/R2 全绿；router golden 集无回归（重生成新版本冻结）；每轮 LLM 调用数：追问轮恒 1 次。
- 回滚：`UNDERSTAND_MERGED=false` 恢复旧拓扑。

## §5 Phase 3 —— 澄清式反问（三档兜底）

### 目标
改写/路由置信度不足时，反问 + 一键候选，替代硬拒答（工业界第三档兜底）。

### 后端
- 新节点 `agent/nodes/clarify.py`：
  ```python
  def node_clarify(state): 
      return {"business_result": {"branch": "clarify",
              "answer": "您是想问以下哪个？", "data": {"candidates": [...]}},
              "messages": [AIMessage(content="您是想问以下哪个？")]}
  ```
- 仅在 `RouterDecision.needs_clarification=True` 且 `candidates` 非空时走本节点（图条件边）。
- `core/protocol/reply.py`：`ReplyType` 增 `"clarify"`；`_BRANCH_TO_REPLY["clarify"]="clarify"`；
  `to_reply` 不改 error_code（澄清不是错误）。

### 前端
- `frontend/src/types/chat.ts`：`ReplyType` 增 `'clarify'`；`ChatData` 增
  `{ kind: 'clarify'; candidates: string[] }`。
- `adapters/chatAdapter`：`reply_type==='clarify'` → 映射。
- 聊天渲染器注册表（7 分支同源处）：clarify 渲染为一句引导 + 候选 chips；
  点击 chip → 以候选文本走 `submit()`（复用现有流式链路，Phase 4 接缝已留）。
- 测试：`frontend/src/test/chat-renderers.test.tsx` 增 clarify 用例；typecheck / test / build 全绿。

### 验收
- 前端点击候选能发起新一轮提问；无文件场景澄清率 <10%（金标抽样观测）。
- 回滚：`CLARIFY_ENABLED=false` → clarify 决策降级为直接按 intent 路由。

## §6 Phase 4 —— 观测字段 + 检索成本（低风险，独立）

### 6a 观测字段（Langfuse 全链路可核对改写前后）
- Phase 2 的 router/understand span 上写 `ztb.understand.original / .resolved / .needs_clarification`；
  Phase 1 的 rewrite span 写 `ztb.rewrite.*`。`core/observability/tracing.py` 无需改动
  （复用 `set_span_attrs` / `observation_io`）。
- 目的：每轮 trace 可见"原问题 → 改写后问题 → 检索 → 重排"，E4-1 回灌金标直接核对。

### 6b 空检索跳过子句补检 `public_kb/tools.py:kb_search_expanded`
- 现逻辑 `if clauses and len(docs) < max_chunks:` 在 base 为空时仍跑子句检索
  （`len(docs)=0<20` 恒真）→ 拒答路径白付多次 embedding+Milvus。改为 `if docs and clauses and ...`。
- 单测：base 空 + 有子句 → 不再调用子句 retrieve（`test/test_recall_optimization.py` 扩展或新增）。

### 验收
- 拒答路径不再付子句补检；trace 出现改写前后对照字段。
