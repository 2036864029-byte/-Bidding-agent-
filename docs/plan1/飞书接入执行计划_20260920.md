# 飞书接入执行计划

> 版本：v1.1 · 2026-09-21
> 状态：**待评审**（本文只做方案，不含任何代码改动）
> 目标：在手机上通过飞书提问 → 本地电脑（唯一服务器）产出答案 → 回传飞书
> 结构：**一条基建（P0）+ 两条并行线** —— 并行线 A「任务进度推送」（**优先交付**）、
> 主线「机器人问答」（P1~P5）。v1.1 新增并行线 A（§4A），基于用户 2026-09-21 拍板。

---

## 0. 目标与非目标

### 目标
1. 用户在飞书（手机端）向机器人提问，拿到与前端对话控制台**同源**的回答
2. 多轮上下文、引用来源、澄清反问等能力与现有 7 个回答分支保持一致
3. 单机（本地电脑）可承载，不影响现有前端与后端服务
4. （**并行线 A，最优先交付**）网页端发起的长任务（大文件解析 / 长提问）进度与结果摘要，推送到用户手机飞书——用户在电脑上传后离开，手机上看进度与结果

### 非目标（本期明确不做）
- 不做面向任意飞书用户的公开分发（需「商店应用」+ 飞书官方审核，是另一条产品线）
- 不做飞书内嵌网页应用（H5 工作台），只做**机器人形态**
- 不改造现有 `/chat` 契约与前端；飞书是**新增消费方**，不修改既有生产路径
- 不做多副本/分布式部署（单机前提，见 [[本地电脑成为唯一服务器]]）

## 1. 现状评估：可复用的接缝

**结论：本项目的入口分层已经就位，飞书通道是「第三个入口」**，形状与既有的两个完全一致。

### 1.1 已有的两个入口（飞书要照抄的形状）

| 入口 | 位置 | 做的事 |
|---|---|---|
| HTTP | `api/server.py` | 请求 → `agent.invoke` → `to_reply` → `reply_to_response` |
| CLI | `api/cli.py:48-57` | 问题 → `agent.invoke` → `to_reply` → `render_reply` |

`api/cli.py` 已经证明「非 HTTP 入口」这件事在本项目成立：它只做三件事 —— 调图、转协议、渲染。飞书通道 = 同样三件事 + 飞书 SDK。

### 1.2 三个关键接缝（都有代码证据）

**① 会话模型天生适配**（`api/server.py:63`）
```python
def _resolve_session_id(session_id: Optional[str]) -> str:
    return session_id or uuid.uuid4().hex
```
「带则沿用、未带则生成并回传」。飞书的 `open_id`（私聊）/ `chat_id`（群）直接当 `session_id` 传入 →
多轮上下文（MemorySaver 检查点）、文件归属校验、`tenant_scoped` 隔离**全部复用，零改动**。

**② 非流式端点返回的形状就是飞书要的**（`api/schemas.py:27-46`）
`POST /chat`（`stream=false`）返回 `{answer, reply_type, citations, data, latency_ms, session_id, error_code}`。
飞书不支持流式 → **完全不需要碰 SSE 链路**（`_sse_stream`）。

**③ 出口协议已抽象，7 分支映射已完成**（`core/protocol/reply.py:16-35`）
`ReplyType` 八值 + `_BRANCH_TO_REPLY` 已把分支判完。飞书只需新增一个**渲染器**，
与 `core/protocol/renderers/{api,cli}.py` 并列。

### 1.3 已就位的两个「白拿」能力

**按用户限流 + 按用户隔离 —— 用现成的 `X-Tenant-ID` 头**

- 限流键：`api/middleware/rate_limit.py:99-107` —— `X-Tenant-ID` → `X-Forwarded-For` → 直连 IP
- 隔离：`core/observability/context.py:69` `tenant_scoped()` → `thread_id = "{tenant}::{session}"`

> ⚠️ **这是本方案最容易踩的坑**：飞书通道是**单一进程**调 `/chat`，
> 若不传 `X-Tenant-ID`，**所有飞书用户在限流器眼里是同一个客户端**（同一 IP）
> → 一个人刷爆就把其他人全 429 了。必须传 `X-Tenant-ID: feishu:<open_id>`。

**错误码已分类**（`core/errors/codes.py:22-53`）
`biz_*` / `sys_*` / `model_*` / `dep_*` 四类，可直接映射为飞书的友好文案。

### 1.4 数据契约（飞书渲染的输入）

`agent/guardrails/output.py:34-42` 定义了每个分支的 `data` 必含字段：

| branch | data 必含 | 飞书渲染方式 |
|---|---|---|
| `knowledge_qa` | — （引用在 `reply.citations`） | 正文 markdown + 引用区 |
| `price_inquiry` | `records` | **原生 table 组件**（见 §3.3） |
| `general_chat` | 无 | 纯文本 |
| `doc_qa` | `status` | 正文 + 状态 |
| `deep_agent` | `trace` | 正文 + 思维链折叠区 |
| `safety` | 无 | 提示卡 |
| `fallback` | 无 | 错误卡（含 `error_code` 文案） |
| `clarify` | `candidates` | **卡片按钮**（点击即追问） |

`price_records` 的行列契约（`price_engine/rendering/output_templates.py:354-364`）：
```python
rows = [{"winning_amount": ..., "project_name": ...}, ...]   # 机器键
columns = [{"key": "winning_amount", "label": "中标金额"}, ...]
```
前端消费同一份（`frontend/src/adapters/chatAdapter.ts:236-244`）——
**飞书渲染器对齐同一个契约，不引入第二套字段映射。**

## 2. 架构决策

### D1：飞书通道作为**独立进程**，通过 **HTTP** 调本地 `/chat`

```
飞书云 ──(长连接/出站)──> channels/feishu (本机进程) ──HTTP──> 127.0.0.1:8000 /chat
                                                              (已有进程，AgentGraph 单例)
```

**为什么不是「进程内直接 import AgentGraph」**（像 `api/cli.py` 那样）：

| | 进程内 | **HTTP 客户端（选它）** |
|---|---|---|
| 图实例 | 再起一个 → 检查点/会话状态与 8000 分家 | 复用唯一实例 |
| 限流 | 绕过 | 白拿 |
| 在飞闸门 `InflightGate` | 绕过 | 白拿 |
| 审计 `record_audit` | 绕过 | 白拿 |
| OTel trace | 需另配 | 白拿（同一 trace 链路） |
| 错误信封 | 需另做 | 白拿（统一 `error.code`） |
| 迁移到别的机器 | 重新初始化模型 | **只改一个 base URL** |

代价：本地多一跳 HTTP（~1ms，可忽略）；`API_KEYS` 非空时要给通道配一个 key
（**不要**把 `/chat` 加进 `auth_exempt_paths` —— `api/middleware/auth.py:29-31`）。

### D2：长连接模式（不使用 Webhook）

飞书开放平台支持 WebSocket 长连接：本机**主动出站**连飞书，**不需要公网 IP、不需要内网穿透**。
这与本机作为唯一服务器的现实天然契合。

### D3：`python -m channels.feishu` 作为进程入口；`channels/` 为新增顶层包

- `api/` 的语义是「FastAPI HTTP 层」，飞书是独立的常驻进程，不应塞进去
- 留出 `channels/` 给未来的其它通道（钉钉/企业微信），避免日后重构
- `python -m` 入口**不需要** `sys.path` 前置 hack，因此**不需要**新的 ruff per-file-ignore
  （`api/cli.py` 那类 `E402` 例外见 `pyproject.toml:69-75`）

## 3. 关键设计

### 3.1 目录与文件清单

```
channels/
  __init__.py
  feishu/
    __init__.py
    __main__.py          # python -m channels.feishu 入口（装配 + 启动）
    config.py            # FeishuConfig（读 Settings，不另建配置源）
    client.py            # lark-oapi 装配：ws.Client + message/reaction 调用封装
    handler.py           # 事件处理：解析消息 → 调后端 → 回复（含并发与幂等）
    backend.py           # 后端 HTTP 客户端（调 /chat、/files/upload），含 X-Tenant-ID
    render.py            # ★ AgentReply → 飞书卡片（本计划的主要工作量）
    session.py           # open_id/chat_id → session_id 映射（可纯函数，无状态）
    cards/               # 各分支的卡片模板（可选拆分，见 P2）
      __init__.py
      table.py           # records/columns → 原生 table 组件
```

### 3.2 会话映射

| 飞书场景 | 标识 | session_id |
|---|---|---|
| 私聊 | `open_id` | `fs-p2p-<open_id>` |
| 群聊 | `chat_id` + 发言人 `open_id` | `fs-group-<chat_id>` |

群聊按 `chat_id` 共享会话（群里的人看到同一个上下文），私聊按人隔离。
`X-Tenant-ID` 一律用 `feishu:<open_id>`（**按人限流**，而非按群/按整个通道）。

> ⚠️ 安全：`set_tenant_id`（`core/observability/context.py:60-61`）**不做校验**，
> 原样进入命名空间字符串。飞书 `open_id` 形如 `ou_xxxxxxxx`（安全），
> 但**必须显式白名单校验**（如 `^[A-Za-z0-9_-]{1,64}$`），防止非法字符进入命名空间/日志。

### 3.3 卡片渲染（核心工作量）

**关键约束（已核官方文档）**：
- 卡片 JSON 2.0 必须**显式声明** `{"schema": "2.0", "body": {"elements": [...]}}`
- **markdown 表格不被卡片支持** —— 不能把 `answer` 里的 `|` 竖线当表格贴上去
- 表格必须用**原生 `table` 组件**，且：**不可嵌套**（只能放 `body.elements` 根层）、
  **单卡最多 5 个表格**、`columns` 最多 50 列、`page_size` ∈ [1,10]
- `columns[].data_type` 支持 `text` / `lark_md` / `number`(带 `format.symbol/precision/separator`) / `options` / `persons` / `date`

**映射设计**：`data.columns[].label` → `display_name`，`data.columns[].key` → `name`，
`data.records` → `rows`（行键已是机器名，**直接对齐，无需转换**）。

金额列可映射 `data_type: "number"` + `format:{symbol:"¥", separator:true}` —— 这正是
`price_engine` 里 `winning_amount` 这类字段的天然归处。

**注意 `answer` 与 `data` 的分工**：`answer` 是**纯文本叙述**，价格类的列表行是竖线分隔的
（`price_engine/rendering/answer_templates.py:231-234`）：
```
1 [AH2024-001] 某某项目 | 某某单位 | 中标 某某公司 | 2024-05-01 | 预算 xxx | ...
```
→ **卡片正文只用 `answer` 的引导句/结语，列表部分改由 table 组件承载**，
避免同一批数据在飞书里出现两次（一次竖线文本、一次表格）。

**clarify 的候选 → 卡片按钮**：`data.candidates` 是字符串数组
（`agent/nodes/clarify.py:40-52`），1 个候选 = 1 个按钮，
按钮 value 带候选文本，点击回调直接作为新问题提问。这是飞书端体验最好的一个分支。

### 3.4 长耗时处理（必须做，否则用户以为机器人死了）

一次问答 3~10s，`deep_agent` 更久。方案：

1. **即时 ack**：收到消息立刻打一个 emoji reaction（`im.v1.message_reaction.create`）
   —— 最轻的「已收到」信号，不产生消息噪声
2. **可选**：回一张「正在查询…」占位卡，拿到结果后 `message.patch` 原地更新为结果卡
3. **事件处理不阻塞长连接线程**：丢进线程池/队列，立即返回

### 3.5 后端 HTTP 客户端（`backend.py`）

- `POST /chat`（`stream=false`），超时给足（建议 120s，`deep_agent` 慢）
- 请求头：`X-API-Key`（若 `API_KEYS` 非空）、`X-Tenant-ID: feishu:<open_id>`、
  `X-Request-ID`（透传，便于与后端日志/trace 串联 —— `api/middleware/request_context.py:36`）
- **直连环回必须绕开系统代理**：复用 `core/net.py` 的
  `ensure_no_proxy_for_loopback()` / `is_loopback_url()`（本项目已踩过这个坑）
- 响应：`reply_type` 分发到 `render.py`；`error_code` 非空 → 错误卡

## 4A. 并行线 A：任务进度推送（优先交付线）

> 用户已拍板（2026-09-21）：**先做本线，机器人问答（主线 P1~P3）随后**；粒度 = 里程碑 + 结果摘要，不做百分比；推送 = 进度 + 结果摘要。

### 4A.0 目标与非目标

**目标**：用户在**网页端**上传大文件 / 发起长提问 → 前端弹提醒（情况1/情况2）→ 用户点「连接飞书」完成绑定 → 任务里程碑（开始/完成/失败）+ 结果摘要推送到用户手机飞书。

**非目标**：
- 不做解析**百分比**（MinerU 不吐进度，现状无数据源，硬做要改解析流程且做不准）
- 不做「飞书内嵌网页应用」；OAuth 只是授权跳转，不是嵌页
- 不依赖机器人问答（主线）——本线在 P0 后独立可交付

### 4A.1 链路设计（四环）

```
环1 连接绑定：前端点「连接飞书」→ 跳 authorize 页 → 回调 code
              → authen/v1/oidc/access_token（响应含 open_id）
              → 存 Redis：web_session_id ↔ open_id（TTL）
环2 里程碑事件源：
              · 上传解析 → core/jobs 的 _run/_finish 状态迁移钩子
              · 长提问   → SSE 的 result/error 事件钩子
环3 推送：im.message.create + tenant_access_token + receive_id_type=open_id
环4 前端提醒：FileChips 状态机 + 上传触发弹窗（情况1/情况2）
```

**环 1 详细**（本线特有的新增，主线没有）：
- 跳转：`https://accounts.feishu.cn/open-apis/authen/v1/authorize?client_id=<app_id>&response_type=code&redirect_uri=<已配白名单>&scope=contact:user.base:readonly&state=<web_session_id>`
- 回调：新后端端点换 token → 拿 `open_id` → 绑定写入 Redis（TTL 建议与会话 TTL 一致）
- 判定：前端调「绑定查询」接口 → 返回 bool → 决定情况 1 / 情况 2 文案
- 安全：`state` 必须校验（防 CSRF）；`open_id` 白名单校验后入命名空间（同 D5 的坑）

**环 2 详细**（现状支持里程碑，需加钩子）：
- 上传解析：`core/jobs/queue.py:196-207` 的 `_run`（开始）/ `_finish`（完成/失败）是现成的状态迁移点，挂钩子发里程碑事件（带 task_id / file_id / 文件名）
- 长提问：`api/server.py` 的 SSE `result` / `error` / `done` 事件（`_sse_stream`）是现成事件点，挂钩子发「回答就绪」
- 事件带 `web_session_id`（提问来自网页端该会话）→ 环 3 查绑定

**环 3 详细**：
- 权限 `im:message:send_as_bot`；调用频率上限 1000 次/分、单用户 5QPS，个人单机远够
- **硬前提**：用户必须在机器人可用范围内（P0 配置保证）
- 推送失败（用户未在可用范围等）只记日志，**不阻塞业务**（同 rerank 降级原则，但不能静默——至少要能查日志）

**环 4 详细**：
- 触发点：上传成功但 `status ∈ {pending, processing}`（即走了异步解析）时弹提醒
- 情况 1（未绑定）：文案「您可以连接飞书，方便您在手机端了解任务执行进度」+ 按钮「是否连接飞书」→ 点是 → 跳 OAuth
- 情况 2（已绑定）：文案「您已经连接了飞书，可以随时在移动端了解任务执行进度」
- 提醒只弹一次/会话，避免打扰；`localStorage` 记已提醒标记

## 7. 风险与应对

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | **本地电脑是单点**：休眠/重启/断网 → 所有用户不可用 | 高 | P5 常驻 + 开机自启；明确告知使用者可用时段 |

| R3 | 限流桶坍缩：不传 `X-Tenant-ID` → 所有飞书用户算一个客户端 | 中 | P1 强制带上；加用例锁死 |

（不动 `/chat`、不动前端、不动 `agent/`），删除 `channels/` 即完全回退。

## 9. 决策记录

| # | 决策 | 理由 |
|---|---|---|
| D1 | 独立进程 + HTTP 调 `/chat` | 复用限流/闸门/审计/trace；迁移只改 base URL |
| D2 | 长连接，不用 Webhook | 无需公网 IP / 内网穿透，契合单机现实 |
| D3 | 新增 `channels/` 顶层包 | 与 `api/`（HTTP 层）语义分离，留扩展位 |
| D4 | 渲染器对齐既有 `records/columns` 契约 | 不引入第二套字段映射，前端/飞书同源 |
| D5 | 按用户 `X-Tenant-ID` | 限流与隔离都按人，防单人拖垮全体 |
| D6 | 复用 `to_reply` + 新增 `renderers/feishu` | 与 api/cli 渲染器并列，符合既有分层 |
| D7 | **任务进度推送与机器人问答解耦成两条并行线** | 进度推送依赖的飞书能力 ⊂ 机器人问答（不需要长连接/事件订阅/卡片渲染），共享的只有 P0 基建；进度推送更简单、更早见价值，**优先交付**（用户已拍板） |
| D8 | 进度推送 = 里程碑 + 结果摘要，不做百分比 | 现状 job 状态/SSE 事件只有里程碑；MinerU 不吐解析百分比，硬做要改解析流程且做不准（用户已拍板） |
| D9 | 网页「连接飞书」= 飞书 OAuth 授权绑定 | `authen/v1/oidc/access_token` 响应直接含 open_id；绑定 `web_session_id ↔ open_id` 存 Redis，是「情况1/情况2」判定的唯一依据 |
