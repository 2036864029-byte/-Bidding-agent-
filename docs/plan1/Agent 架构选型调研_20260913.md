## 0. 结论（先行）

1. **Plan-and-Solve 与 ReAct 能融合，且这正是 2024–2026 的主流演进方向。** 我们缺的
   恰恰是业界公认的那一环 —— **重规划（Replanning）**。而且**融合点的钩子在我们代码里
   已经埋好了**（§2）：`REFLECT` 已经算出 `verdict=="gap"`，只是被忽略。
2. **但在我们系统里，这个问题可能根本不该用 agent 解。** 「带文件 + 跨模块」的两步是
   **确定性的**：有文件就该读（无歧义）、合规类问题该查法规（已有规则表）。
   上一个同形状的问题（纯文本多跳）已经证明过：**零 LLM 的确定性流水线打赢了 LLM agent**
   （双段全中 0.6286 vs 0.5143【实测】），而后者慢 **30 倍**。→ §5 的 **L1**
3. **无论选哪档，都必须先建「文件 + 跨模块」场景集门禁。** 现有金标集
   `eval/agent_golden_set.json` 32 条**全是纯 KB 多跳，零文件场景**【实测】——
   拿它验收等于没测。

## 1. 概念厘清：四种形态与它们的融合点

| 形态 | 中途依赖（能否看到结果再决定下一步） | LLM 调用 | 并行性 |
|---|---|---|---|
| **ReAct** | ✅ 每步 thought→action→observation | ~2N + 1 | ❌ 串行 |
| **Plan-and-Solve**（ReWOO 同族） | ❌ 计划一次定死（ReWOO 用 `#E1` 变量引用前序结果，我们连这个都没有） | 1 计划 + 1 综合 | ✅ 可 |
| **Plan-and-Execute + Replanning** | ✅ 每步后可改计划 | 1 + N + N | 部分 |
| **LLMCompiler** | ✅ 计划器直接输出 **DAG**（显式标注依赖与可并行项），失败可重规划 | 1 + 重规划 | ✅ 最强 |
| **Reflexion** | ❌ 只在**跨轮**用语言化反馈重试 | 每轮 +1 | — |

**我们当前处在哪一档**（逐行核对 `agent/nodes/deep_agent.py`）：

```
PLAN(1 LLM, :149) → EXECUTE(0 LLM，所有步骤**并行**，_execute_steps:241 注释"步间无数据依赖")
  → SYNTHESIZE(1 LLM, :279) → REFLECT(1 LLM, :302)
rounds 硬编码 1；REFLECT 只改答案文字，不触发补检索/重规划
```

⇒ **我们是「ReWOO + Reflexion」的混合，且两条腿都不完整**：
ReWOO 那半缺变量引用（步骤间无法传递数据），Reflexion 那半缺"反馈→重试"的动作。
**「读到文件内容后再决定查哪条法规」现在做不到。**

## 2. 融合点：钩子已经埋好，只差接线【实测·代码核对】

两处**现成的确定性信号**，都不需要新增 LLM 判断：

```python
# ① _reflect (:289) —— 三种 verdict，只有一种被用
if verdict == "revised" and revised_answer: final = revised_answer
# 「gap」（观察不足以回答）被解析、存进 trace、然后被忽略

# ② _execute_step (:203) —— 工具自己已经在报告成败
StepRecord(status ∈ {"ok", "empty", "error"}, records_count, latency_ms)
```

⇒ **「要不要再来一轮」是工具已经回答过的问题**，不需要 LLM 再判一次。
把 `gap` / `status in {empty,error}` 接到一次补检索上，是**几十行改动**（§5 的 L2）。

## 3. ⭐ 系统特有成本结构（决定选型的关键，非通用结论）【实测】

通用文章会说"多轮 agent 贵在 LLM"。**在我们系统里这句话是错的。** 两种检索的代价
差一个数量级，且瓶颈位置完全不同：

| 检索手段 | 链路 | 实测延迟 | 是否吃 GPU 瓶颈 |
|---|---|---|---|
| **`read_file`** | in-process：稠密余弦 + BM25 + RRF(k=60)，**无 cross-encoder** | **47ms**（热）/ 390ms（冷建索引） | ❌ **不吃** |
| **`kb_search`** | Milvus 混合 → **bge-reranker-v2-m3 精排** | **1313ms** | ✅ **就是瓶颈** |

瓶颈证据【实测】：rerank 占 kb 检索耗时 **~89%**（embedding 仅 ~8%），服务端吞吐
**~10.4 次/s 饱和**（并发 1/10/50 同值，34 条长候选 96ms/次）；
100 并发 `/chat` p50 8.36s；50 并发下缓存命中与否差 **6.7 倍**（3.9s vs 26.4s）。

**⇒ 迭代的代价是不对称的：反复读文件便宜，反复查法规贵。**
一个 agent 循环里多查两次 KB，挤压的是**已经饱和**的 rerank，不只是多两次 LLM。

| 每多一步的边际成本 | LLM | 工具 | 合计 | 对 GPU 瓶颈的挤压 |
|---|---|---|---|---|
| 读文件步 | ~2.5s | 0.05~0.4s | **~2.6s** | 可忽略（1 次 query embedding） |
| 查法规步 | ~2.5s | ~1.3s | **~3.8s** | **+1 次 rerank（瓶颈上）** |

> 基准：单次 LLM 调用（DeepSeek）100 并发 p50 2.46s【实测】；`deep_agent` 全跑
> 3 次 LLM 实测 **15.8s/题**，单节点 `doc_qa` 约 **0.5s** → **≈30×**【实测，见计划 §518】。

## 4. 工业界现状（本次调研）

### 4.1 取证条件（先说清可信度）

本次 **WebFetch 对所有域名被网络策略阻断**，只能读到搜索结果标题与链接。
⇒ **下文所有论文/产品的具体数字均无法核实**，凡出自记忆者已标注【记忆·未核实】。
**唯一可靠的成本锚点是我们自己的实测**（§3）。

### 4.2 官方指南的立场

Anthropic《Building effective agents》【已确认存在，原文未打开】的核心原则
【记忆·未核实】：**先用最简单的方案，只在"预定义代码路径"确实不够时才上 agent**；
并把"预定义代码路径"= workflow、"LLM 自主决定流程/工具"= agent 明确分开，
明说 **agent 是用延迟与成本换任务表现**。其五种 workflow 里的 **routing
正对应我们的 L0~L3 路由层**。

LangGraph 官方与 Anthropic 一致给出的渐进路径【记忆·未核实】：
**workflow → 单 agent → 多 agent**。我们：L0~L3 属第一档，`deep_agent` 属第二档。

### 4.3 产品侧读用户文件的公开做法

ChatGPT / Claude / NotebookLM 处理用户文件（**产品观察 + 公开文档印象，
非官方架构说明**【记忆·未核实】）：**混合式** —— 文件小则整篇进上下文，
大 / 多文件则"后台分块+索引、模型按需检索"。

共同点两条：**①上传即后台预处理；②文件读取是模型可反复调用的能力**，而非一次性塞入。
**这与 Phase G-6 的"预解析是缓存预热、工具是唯一入口"同构** ——
我们这条设计方向与产品侧一致，不是自创。

### 4.4 RAG 技术谱系（都指向"别每次固定 top-k"）

| 技术 | 解决什么 | 代价 |
|---|---|---|
| [Adaptive-RAG](https://aclanthology.org/2024.naacl-long.389/)【已确认存在】 | 先判问题复杂度，再选"不检索 / 单步 / 多步" | 多一次分类调用 |
| Self-RAG【记忆·未核实】 | 用反思 token 决定要不要检索 | 多一次模型调用 |
| CRAG (Corrective RAG)【记忆·未核实】 | 评估器把结果分 Correct/Ambiguous/Incorrect 分别处理 | 多一次评估调用 |
| **IRCoT / Self-Ask**【记忆·未核实】 | **边推理边检索**（最贴近"中途依赖"） | 多 N 次检索 |

**社区代价共识**【记忆·未核实】：这一族（统称 agentic RAG）**都多付一轮模型调用，
简单问题不该走**。

### 4.5 成本经验值

【记忆·未核实】定性共识：迭代式 tool loop 调用数 = O(轮数)，延迟近似线性，
且**每轮重放上下文 → token 成本增长更快**。建议：**固定流程能解决就别上 agent**。

**我们的实测锚点更硬**：3 次 LLM（一次性规划）= 15.8s；若改 Replanning
（2N+1 次，N=2~3）→ **5~7 次 LLM**【推算，按 §3 边际成本约 20~28s】。
⇒ **绝不能默认启用，必须门禁。**

### 4.6 LangGraph 现成组件（截至 2025-08 知识，**API 名可能已变**）

- `create_react_agent` —— 标准 ReAct 循环
- **Plan-and-Execute 官方教程自带 `replan` 节点** —— 正是我们缺的那一环
- Agentic RAG 教程（自纠正检索）
- 通用能力：checkpointer（**我们已用**，多轮持久化就绪）、`interrupt`（人在环）、
  `Send` API（动态并行 map-reduce，实现 LLMCompiler 式 DAG 的基础）

## 5. 落到我们：阶梯式路径（按代价升序，**建议逐档验证而非直接跳**）

### L1 — 确定性多源流水线（**零规划 LLM**）← 建议先做这一档

**关键发现：这一档的骨架已经在生产里跑着了，加一条 YAML 规则就能通**【实测·代码核对】

`orchestration/main_graph.py` 的 handoff 机制是完整的：每个 agent 节点都有边指向
`handoff_decider`（`:242`），decider 按 `routing_rules.yaml` 匹配，命中则

```
:78-82  存 pending_context = 本 agent 的 business_result（文件那半的答案）
        注入子问题为新 HumanMessage → 条件边路由到目标 agent
:85-104 目标 agent 跑完 → 组合终态：_compose_handoff_answer(文件答案, 法规答案)
        → 合并后的 answer，两半都留在 data.handoff_context
```

⇒ **「文件 + 跨模块」的链路与合并，零代码即可打通** —— 只需在 YAML 加：

```yaml
handoff:
  - from: doc_qa
    to: knowledge_qa
    reason: 文件问答涉及法规/合规判断，需公共法规库佐证
    keywords: [合规, 符合, 依据, 法规, 规定, 违反, 是否合法, 法律, 条例, 第几条]
```

于是 L1 分两小步，**先做 1a 验证链路，再按质量决定要不要 1b**：

| | 做法 | 改动量 | LLM 调用 | 产出质量 |
|---|---|---|---|---|
| **L1a** | 只加上面那条 YAML 规则 | **零代码**（纯数据） | doc_qa 1 + knowledge_qa 1 = **2** | 两段答案**拼接**（`_compose_handoff_answer`），不是融合判断 |
| **L1b** | 把拼接换成**一次综合 LLM**（把两半一起给它，产出真正的合规判断） | 小（改 compose + 一次 LLM 调用） | 2（其中一次是综合） | 真正的跨源判断，如"80 万 = 估算价的 X% ＞ 2% 上限 → 不合规" |

| 项 | 值 |
|---|---|
| 检索 | 1 次 read_file（47ms）+ 1 次 kb_search（~1.3s） |
| 预估延迟 | L1a ~3s；L1b ~5.5s（vs deep_agent 15.8s）【推算，按 §3 边际成本】 |
| 失败的代价 | 低 —— 纯数据改动可秒回退；且与现有 `price→knowledge` 交接同形，机制已跑在生产 |
| 处理不了的 | 源的数量/身份**无法预先确定**的场景（见 §7） |

⚠️ **L1a 的局限要说清**：`_compose_handoff_answer` 是**纯字符串拼接**（`:62` 实测实现）——

```python
return f"{context_answer}\n\n【政策法规解释】\n{final_answer}"
```

两个问题：① 用户拿到的是"文件说 X" / "法规说 Y"两段，**不是"X 违反 Y"的判断**；
② 分隔标题 `【政策法规解释】` 是 `price→knowledge` 场景硬编码的，用在
`doc_qa→knowledge` 上语义不对，至少得改成中性措辞。

⇒ **若产品要的是融合判断（"80 万 = 估算价的 X% ＞ 2% 上限 → 不合规"），
L1a 只算链路验证，必须做 L1b。**

### L2 — `deep_agent` + **一轮有界重规划**

触发条件用 §2 的现成信号（`gap` / `status∈{empty,error}`），**只补一轮**，不循环。

| 项 | 值 |
|---|---|
| 改动量 | 中 —— `run_deep_agent` 加一个重规划分支（LangGraph 官方 plan-and-execute 教程有现成 `replan` 节点范式）+ trace 记录 + 测试；`rounds` 字段已在 `AgentTrace` 预留 |
| LLM 调用 | 正常 3；补一轮 5 |
| 触发率 | **待测**（门禁要回答的核心问题之一） |
| 适用边界 | 源的身份需要**看到中间结果才能定**（如"读完文件发现还要查这家企业的处罚"） |
| 失败的代价 | 中 —— 触发率过高会把 15.8s 变成 20s+，且挤压 rerank 瓶颈 |

### L3 — 完整迭代 ReAct / LLMCompiler 式 DAG

| 项 | 值 |
|---|---|
| 改动量 | 大 —— 要把 `deep_agent` 从**一次性函数**改成**带环的子图**（agent ↔ tools 循环）；好处是现有 checkpointer 可直接复用做多轮持久化，`knowledge_qa` 已有子图先例可抄 |
| LLM 调用 | ~2N + 1 |
| 适用边界 | 开放域、步数不可预判；**本项目当前无此证据** |
| 建议 | **暂不做**，等 L1/L2 的门禁数据说话 |

## 6. 为什么 L1 值得先试（不是拍脑袋）

1. **同形状问题已有先例**：Layer 1（确定性子句拆分并集，**零 LLM**）双段全中
   **0.6286**，**高于** deep_agent 的 **0.5143**，且后者 3× LLM、15.8s/题【实测，计划 §518】。
   ⇒ 本项目已验证过：**更贵的 agent 在这个领域不一定更好。**
2. **跨源组合机制已上线且零代码可复用**【实测·代码核对】：
   - 交接决策：`orchestration/routing_rules.yaml` 的 `handoff` 段，
     `price_inquiry → knowledge_qa` 已在生产（靠关键词，零 LLM）
   - 交接执行：每个 agent 节点都有边到 `handoff_decider`（`main_graph.py:242`），
     且 `pending_context` 会保存发起方的 `business_result`，
     由 `_compose_handoff_answer` 组合为**合并答案**（`:85-104`）
   - ⇒ 加一条 `from: doc_qa` 的 YAML 规则即可打通 → **改动量是"零代码"，
     不是"小改动"**。这比本文初稿的估计更省。
3. **「带文件就必读」是确定性信号** —— Phase G-6 已经把这条论证过：
   "要不要读文件"不需要语义理解，交给 LLM 判只会多一次调用与不确定性。
4. **30× 延迟差**（0.5s vs 15.8s）【实测】，而 L1 的形态与现有 `doc_qa` 同形。

---

## 7. 但也要认清 L1 的失效边界（别把它当万灵药）

L1 处理不了的，正是 **Phase G-5 认定"文本判据撞墙（天花板 ~73%）"的那一类**：

- 问题里**没有**明确说还要查别的源，但实际需要（"这份标书合规吗" → 可能要查企业处罚）
- 需要**多文件挑选**（会话里有 5 个文件，该读哪几个）
- 步数不确定（读完 A 才知要读 B）

⚠️ 但注意 Phase G-5 的修正：**这类场景的触发信号是"是否带文件"（确定性），
不是那个撞墙的文本判据。** 所以 L2 的价值不在于"猜得准"，而在于
**"猜到后能补"**（一轮重规划）。L2 的门禁要回答的就是：**补这一轮，命中率提升
是否值回触发率 × 3.8s 的代价。**

## 8. 门禁设计（**无论选哪档都要先做**）

**现有资产**：`scripts/run_deep_agent_eval.py`、`run_agent_trace_eval.py`、
`run_deep_agent_recall_eval.py`、`run_eval_gate.py`【实测·全部存在】
→ 评测基建不用新建。

**缺口**：`eval/agent_golden_set.json` 32 条**全是纯 KB 多跳**
（字段 `expected_sequence` 支持工具顺序断言），**零文件场景**【实测】。
⇒ 必须新建**「文件 + 跨模块」场景集**（Phase G-6 已要求："构造'文件 + 跨模块提问'场景集"）。
建议规模与构成：

| 类型 | 例 | 期望工具序列 |
|---|---|---|
| 纯文件 | "这份标书的投标保证金是多少" | `[read_file]` |
| 文件 + 法规 | "保证金比例是否符合招标投标法" | `[read_file, kb_search_tool]` |
| 文件 + 结构化 | "这份标书的采购人有没有不良记录" | `[read_file, price_query]` |
| 单源可解（**误入率用**） | "招标方式有哪些" | `[kb_search_tool]`（**不该读文件**） |

**指标**：命中率 / 误入率 / LLM 调用数 / 延迟 / **p95**。

⚠️ **p95 不能只看单题延迟**：多一次 kb_search 会挤压已饱和的 rerank（§3），
100 并发下的放大远大于单题 +1.3s。→ 门禁必须包含一次**并发压测**，
不能只跑离线单题集。

**我的建议：A → 用场景集测 → 若误入率/漏答率证明 L1 不够，再做 L2。**
理由：L1 便宜、可回退、与现有架构同形，且本项目已有"更贵的方案不一定更好"的实测先例（§6.1）。
**但这是你的产品决策** —— 如果你认为"源不确定"的场景是核心用户价值，
那 L2（甚至 L3）才是对的方向，L1 只是必经的第一步。

**不建议**：跳过场景集直接启用 deep_agent。理由见 §4.5、§5 L2 的失败代价 ——
线上表现瓶颈会从"答不准"变成"慢且不稳定"，且无法定位。
