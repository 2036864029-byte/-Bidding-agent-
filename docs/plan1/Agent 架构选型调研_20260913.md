## 0. 结论（先行）

> ⚠️ **2026-09-13 修订**：初稿把讨论范围窄化为「文件 + 1 个其他源」，
> 并据此推荐 L1。经用户指出真实场景（**一次提问同时涉及文件 + 双库**、
> **千字多子问**）后，结论**已修正** —— 见 §0.1 修订说明与 §9。
> 原推荐「L1 优先」**降级为可选低成本探针，不再是目标形态**。

### 0.1 修订说明（初稿错在哪）

| 初稿的判断 | 修订后 | 依据 |
|---|---|---|
| L1 是"零代码级"、建议先做 | **L1 只支持 2 源（1 跳）**；3 源会丢数据，不是零代码 | `main_graph.py:80` 每次交接**覆盖** `pending_context`（§5 L1） |
| L1 覆盖"文件 + 跨模块"这一大类 | 只覆盖"文件 + **1 个**其他源"；**文件 + 双库不覆盖** | 同上 |
| 长多子问没讨论 | **这是 L1 的真实短板**：KB 侧已有确定性拆分，但**"每个子问该去哪个源"没人管** | `kb_light_decompose` 只拆不路由（§7） |
| L2 的价值在"补一轮" | **L2 的价值主体是"一次排出多源计划"**；重规划只解决"中途才发现要查别的" | 现有 PLAN 已能排 3 步、SYNTHESIZE 已能合并多源（§5 L2） |

### 0.2 修订后的结论

1. **「多 Agent + 工具化」方向不受影响** —— 本文讨论的是**编排者是谁**
   （规则 vs LLM），不是**要不要多 Agent**。L1 也是多 Agent（capability 间交接），
   只是编排者是 YAML 表。用户既定的目标③「把项目优化为成熟的 AI Agent 项目」
   **本身就要求 LLM 自主选工具** —— 这一点 L1 满足不了（Phase G-1 实测：
   线上"LLM 自主选工具"**一次都没发生过**）。⇒ **若目标是定位/能力，L2 是目标
   本身的要求，不是可选项。**
2. **融合可行，且钩子已埋好**（§2）：`REFLECT` 已算出 `verdict=="gap"` 却被忽略，
   `StepRecord.status∈{ok,empty,error}` 也已在算 ⇒「要不要再来一轮」不需要 LLM 判断。
3. **但从场景覆盖看：L2（现有 deep_agent）比 L1 更合适**（§5）：
   - 「文件 + 双库」**今天就能工作** —— PLAN 一次排 3 步、SYNTHESIZE 合并多源，
     真机已验证（`read_file + kb_search` 自动组合）
   - L1 的 handoff **做不到** 3 源（覆盖 bug）
4. **无论选哪档，都必须先建「文件 + 跨模块」场景集门禁**（§8）：现有金标集
   `eval/agent_golden_set.json` 32 条**全是纯 KB 多跳，零文件场景**【实测】。

## 1. 概念厘清：四种形态与它们的融合点

| 形态 | 中途依赖（能否看到结果再决定下一步） | LLM 调用 | 并行性 |
|---|---|---|---|
| **ReAct** | ✅ 每步 thought→action→observation | ~2N + 1 | ❌ 串行 |
| **Plan-and-Solve**（ReWOO 同族） | ❌ 计划一次定死（ReWOO 用 `#E1` 变量引用前序结果，我们连这个都没有） | 1 计划 + 1 综合 | ✅ 可 |
| **Plan-and-Execute + Replanning** | ✅ 每步后可改计划 | 1 + N + N | 部分 |
| **LLMCompiler** | ✅ 计划器直接输出 **DAG**（显式标注依赖与可并行项），失败可重规划 | 1 + 重规划 | ✅ 最强 |
| **Reflexion** | ❌ 只在**跨轮**用语言化反馈重试 | 每轮 +1 | — |

**我们当前处在哪一档**（逐行核对 `agent/nodes/deep_agent.py`）：

```
PLAN(1 LLM, :149) → EXECUTE(0 LLM，所有步骤**并行**，_execute_steps:241 注释"步间无数据依赖")
  → SYNTHESIZE(1 LLM, :279) → REFLECT(1 LLM, :302)
rounds 硬编码 1；REFLECT 只改答案文字，不触发补检索/重规划
```

⇒ **我们是「ReWOO + Reflexion」的混合，且两条腿都不完整**：
ReWOO 那半缺变量引用（步骤间无法传递数据），Reflexion 那半缺"反馈→重试"的动作。
**「读到文件内容后再决定查哪条法规」现在做不到。**

## 2. 融合点：钩子已经埋好，只差接线【实测·代码核对】

两处**现成的确定性信号**，都不需要新增 LLM 判断：

```python
# ① _reflect (:289) —— 三种 verdict，只有一种被用
if verdict == "revised" and revised_answer: final = revised_answer
# 「gap」（观察不足以回答）被解析、存进 trace、然后被忽略

# ② _execute_step (:203) —— 工具自己已经在报告成败
StepRecord(status ∈ {"ok", "empty", "error"}, records_count, latency_ms)
```

⇒ **「要不要再来一轮」是工具已经回答过的问题**，不需要 LLM 再判一次。
把 `gap` / `status in {empty,error}` 接到一次补检索上，是**几十行改动**（§5 的 L2）。

## 3. ⭐ 系统特有成本结构（决定选型的关键，非通用结论）【实测】

通用文章会说"多轮 agent 贵在 LLM"。**在我们系统里这句话是错的。** 两种检索的代价
差一个数量级，且瓶颈位置完全不同：

| 检索手段 | 链路 | 实测延迟 | 是否吃 GPU 瓶颈 |
|---|---|---|---|
| **`read_file`** | in-process：稠密余弦 + BM25 + RRF(k=60)，**无 cross-encoder** | **47ms**（热）/ 390ms（冷建索引） | ❌ **不吃** |
| **`kb_search`** | Milvus 混合 → **bge-reranker-v2-m3 精排** | **1313ms** | ✅ **就是瓶颈** |

瓶颈证据【实测】：rerank 占 kb 检索耗时 **~89%**（embedding 仅 ~8%），服务端吞吐
**~10.4 次/s 饱和**（并发 1/10/50 同值，34 条长候选 96ms/次）；
100 并发 `/chat` p50 8.36s；50 并发下缓存命中与否差 **6.7 倍**（3.9s vs 26.4s）。

**⇒ 迭代的代价是不对称的：反复读文件便宜，反复查法规贵。**
一个 agent 循环里多查两次 KB，挤压的是**已经饱和**的 rerank，不只是多两次 LLM。

| 每多一步的边际成本 | LLM | 工具 | 合计 | 对 GPU 瓶颈的挤压 |
|---|---|---|---|---|
| 读文件步 | ~2.5s | 0.05~0.4s | **~2.6s** | 可忽略（1 次 query embedding） |
| 查法规步 | ~2.5s | ~1.3s | **~3.8s** | **+1 次 rerank（瓶颈上）** |

> 基准：单次 LLM 调用（DeepSeek）100 并发 p50 2.46s【实测】；`deep_agent` 全跑
> 3 次 LLM 实测 **15.8s/题**，单节点 `doc_qa` 约 **0.5s** → **≈30×**【实测，见计划 §518】。

### 3.1 追问：reranker 已自建部署，为什么还是瓶颈？

**因为自建解决的是「网络 / 配额 / 计费」，不是「算力天花板」。** 两者是不同的问题。

实测证据（计划文档 Phase E 实测二/三）【实测】：

| 观测 | 数值 | 说明 |
|---|---|---|
| rerank 服务端吞吐 | 并发 1 → 9.1 次/s；10 → 10.5；50 → 10.4 | **吞吐不随并发增长 = 已饱和**，天花板 ≈ 10 次/s |
| 单次 rerank | 34 条长候选（≈228 token/条）→ ~96~110ms | 计算量在这里 |
| 服务侧 GPU | 现网 fp32 逐请求 **377 对/s**（10.9 请求/s），**GPU 82% 均值 / 95% 峰值** | 计算受限，不是等待受限 |
| 100 并发实测 | 120 次检索全部未命中 → **200 次 rerank ÷ 10 次/s ≈ 20s**，观测 20~25s | **与预测完全吻合** |

⇒ **瓶颈是 cross-encoder 对 34 条长文本做逐条重打分的算力**（L20 · fp32 · 单进程无动态批处理），
不是部署位置。加并发只是排队，不会提高吞吐。

**已实测的两个杠杆**：

| 杠杆 | 实测收益 | 现状 |
|---|---|---|
| **fp16**（一行配置 + 重部署） | **2.63×** → 979 对/s（28.8 请求/s），GPU 降到 64%；排序 34/34 一致、分数差 0.06% | **被列为触发式**（p95>8s 连续 3 天 或 缓存命中率<60%）—— 计划 §Phase E 标为"推荐先做"，只是等触发 |
| **缓存命中率** | 命中 p50 **3.9s** vs 全未命中 **26.4s**（**6.7×**） | 已上线；F-2 single-flight 防击穿仍缺（100 并发时全部同时未命中） |

⚠️ **但 fp16 不影响本调研的核心结论**：它降的是**检索**那部分，
而 `deep_agent` 的 15.8s 里 **LLM 占大头**（3 次调用）。fp16 能让多源方案更耐用，
但不会把 15.8s 变成 5s。**这笔账待实测拆解**（见 §9.3）。

✅ **顺带一个正向结论**：本文档推荐的 `read_file`（C1 交付）**走的是 in-process
余弦 + BM25 + RRF，完全不经过 cross-encoder** —— 也就是说**文件类问题已经绕开了
这个瓶颈**，迭代读文件不会加重它。这正是 §3 表格里"代价不对称"的根源。

大 / 多文件则"后台分块+索引、模型按需检索"。

### 4.4 RAG 技术谱系（都指向"别每次固定 top-k"）

| 技术 | 解决什么 | 代价 |
|---|---|---|
| [Adaptive-RAG](https://aclanthology.org/2024.naacl-long.389/)【已确认存在】 | 先判问题复杂度，再选"不检索 / 单步 / 多步" | 多一次分类调用 |
| Self-RAG【记忆·未核实】 | 用反思 token 决定要不要检索 | 多一次模型调用 |
| CRAG (Corrective RAG)【记忆·未核实】 | 评估器把结果分 Correct/Ambiguous/Incorrect 分别处理 | 多一次评估调用 |
| **IRCoT / Self-Ask**【记忆·未核实】 | **边推理边检索**（最贴近"中途依赖"） | 多 N 次检索 |

**社区代价共识**【记忆·未核实】：这一族（统称 agentic RAG）**都多付一轮模型调用，
简单问题不该走**。

### 4.5 成本经验值

## 5. 落到我们：阶梯式路径（按代价升序，**建议逐档验证而非直接跳**）

### L1 — 确定性多源流水线（**零规划 LLM**）← 建议先做这一档

**关键发现：这一档的骨架已经在生产里跑着了，加一条 YAML 规则就能通**【实测·代码核对】

`orchestration/main_graph.py` 的 handoff 机制是完整的：每个 agent 节点都有边指向
`handoff_decider`（`:242`），decider 按 `routing_rules.yaml` 匹配，命中则

```
:78-82  存 pending_context = 本 agent 的 business_result（文件那半的答案）
        注入子问题为新 HumanMessage → 条件边路由到目标 agent
:85-104 目标 agent 跑完 → 组合终态：_compose_handoff_answer(文件答案, 法规答案)
        → 合并后的 answer，两半都留在 data.handoff_context
```

⇒ **「文件 + 跨模块」的链路与合并，零代码即可打通** —— 只需在 YAML 加：

```yaml
handoff:
  - from: doc_qa
    to: knowledge_qa
    reason: 文件问答涉及法规/合规判断，需公共法规库佐证
    keywords: [合规, 符合, 依据, 法规, 规定, 违反, 是否合法, 法律, 条例, 第几条]
```

于是 L1 分两小步，**先做 1a 验证链路，再按质量决定要不要 1b**：

| | 做法 | 改动量 | LLM 调用 | 产出质量 |
|---|---|---|---|---|
| **L1a** | 只加上面那条 YAML 规则 | **零代码**（纯数据） | doc_qa 1 + knowledge_qa 1 = **2** | 两段答案**拼接**（`_compose_handoff_answer`），不是融合判断 |
| **L1b** | 把拼接换成**一次综合 LLM**（把两半一起给它，产出真正的合规判断） | 小（改 compose + 一次 LLM 调用） | 2（其中一次是综合） | 真正的跨源判断，如"80 万 = 估算价的 X% ＞ 2% 上限 → 不合规" |

| 项 | 值 |
|---|---|
| 检索 | 1 次 read_file（47ms）+ 1 次 kb_search（~1.3s） |
| 预估延迟 | L1a ~3s；L1b ~5.5s（vs deep_agent 15.8s）【推算，按 §3 边际成本】 |
| 失败的代价 | 低 —— 纯数据改动可秒回退；且与现有 `price→knowledge` 交接同形，机制已跑在生产 |
| 处理不了的 | 源的数量/身份**无法预先确定**的场景（见 §7） |

⚠️ **L1a 的局限要说清（三条，每条都有代码依据）**：

**① 组合是纯字符串拼接，不是综合**（`:62` 实测实现）：

```python
return f"{context_answer}\n\n【政策法规解释】\n{final_answer}"
```

用户拿到的是"文件说 X" / "法规说 Y"两段，**不是"X 违反 Y"的判断**；
且分隔标题 `【政策法规解释】` 是 `price→knowledge` 场景硬编码的，用在
`doc_qa→knowledge` 上语义不对。

**② 只支持 2 个源（1 跳）—— 这是硬限制**（`main_graph.py:80`）：

```python
if new_handoff is not None:
    return {"handoff": ..., "pending_context": business_result, ...}   # ← 每次交接都覆盖
...
context_answer = (state["pending_context"] or {}).get("answer", "")    # ← 只读一个
```

**第 2 次交接会把第 1 次的结果覆盖掉** ⇒ `doc_qa → knowledge_qa → price_inquiry`
三源链路最终只合到最后两个源的答案，**文件那半丢了**。
要做 3 源须把 `pending_context` 改成累积列表 + 补第二条 YAML 规则 —— **不是零代码**。

**③ 不解决"每个子问该去哪个源"**（见 §7）：千字多子问会被 L1 规则**整体**判给
一个 capability，其余子问只能靠该 capability 自己兜（KB 侧有 clause 拆分兜得住，
跨源没有）。

⇒ **结论：L1a 的适用面比初稿写的小得多。** 它的合理定位是
**"2 源场景的低成本探针"**（验链路 + 拿到真实数据），**不是目标形态**。

### L2 — **现有 `deep_agent`**（目标形态）→ 再按门禁决定是否加「一轮有界重规划」

⚠️ **先纠正一个我自己的误判**：L2 的价值主体**不是**"补一轮重规划"，而是
**"一次排出多源计划 + 合并多源"** —— 而这两件事**今天就已经能工作**：

| 能力 | 现状 | 证据 |
|---|---|---|
| 一次排出多源计划 | ✅ 已有 | 真机验证：问"保证金比例与评标委员会构成是否合规" → 规划器**自己**输出 `[read_file, kb_search_tool]`（§Phase G-8）。加第三源就是排第 3 步 |
| 合并多源为一份回答 | ✅ 已有 | `_synthesize` 把全部 `steps` 的观察喂给 LLM 出**一份**回答（区别于 L1 的字符串拼接） |
| 看到中间结果再改计划 | ❌ 缺 | `plan` 一次定死、步骤并行执行；`gap` 不触发补检索 |

⇒ **对「文件 + 双库」这种"一次提问涉及多个已知源"的场景，现有 deep_agent
已经够用，不需要重规划。** 重规划只解决另一类：**源的数量/身份在规划时不知道，
要看到中间结果才能定**（"读完文件才发现还得查这家企业的处罚"）。

| 项 | 值 |
|---|---|
| 改动量 | 启用现有节点（registry `enabled=False` → 配置项）+ 路由闸门；**重规划是可选增量** |
| LLM 调用 | 3（PLAN + SYNTHESIZE + REFLECT，`reflect=False` 则 2）；加一轮重规划 → 5 |
| 延迟 | 实测 **15.8s/题**（vs 单节点 0.5s）；补一轮约 +4~8s【推算】 |
| 触发率 | **已有实测实例**：49 条里 1 条（2%）确实需要"换 query 再读一次"（§8.4）—— 是否值回 +2 次 LLM 仍待定 |
| 失败代价 | 中 —— 常态延迟 15.8s 起；若触发率高会到 20s+，且每次 kb 步挤压 rerank 瓶颈 |

> Phase G-8 记录的**反思 JSON 解析脆弱点**（`Expecting ',' delimiter`）须在启用前修掉，
> 否则门禁数据混入"答案没被审校"的噪声。

### L3 — 完整迭代 ReAct / LLMCompiler 式 DAG

| 项 | 值 |
|---|---|
| 改动量 | 大 —— 要把 `deep_agent` 从**一次性函数**改成**带环的子图**（agent ↔ tools 循环）；好处是现有 checkpointer 可直接复用做多轮持久化，`knowledge_qa` 已有子图先例可抄 |
| LLM 调用 | ~2N + 1 |
| 适用边界 | 开放域、步数不可预判；**本项目当前无此证据** |
| 建议 | **暂不做**，等 L1/L2 的门禁数据说话 |

## 7. L1 的失效边界（修订：这里是 L1 最大的问题）

### 7.1 千字多子问 —— L1 处理不了的核心场景

用户提的场景：**一段 1000 字的问题里含多个子问，且子问分属不同源**
（"这份标书里 X 是怎么规定的？按规定这种做法合规吗？顺便查一下这家公司有没有不良记录"）。

现状拆解：

| 环节 | KB 侧 | 跨源 |
|---|---|---|
| **拆子句** | ✅ 已有且有效：`kb_light_decompose` → `_split_clauses`（`tools.py:282`，6 行正则）→ 每子句各检一次（零 LLM，双段全中 **0.6286**【实测】） | ❌ **无** |
| **每个子问路由到哪个源** | 不需要（都在同一个库） | ❌ **无任何机制** |

而 L1 的父级路由（`classify_rules`）是**整体**判定：命中第一条规则就把**整个问题**
交给**一个** capability，其余子问只能靠该 capability 自己兜。
⇒ **"文件 + 双库"的多子问，L1 结构性做不到。** 这是 plannner 真正挣工资的地方。

> ⚠️ **不要直接套用 E5 的 73% 天花板**：E5 量的是"纯文本多跳**该不该拆**"，
> 与"每个子问**该去哪个源**"是**不同的判断**，是否同样撞墙**未实测**。
> 可以做的确定性替代是"逐子句按规则路由"（子句已能拆、规则已存在），
> 但**未验证**，属待测假设。

### 7.2 其他 L1 边界

- 问题里**没明说**还要查别的源，但实际需要（"这份标书合规吗" → 可能要查企业处罚）
- 需要**多文件挑选**（会话里有 5 个文件，该读哪几个）
- 步数不确定（读完 A 才知要读 B）

⚠️ Phase G-5 的修正仍然成立：**这类场景的"是否带文件"是确定性信号**，
所以 L2 的规划器**不需要猜"要不要读文件"**（那是确定性的），只需决定
**"除文件外还要不要查别的、查哪个"** —— 判断空间比 E5 量过的小得多。

## 8. 门禁设计（**无论选哪档都要先做**）→ ✅ 已建，且已跑出基线

**已建**（`3c4f6ac` / `0c4116b`）：`eval/file_golden_set.json` **49 条** +
`eval/fixtures/` **4 份合成标书**（智慧园区 / 医疗设备 / 道路工程 / 运维服务，
4 个不同领域）。金标由「**我造文档 → 答案自带**」得来，**造题人工成本为 0**；
harness 走生产节点（`evals/runners/agent_trace.py` 的文件模式）。
人工只剩一件：确认"问法像不像真实用户"（`review_status=draft`）。

### 8.1 基线（49 条，2026-09-13）

| 指标 | 值 |
|---|---|
工具选择 | P=0.99 R=0.99 **F1=0.989**，全覆盖 98% |
工具序列 有序覆盖 | **98%** |
答案命中 | **26/30 = 86.7%** |
误入率 | **0**（8 条 no_file_needed 全部正确走单源） |
耗时 | 3s/题（含多步与长问） |

分类：file_only **100%** · file_price **100%** · file_kb 83% · file_multi 80% · **multi_file 50%** ⚠️

### 8.2 测试集当场抓出的三个缺陷（这就是它的价值）

| # | 缺陷 | 状态 |
|---|---|---|
1 | **观察摘要把事实截在句中**（120 字/块 × 3 块 × 总 400）——read_file 的段落原文送不到 LLM | ✅ 已修（`0c436c5`）：按工具区分预算；答案命中 67~82% → 91.7% |
2 | **反思 JSON 稳定解析失败**（长散文塞进 JSON 字符串）→ 等于答案没被审校 | ✅ 已修（`0c436c5`）：改标记行 + 正文，解析失败归零 |
3 | **`read_file` 留空文件名时永远取"最近上传的那个"** → 多文件问题必然失败（连续两次调用拿回**同一份**文件） | ⏳ **待定方案**（见 §8.3） |

### 8.3 ⏳ 待定：多文件默认行为

实测原话（multi_file 只有 50% 的根因）：*"只返回了《道路工程》的工期条款，
**未返回《智慧园区》的任何工期信息**"* —— 两次 `read_file` 都拿回了同一份文件。

可选方案：
- **A**：`file_name` 留空 → 改为**在会话全部文件内检索**（chunk 带 `doc_name` 供 LLM 归属）。
  单文件时行为不变；多文件时正是"哪份文件说了X"这类问题需要的。
- **B**：PLAN_PROMPT 里明确要求多文件场景必须逐个传 `file_name`。
- **C**：两者都做（A 兜底 + B 提高一次命中率）。

**推荐 A**（工具默认行为应当对"会话里有几份文件"这件事自适应，不依赖规划器记得传参）。

### 8.4 ✅ 已获得"重规划"的实测实例

一条 file_kb 失败：问"投标保证金是否合规"，agent 读了文件拿到了保证金金额，
但合规判断还需要**项目预算**（在第一章）——而该事实**没被这次检索带回来**
（query 是保证金）。它需要**换一个 query 再读一次**。

⇒ 这就是 §5 L2 说的"中途才发现要查别的"的**首个实测实例**（1/49 ≈ 2%）。
**它把 L2 增量从"推测有价值"变成了"有据可查"** —— 但 2% 的触发率是否值回
+2 次 LLM 的代价，仍要按 §9.2 第 4 步用数据定。
