###  mineru在 48GB 单卡上怎么做

企业级项目绝不会让每一个 Web 接口进程都去加载一遍 PyTorch 模型，而是采用 **“单模型常驻显存 + 动态 Batch（批处理）+ 任务队列”** 的架构。

```
[前端/本地客户端]
       │ (HTTP 异步请求 complex 页面)
       ▼
[云端 Web API 层 (FastAPI / Gunicorn)] ──> 只负责接收请求，不加载 GPU 模型！
       │
       ▼ (投递任务)
[Redis / 内存异步队列]
       │
       ▼ (批量拉取 4~8 页)
[GPU 推理独占进程 (MinerU)] ──> 显存里只加载 1 份模型 (仅占 ~6GB)
       │                        └── 开启 Batch 推理 (Batch Size = 4 或 8)
       ▼
[处理完成并回调返回结果]
```

#### 关键提速手段：动态 Batching（批处理）

GPU 是矩阵并行计算的“怪兽”。

- **单页串行**：处理 1 张图片需要 1 秒，处理 8 张图片需要 **8 秒**。
- **Batch 处理**：把 8 张图片拼成一个矩阵 Batch 同时喂给 GPU，处理 8 张图片只需要 **1.2 ~ 1.5 秒**！

在 48GB 的大显存下，模型权重只占 6GB，剩下的 40GB 显存完全足够支撑 `Batch Size = 8` 甚至更高。**吞吐量能瞬间提升 4 到 5 倍**，且完全不会爆显存。

### 三、 你们开发说的“重新部署”到底指什么？

你的开发人员所说的“重新部署 `ztb-mineru-api`”，意思是**把这个服务从“朴素的单文件 API”改造成“标准 AI 推理微服务”**：

1. **剥离 Web 连接与 GPU 深度计算**：让 Web 接口只负责接收页面并返回任务 ID，不再阻塞 HTTP 连接（解决 `/health` 心跳 5 秒超时无响应的问题）。
2. **构建独占的 GPU Worker**：只启动 **1 个** 专门与 GPU 交互的 Python 后台进程，在 48GB 显存中只加载 1 次 MinerU 模型。
3. **引入内部 Queue 和 Batch 逻辑**：GPU Worker 自动将排队的复杂页面打包成 Batch 送入 GPU 进行并行推理。

### 推荐落地推进方案

1. **本地代码无需修改**：你本地做好的页级拆分、PyMuPDF 规则过滤和路由逻辑完全保留，这部分写的非常对。
2. **推动云端 `ztb-mineru-api` 重构**：让负责云端部署的人员将该服务重构为 **FastAPI + Async Background Queue（或 Celery）** 架构，重点是在 MinerU 推理端加上 **Batch 批处理**。
