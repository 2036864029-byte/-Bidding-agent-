## 0. TL;DR

| 问题 | 结论 |
|---|---|
| 全项目几个工具？ | **4 个**，线上实际生效 **3 个**（第 4 个定义了没人挂） |
| 为什么引擎多工具少？ | **能力 ≠ 工具**。5 个能力是「被路由选中的流水线」，不是 agent 循环 |
| 改造要推翻架构吗？ | **不要**。ReAct 循环的实现在 `agent/tool_agent.py` 已写好且测过，缺的是"接起来" |
| 主要缺口 | ① 参数契约写死（`args_schema` 不生效）② 无 observation 回灌（不是循环） |
| 工程量 | Phase 1 **0.5 天** / Phase 2 **1.5~2 天** / Phase 3（可选）**3~5 天** |
| 影响面 | **爆炸半径小**：deep_agent 是窄入口（误入 3.8%），主链路 5 个能力**零影响** |
| 会返工吗？ | 评测层**零改动**（只读 `steps`）；前端**1 处必改**（头部"0 步规划"） |

**一句话**：这是一次**局部替换**，不是架构迁移。改动限定在 `agent/nodes/deep_agent.py` +
`agent/tool_agent.py` 两个文件内，主图、router、5 个业务能力、评测口径全部不动。

### 1.2 三个认知陷阱（导致高估工具数量）

**陷阱 1 — `CapabilitySpec.tools` 零消费。** 实测 grep：

```
spec.tools   → 0 处引用
model_slots  → 0 处引用（registry.py 自身声明除外）
```

`agent/registry.py:15` 的注释"声明用"是**字面意思**。`_seed_deep_agent()` 里的
`tools=["kb_search","price_query","read_file"]`（`registry.py:285`）**没有任何代码读它**，
纯粹是给人看的文档。**看 registry 会误以为工具已接线。**

**陷阱 2 — `route_*` 看起来像工具。** 见 §1.1 注。

**陷阱 3 — 定义了≠挂载了。** `parse_file_as_tool` 有完整实现与测试
（`test/ingestion/test_parse_tool.py`），但**从没有任何 agent 挂它**。

### 1.3 为什么"引擎多、工具少"：能力 ≠ 工具

| | 能力节点（当前主线） | 工具（Agent 范式） |
|---|---|---|
| 单位 | LangGraph 图的**节点** | LLM 在循环里调的**函数** |
| 谁决定 | router **只分类一次**，选中即整条流水线跑到底 | LLM **每轮**自己决定调哪个、传什么参数 |
| 能否回头 | 不能（单向） | 能（看 observation 再决定） |
| 数量 | 5 enabled + deep_agent（env 启用） | 4（线上 3） |

引擎多的原因：每个能力背后是一个**专用子系统**——
`knowledge_qa`→`public_kb` RAG、`price_inquiry`→`price_engine` 召回链、
`doc_qa`→文档解析链、`deep_agent`→3 工具的 Plan-and-Solve。

**项目主体是「Router + 专用流水线」，不是 Agent 架构。** 只有 `deep_agent` 是 agent 范式。

图共 3 个：`agent/graph.py`（单图）、`orchestration/main_graph.py`（supervisor 主图）、
外加 `agent/nodes/knowledge_qa/subgraph.py` 与 `agent/nodes/price_inquiry/subgraph.py`。

### 1.4 deep_agent 现状逐层拆解

| 环节 | 实现 | 行号 | 性质 |
|---|---|---|---|
| 工具清单 | `_default_tools()` 硬编码 3 个 | `deep_agent.py:488-494` | 白名单，写死 |
| PLAN | 工具名+描述**渲染成 prompt 文本** → LLM 输出**自定义 JSON 数组** → `_extract_json` 解析 + 字符串比对 | `deep_agent.py:150-181` | **文本协议，非原生 tool calling** |
| EXECUTE | `args = {"question": step.query}` + `_TOOL_DEFAULTS[tool]` | `deep_agent.py:292-293` | **参数契约写死** |
| 步骤关系 | `ThreadPoolExecutor` **并发**，步间无依赖 | `deep_agent.py:313-327` | **一次性计划，非循环** |
| SYNTHESIZE | 观察拼接 → 流式草稿 | `deep_agent.py:340-355` | 正常 |
| REFLECT | prompt + `VERDICT:/NOTES:` 标记行解析 | `deep_agent.py:361-421` | 文本协议，但**已是标准 Reflection** |

**两个真实缺口**：

1. **参数不可由 LLM 决定** —— `deep_agent.py:292` 只传 `question` + 一张硬编码默认表
   （`_TOOL_DEFAULTS`，`:106-110`）。任何工具的 `args_schema` 都不生效，
   加新工具/新参数就要改这两处代码。
2. **无 observation 回灌** —— 步骤**并发执行**且**不回到 LLM**，首轮空结果无法触发补检索。
   这是"不是循环"的实证。

**入口（窄）**：`deep_agent` 由 supervisor 的**确定性闸门**触发
（`orchestration/routing_rules.yaml:41-47` `agent_gate`：带文件 + 跨源关键词，
实测误入 3.8% / 命中 87%），**不走 L3 LLM 路由**。启用由 env
`CAPABILITY_ENABLED=deep_agent` 控制（`.env:95`）。

## 2. 差距分析（对照标准形态）

| 层次 | 标准做法 | 现状 | 是否本方案解决 |
|---|---|---|---|
| **调用形态** | native tool calling + 有界循环 + observation 回灌 | 文本 JSON 协议 + 并发无回灌 | ✅ Phase 1+2 |
| **工具契约** | `args_schema` 真实生效 | `_TOOL_DEFAULTS` 写死 | ✅ Phase 1 |
| **工具数量** | 覆盖业务能力面 | 4 个（线上 3） | ⭕ Phase 3（可选） |
| **对外集成** | MCP | 无 | ❌ 本阶段不做 |
| **对内可维护** | Skills（渐进式披露） | 无 | ❌ 本阶段不做 |

**为什么本阶段不做 MCP / Skills**（重申关键区分，避免走错方向）：

- **Skills 解决不了"调用不灵活"**。Skill = `SKILL.md` + 资源的**渐进式披露**包，
  解决"领域知识太多塞不进 prompt"与"可插拔可维护"。它**不改变调用机制**。
- **MCP 解决的是跨进程/跨系统集成**，触发条件是"有外部系统要对接"，
  当前不成立。
- 真正的瓶颈在**前两行**（参数契约 + 循环形态），成本也最低。

## 3. 目标形态与设计决策

### 3.1 目标形态：Plan-and-Execute + Reflection（推荐）

```
PLAN        LLM 拆解步骤，**每步带 args**（Phase 1 改造点）
              ↓
EXECUTE r1  并发执行本轮步骤（保留 S4 并发收益）
              ↓
REPLAN?     把本轮 observations 回灌 LLM → 决定是否补充步骤（Phase 2 改造点）
              ↓   （有界：max_exec_rounds=2）
EXECUTE r2  仅执行补充步骤
              ↓
SYNTHESIZE  观察拼接 → 流式草稿（保留）
              ↓
REFLECT     审校 → adequate / revised / gap（保留不动）
```

**为什么不是纯 ReAct（设计 A）**：纯 ReAct 是**顺序**循环，
会把当前 `_execute_steps` 的**并发收益丢掉**——3 步每步约 1s 时，
并发 ≈1s、顺序 ≈3s，是**可见的延迟回归**。deep_agent 的典型场景
（带文件 + 跨源）恰好是 2~4 步的组合检索，并发价值高。

> **设计 A（纯 ReAct）作为备选**：直接 `run_tool_agent()` 替换 PLAN+EXECUTE+SYNTHESIZE，
> 保留 `_reflect()`。改动更小（~200 行）、复用最多，代价是**丢并发**与**丢可解释计划**
> （前端"思考过程"面板会只剩执行列表）。若 Phase 2 实测发现回灌轮复杂度过高，
> 可退化为设计 A —— **两者共用 Phase 1 的产物，不会返工**。

### 3.2 trace 契约迁移（**本方案最关键的设计点**）

**现状契约**（`core/contracts/trace.py:24-64`）：

```
AgentTrace { plan: PlanStep[], steps: StepRecord[], reflection, rounds, mode }
PlanStep   { id, objective, tool, query, depends_on }
StepRecord { step_id, tool, query, status, observation_head, records_count, latency_ms, sources[] }
```

**关键发现 — 评测层对 `plan` 零依赖：**

`evals/metrics/agent_trace.py:26-63` 的 `tool_selection()` / `tool_sequence()`
**只读 `trace["steps"][].tool`**；`trace_summary()`（`:76`）的
`duplicate_calls` 用 `(tool, query)` 对。**全程不读 `plan`**。

→ **只要 `steps` 保持 `{tool, query, status, latency_ms}` 形状，评测口径零改动。**
这是本次改造风险最低的部分。

**迁移规则（全部为增量，不破坏既有字段）**：

| 变更 | 内容 | 兼容性 |
|---|---|---|
| `StepRecord` 新增 `args: Dict[str,Any]` | 记录 LLM 实际传入的参数 | 新增可选字段，旧消费方忽略 |
| `StepRecord` 新增 `round: int = 1` | 第几轮执行（r1/r2） | 同上 |
| `PlanStep` 新增 `args: Dict[str,Any]` | Phase 1：LLM 规划时给出的参数 | 同上 |
| `AgentTrace.mode` 新增取值 | `plan_execute_reflect`（保留旧值） | 前端 `mode: string`，不编译失败 |
| `plan` 保持列表语义 | **不清空**（保留可解释计划） | 前端面板不变 |

**`plan` 的真实消费方只有 2 处**（已实测 grep 全项目）：

| 消费方 | 位置 | 影响 |
|---|---|---|
| 前端面板 | `DeepAgent.tsx:54,61,65` | 面板正文已守卫；**头部未守卫**（§3.3） |
| 单元测试 | `test/agent/test_deep_agent.py` **7 处** | 见下方清单 |

**实测**：`evals/`、`scripts/`、`agent/`、`core/` 里**零处**读 `trace["plan"]`
或 `.plan` —— 再次确认评测层只认 `steps`。

**`test/agent/test_deep_agent.py` 中依赖 `plan` 的断言清单**（开工前需逐条确认）：

| 行 | 断言 | Phase 1 | Phase 2 |
|---|---|---|---|
| `:85` | `len(trace["plan"]) == 2` | ✅ 不变 | ✅ 不变（PLAN 保留） |
| `:86` | `[p["tool"] for p in plan] == [...]` | ✅ 不变 | ✅ 不变 |
| `:125` | `mode == "plan_and_solve"` | ✅ 不变 | ⚠️ **须改为新 mode** |
| `:136-138` | 解析失败降级单步（plan 长度/tool/query） | ✅ 不变 | ✅ 不变 |
| `:152-153` | 非法工具被过滤 | ✅ 不变 | ✅ 不变 |
| `:229` | `trace["plan"][0]["tool"] == "price_query"` | ✅ 不变 | ✅ 不变 |

→ **结论：Phase 1 对既有测试零破坏**（纯增量字段）；
Phase 2 只需改 `:125` 一处 mode 断言 + 补 REPLAN 新用例。

**`query` 字段继续填人类可读串**（如 `question=xxx top_k=5`），
**不要换成 dict** —— 前端 `DeepAgent.tsx:136` 直接渲染 `查询：{step.query}`，
换类型会静默显示 `[object Object]`（本项目已踩过同类坑）。

### 3.3 前端必改点（**仅 1 处**）

### Phase 1 — 参数契约（0.5 天，收益最直接）

**目标**：让 LLM 能决定工具参数，不再依赖硬编码的 `_TOOL_DEFAULTS`。

**改动文件：`agent/nodes/deep_agent.py`**

1. **`PlanStep` 加 `args`**（`core/contracts/trace.py:24-31`）
   新增 `args: Dict[str, Any] = Field(default_factory=dict, description="本步工具参数")`。

2. **`PLAN_PROMPT` 加 args 要求**（`deep_agent.py:52-67`）
   在 JSON 结构说明里加 `args`（可选对象），并**列出每个工具的可调参数**
   （由工具的 `args_schema` 动态生成，不要手写第二份清单）。

3. **`_plan_question()` 解析 args**（`deep_agent.py:150-181`）
   解析 `item.get("args")`，非法/非 dict → `{}`（不阻断）。

4. **`_execute_step()` 改用 LLM 给的 args**（`deep_agent.py:279-310`）
   ```python
   args = {"question": step.query}
   args.update(_TOOL_DEFAULTS.get(step.tool, {}))   # 降级为「兜底默认值」
   args.update(step.args or {})                      # LLM 显式参数优先
   ```
   `_TOOL_DEFAULTS` **保留**（作为 LLM 未指定时的安全默认），但不再是唯一来源。

5. **`StepRecord` 落 args**（`deep_agent.py:304-310`）
   `args=args`（剔除 `question` 以免与 `query` 重复），便于归因"参数是谁定的"。

**验收**：
- `python -m pytest test/agent/test_deep_agent.py -q` → EXIT=0（34 个用例须全绿）
- 手工验证：提一个带文件问题，检查 trace 中 `steps[].args` 非空且反映 LLM 选择
- 前端：确认"查询：..."仍为可读字符串（未变 `[object Object]`）

**回滚**：`PlanStep.args` 缺省 `{}`，行为等价于改造前 —— 删掉 3~4 行即可回退。

### Phase 2 — observation 回灌（Plan-and-Execute，1.5~2 天）

**目标**：把"一次性计划"变成"有界循环"——首轮空结果/缺口可触发补检索。

**改动文件：`agent/nodes/deep_agent.py`**

1. **新增 REPLAN 阶段**（新函数 `_replan(question, steps, llm, tools, ...)`）
   - 输入：原问题 + 已完成步骤的 observations（复用 `_observations_text()` `:330`）
   - 输出：**补充步骤列表**（复用 `_plan_question` 的解析逻辑，复用 `PlanStep`）
   - 判据：LLM 输出空数组 = 不再补检索（正常终止）
   - 复用 `bind_tools` 或 JSON 协议**均可**；建议沿用 JSON 协议以与 Phase 1 一致

2. **`run_deep_agent()` 主流程改为有界轮**（`deep_agent.py:427-482`）
   ```
   plan_all = _plan_question(...)
   executed = []
   for round_id in 1..max_exec_rounds:          # 新开关，默认 2
       batch = plan_all(第1轮) 或 _replan(...)   # 第2轮起由 REPLAN 产出
       if not batch: break
       executed += _execute_steps(batch, tool_map)   # 保留 S4 并发
   ```
   - **`max_exec_rounds` 默认 2**（一轮计划 + 至多一轮补充），受
     `Settings` 控制，便于回滚与压测
   - **每轮内部仍并发**（`_execute_steps` 不动）—— 保住 S4 收益

3. **`StepRecord.round` 落轮次**（配合 §3.2 契约）

4. **`AgentTrace.mode`** 置 `plan_execute_reflect`

5. **新增开关**（`core/config/settings.py`）
   `deep_agent_max_exec_rounds: int = 2`、`deep_agent_replan_enabled: bool = True`
   —— 关掉即退回 Phase 1 行为，**一行配置回滚**

**同步改动（必须，否则算没做完）**：

| 文件 | 改什么 |
|---|---|
| `frontend/src/components/chat/renderers/DeepAgent.tsx:53-56` | 补 `plan.length > 0` 守卫（§3.3） |
| `frontend/src/types/chat.ts:102-113` | `TraceStep` 加 `args?`/`round?`（可选字段） |
| `frontend/src/adapters/chatAdapter.ts:175-180` | 映射新增字段（宽容，缺省不报错） |
| `evals/metrics/agent_trace.py` | **零改动**（见 §3.2）— 但 `plan_steps` 口径需复核 |
| `test/agent/test_deep_agent.py` | 补 REPLAN 用例（补检索触发/不触发/上限/异常降级） |

**验收**：
- `python -m pytest test/agent/ -q` → EXIT=0
- `cd frontend && npx vitest run` → 全绿 + `npm run typecheck` EXIT=0
- **回归对比 Phase 0 基线**：工具选择覆盖**不下降**，平均延迟增幅 **≤30%**
  （回灌轮会多一次 LLM 调用，延迟上升是预期内的；超阈值则调 `max_exec_rounds`）
- 造一个"首轮必空"的用例，验证第二轮确实补检索

**回滚**：`DEEP_AGENT_REPLAN_ENABLED=false`（回 Phase 1）；

## 附录 C — 执行记录（2026-09-16 实际落地）

### C.1 与方案的偏离（**重要**）

| 项 | 方案原文 | 实际落地 | 原因 |
|---|---|---|---|
| 参数契约范围 | "LLM 可决定工具参数" | **白名单，仅 `read_file.file_name`** | 实测放开全部参数使引用覆盖率 0.948→0.894（**超出 ±3% 容错**）；LLM 有 8/16 次把 `summary` 改 False、9/16 次把 `top_k` 调 8 —— 这些是系统调优旋钮，交出去只增方差 |
| PLAN_PROMPT | 加参数清单块 | **只改一个短语**（"传入"→"放进该步的 args"） | 多行参数清单块同样扰动规划（plan 均值 1.92→1.84），压成一行也无改善 → 最终删去 |
| `_tool_params_lines()` | 动态生成参数清单进提示 | **已删除** | 白名单只剩 1 个参数后，它与提示词里那句话重复，纯占预算 |
| 测试 | 补 REPLAN 用例 | **48 个用例**（34 原有 + 9 Phase1 + 7 Phase2） | — |

### C.2 关键实现决定

1. **`_parse_steps()` 抽取**：PLAN 与 REPLAN 共用解析逻辑（工具名过滤 / args 清洗 / 步数封顶），
   `start_id` 参数保证补检索步骤的 `step_id` 接在已执行步骤之后（轨迹全局唯一，无撞号）。
2. **轮内仍并发**：`_execute_steps()` 保留 `ThreadPoolExecutor`，回灌只发生在轮与轮之间 ——
   保住 S4 的并行收益（这是选 Plan-and-Execute 而非纯 ReAct 的核心理由）。
3. **mode 双轨**：`budget > 1` 时用 `plan_execute[_reflect]`，`=1` 时保留旧值
   `plan_and_solve[_reflect]` —— 回滚到旧配置时 trace 语义不漂移。
4. **补检索失败一律返回空**：REPLAN 是**增益**而非必需，异常/解析失败按"观察已足够"处理，
   绝不阻断本轮。
