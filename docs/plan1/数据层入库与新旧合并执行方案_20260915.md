## Phase 1 — 建库 + 导入 11 张表（无设计风险，建议立刻做）

### 1.1 建库建表

```sql
CREATE DATABASE IF NOT EXISTS bidding DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_unicode_ci;
```
然后**按 `mysql_schema.sql` 从上到下执行**（文件已按外键依赖排序：`project` → `announcement` → 其余 9 张）。

### 1.2 ⚠️ 导入前必须先修 `reference_loader.py` 的路径

```python
BASE = Path(__file__).resolve().parent.parent   # = ztb_demo/
DELIVERY = BASE / "data" / "delivery"           # ← 指向 ztb_demo/data/delivery/
```
但实际 JSONL 在 **`ztb_demo/delivery_package/`**。**照现在这样跑会 11 个文件全部 `[skip] ... 不存在`，且退出码仍是 0**——静默失败，极易误判为"导完了"。

三种改法，任选：
- **(A) 推荐**：给脚本加 `--dir` 参数（默认仍是 `data/delivery`），导入时传 `--dir delivery_package`
- (B) 把 `delivery_package/` 整个拷/软链到 `data/delivery/`
- (C) 直接把 `DELIVERY` 改成 `BASE / "delivery_package"`

## Phase 2 — 新旧数据统一（⚠️ **需要你拍板**）

### 核心障碍

新 schema 是**公告中心**结构：`attachment` / `project_product_item` / `award` **全部外键挂在 `announcement_id`** 上。
而旧 `bid_project`（17,742 行，2018~2025）**根本没有公告**——它只有项目号、项目名、采购人、中标人、金额、日期、省市、类别。

所以旧数据**没法直接放进新 schema**：要塞进 `award` 就得先有 `announcement`。

### 三个选项

| | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A（推荐）** | 另建**统一宽表** `project_unified`，新旧各自 ETL 进去，按引擎的召回模式建索引 | 多一张表；需写 ETL + 增量重跑逻辑 | 低：不碰新 schema 的完整性，可随时重建 |
| B | 为 17,742 个旧项目**合成占位公告**（`announcement_type='LEGACY'`，正文 NULL），再挂 award | 造 17,742 条假公告，污染 `announcement` 语义与计数 | 中：审计/统计口径被稀释，"802 条公告"不再是真的 |
| C | 建 **VIEW**，把旧 `bid_project` 与新 `project`+`award` UNION 成统一形状 | 零物化、零风险 | **高（性能）**：VIEW 上无索引，而 price_engine 的重召回链（FULLTEXT/LIKE/逐词拆分）依赖索引，实测会拖垮 |

**推荐 A**：既不动新 schema 的公告中心完整性，又能给引擎可索引的统一读取面；统一宽表的字段取新旧并集（`project_no / project_name / region / category / purchaser / winning_bidder / winning_amount / winning_date / source`），`source` 列标记 `LEGACY` / `CCGP` 便于回溯与增量。

### 合并前后的已知数据问题（会直接影响功能）

| 问题 | 影响 | 建议 |
|---|---|---|
| 旧 `subject_matter`（标的物）**基本是错配噪声**（空调→"监控设备"、家具→"阀门"、物业→"水泥"） | **产品 Top 榜不能用它** | 走 `project_product_item`；但该表 `normalized_product_name` 1,270/1,489 个不同值 ≈ **没做归一**，且 Top 值全是 `货物名称`/`详见附件` 等**表头**。产品维度需先清洗 |
| 旧 `project_name` **10.6%（1,873 条）是整段公告正文** | 表格渲染成大段文字；会污染 Milvus embedding | ETL 时截断/剥离 |
| 新 `region_name` **161 个值未省级规范化**（含"省直辖县级行政区划"） | 看板地区热力图脏 | 统一宽表落库前做省级映射 |
| 旧省份只有 18 个，新数据覆盖更广 | 合并后地区分布会变 | 属预期，不是 bug |
| 旧 `company_info` 38,911 vs 新 `supplier` 1,058（仅 399 有信用代码） | 供应商模块覆盖率 | 按信用代码做新旧打通（Phase 2 的一部分） |

## 附：产品明细清洗（2026-09-15，已执行）

脚本：`scripts/clean_product_items.py` → 新表 **`bidding.project_product_clean`**。

### 关键发现：不是"脏"，是**原列只认了 2/3 的模板**

`project_product_item.product_name` 只读 `货物名称` / `服务名称`，但 `raw_row` 里实际有**三套公告模板**
（1,489 行 **100% 覆盖**）：

| 模板 | 产品名键 | 配套字段 | 命中行 |
|---|---|---|---|
| 货物表 | `货物名称` | 货物品牌 / 货物型号 / 货物数量 / 货物单价(元) | 424 |
| 服务表 | `服务名称` | 服务时间 / 服务标准 / 服务范围 | 305 |
| **标的表** | **`标的名称`** | 标项名称 / 品牌 / 规格型号 / 数量 / 单价(元) | **623** |

**那 623 行（41.8%）"没有名字"是假象**——名字在 `标的名称` 里。原列的
`normalized_product_name` 1489/1489 等于原文，是因为它根本没取到值。

### 清洗做了什么

1. **按模板正确取名字**（`标的名称` → `货物名称` → `服务名称` 优先序）
2. **丢弃占位串** 137 行（`货物名称`/`详见附件`/`服务名称`/`详见开标一览表` …）
3. **拆开一格多产品** 92 行：按 `[、;；]` 切；单价并列且数量对齐时按下标配对
   （如 `601990.00、326869.00、…` ↔ 7 个产品系统）
4. **结构化取出品牌 / 型号 / 数量 / 单价**（原先是一串拼接原文）

### 结果

```
源 1489 行 → 产品行 1632（拆出 92 个多产品格，丢弃 137 个占位行）
不同产品 1519
品牌覆盖 1265/1632 (77.5%)  型号 1264 (77.5%)  单价 1149 (70.4%)
频率: 出现≥2次 86 个 / ≥3次 27 个 / ≥5次 0 个
```

### ⚠️ 但"产品 Top 榜"仍然做不了（诚实的结论）

清洗修好了**正确性**，修不了**数据量**：1,632 行里 1,519 个不同产品，
**最高频次只有 3，且没有任何产品达到 5 次**。Top12 全部并列 3 次，
其中一半是同一个食堂配送项目里的蔬菜（南瓜/土豆/大白菜/大葱/小白菜/山药/油白菜/甜瓜/生姜）。

→ **建议**：看板的产品区**继续用静态占位**，或改成"产品出现次数（样本稀疏）"并如实标注，
不要做成看起来像排行榜、实际是随机并列的东西。要做出真榜单需要**更长时间窗**（当前仅 8 天）
或换用 `announcement.content_text` 重新抽取。

另有 40 个产品名 >35 字（2.6%），是**服务类**采购（服务名本身即项目名，如

## 3.5 看板调整：撤产品榜 + 上行业走势（2026-09-15）

### 产品榜撤掉

**根因不是"全是蔬菜"，是频率分布没有信号**：分布是「最高 3 次 / 27 个产品；
2 次 / 59 个；**1 次 / 1,433 个**（占 1,519 个不同产品的 94%）」。
我在 SQL 里写的是 `ORDER BY c DESC, product_name` —— 27 个并列 3 次时**按名称排**，
中文排序把「南/土/大/小/山/油/甜/生」排前面，于是吐出来正好是那批蔬菜。
**换个排序键就会是另外十个** —— 这不是"最热门产品"，是"并列时按拼音排"的确定性假象。
（顺带查到：蔬菜各 3 次来自**三个不同的食堂配送公告**各列一遍，`announcement_id` 互不相同，
不是重复数据。）

已撤：删 `ProductRank.tsx`、`product_rank` 字段、相关测试；端点不再返回该字段。

### 行业走势（交易类型 × 月）

|---|---|
