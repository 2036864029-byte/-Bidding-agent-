# 多跳召回问题解决方案（E5 之后 · 2026-09-10）

> 承接「评测与可观测性执行计划」§9 E5 决策点。本文档把「多跳问题（答案分布在 ≥2 块）
> 第二块进不了上下文」的问题，从数据与代码两个层面定位清楚，给出**分层、可执行、可回退**
> 的解决方案。所有改动点均标注当前代码 file:line。

---

## 0. 结论速览

- **问题**：多跳问题双段全中仅 0.3714（35 条多跳里只有 37% 两段都进 top-5）。
- **根因 1（窗口太窄）**：检索最终窗口被 `retrieval_top_k=5` 截断（`retriever.py:294`），
  rerank 窗口只有 5×2=10（`retriever.py:129-134`），而 fusion 候选是 30 组
  （`milvus_search.py:69`）——第二块排在 fusion 第 11 名后就永远进不了 rerank。
- **根因 2（判定不可行）**：「答案落几块」由语料切分决定，**不由问题文本决定**——
  multi 里 34% 单问号（看不出要拆），single 里 40% 双问号（看着要拆）。文本判定（原子性
  判据）上限 ~73%，路由挑「谁要多块」必输。
- **根因 3（分解贵）**：deep_agent 分解有效（complex_20 召回 0.35→0.70）但每次固定
  3 次 LLM、15.8s/题、MRR 降 8.6pp——不能全量。
- **方案**：三层叠加，由浅入深，独立推进：

| 层 | 内容 | LLM 成本 | 已验证 |
|---|---|---|---|
| **Layer 0** | 检索窗口放宽 `retrieval_top_k` 5→11 | 零 | ✅ 已落地：dev_100 实测复现双段全中 0.3714→0.4286、MRR 不降 |
| **Layer 1** | knowledge_qa 检索层「证据检查 + 按需补充检索」（路线 B 最小闭环） | 零~1 次/题 | ⚠️ 机制已被 deep_agent 证明有效，触发信号待实测选型 |
| **Layer 2** | deep_agent EXECUTE 并行化 + 成本闸门 | 仅确认多原子的问题 | ⚠️ 代码现状为顺序执行，并行化是真实优化点 |

**核心思想**：把「要不要多块/要不要拆」的决策从**文本预判**（必输）挪到**检索证据**
（可观测）。Layer 0 用「放宽窗口」让第二块有机会进来；Layer 1 用「第一轮证据不足就
按缺口方向补检」兜住窗口外的那部分；Layer 2 只服务真正拆得出的多原子问题，并把它跑快。

## 1. 问题定位（数据与代码事实）

### 1.1 检索窗口现状（为什么第二块进不来）

当前混合检索链路（`public_kb/retrieval/retriever.py`）：

1. dense 30 + sparse 30 → RRF 融合（`retriever.py:193-217`），服务端按 `parent_chunk_id`
   分组，`limit=hybrid_fusion_limit(30)` = **最多 30 个父块组**（`milvus_search.py:69`
   注释明确：分组后 limit 表示分组数）；
2. rerank 只精排 `_rerank_candidate_k()` = `retrieval_top_k × group_size` = **5×2=10**
   （`retriever.py:129-134`，`retriever.py:236`）；
3. 最终**截断到 `retrieval_top_k=5`**（`retriever.py:294`），同父去重后 = 5 个不同父块。

**结论**：fusion 的 30 个候选组里只有前 10 组能进 rerank、前 5 组能进最终上下文。
多跳问题的第二块若排在候选 11 名之后，**被窗口截掉，而不是检索不到**——这正是
「调大窗口就能拿到部分增益」的依据（已验证，见 §3）。

### 1.2 判定层为什么必输（文本与答案分布错位）

dev_100（65 single + 35 multi）问句结构实测：

| 类型 | 问号数分布 | 错位 |
|---|---|---|
| single_hop (65) | 0 问号 2 / **1 问号 35** / **2 问号 26** / 3 问号 2 | **40% 的 single 文本上是双问号** |
| multi_hop (35) | **1 问号 12** / 2 问号 14 / 3 问号 7 / 4 问号 2 | **34% 的 multi 文本上只有 1 个问号** |

实锤案例（dev_100 第一条 multi）：

> 「……该法人需要完成哪些步骤？请结合相关规则说明其时间要求和审批程序。」

金标两块：第十三条（1 个月内办理 = 时间要求）+ 第十六条（承继应申请并经审查批准 =
审批程序）。文本是单场景、单问号，「时间+审批」是**同一流程的构成要素**——判据
`registry.py:203-207` 明确写「同一流程的时间/条件/材料/后果不触发」，于是按设计判
single，漏掉。

反例（E5 记录）：「…享有哪些权利？同时…必须履行哪些义务？」双问号、答案同一块，
被判多原子 → 误入 deep_agent，白跑 3 次 LLM。

**这就是 E5 撞墙的完整图景**：multi 里 34% 文本给不出「要拆」的信号，single 里 40%
给了「要拆」的假信号。「问题的文本结构」与「答案落在几块」在 1/3 以上的样本上错位。
因此**任何基于问题文本的路由判据，天花板 ~73%，门禁（<5% 误入 / ≥80% 命中）不可达**。

### 1.3 分解机制有效但贵的量化

| 口径 | recall | 双段全中 | MRR | LLM/题 | 耗时/题 |
|---|---|---|---|---|---|
| 单查询 top-5（现状） | 0.6714 | 0.3714 | 0.8524 | ~1 | ~2s |
| 内部 `retrieval_top_k` 5→11 | 0.7000 | 0.4286 | 0.8524 | ~1 | ~2s |
| 确定性子句拆分并集 | 0.6571 | 0.4286 | **0.6406** | ~1 | ~3s |
| deep_agent 全链路 | **0.7429** | **0.5143** | 0.7660 | 3 | 15.8s |

（E5 对照 A/B/汇总，2026-09-10，dev_100 的 35 条多跳）
deep_agent 并集 44.6% 的块不在原问题 top-11 内——分解确实取到了新内容，不只是「同一
批块多取几个」。

```
用户问题
  │
  ▼
router（文本路由，只判「走哪个能力」，不再判「复杂度」）
  │
  ▼
knowledge_qa 子图（subgraph.py）
  ├─ retrieve：kb_search（Layer 0：窗口已放宽到 top-11）
  │      │
  │      ├─ [Layer 1] 轻量补检：切子句 → 每子句取 top-5 → 与基线并集
  │      │     （基线原序 + 新块按 score 追加；上限 20 块；开关 kb_light_decompose）
  │      ▼
  ├─ generate：LLM 生成（引用护栏 R1~R7）
  └─ guardrail / 终态

  └─ plan 步骤并发检索 → 并集 → SYNTHESIZE
```

## 3. Layer 0：检索窗口放宽（零 LLM 成本）— ✅ 已落地（2026-09-10）

### 3.1 改动点（实际 4 处）

| 位置 | 改动 | 说明 |
|---|---|---|
| `core/config/settings.py:351` | `retrieval_top_k: int = 5` → `11` | 核心配置改动 |
| `public_kb/tools.py:215` | `kb_search` 默认 `top_k: int = 8` → `11` | **落地时发现**：kb_search 是第二道闸，默认只透 8 块；不改则知识问答主链路（`subgraph.py:161` 无参调用）只吃到 8 块，窗口放宽打折扣 |
| `test/test_recall_optimization.py:259` | 断言 `retrieval_top_k == 5` → `11` | 同步 |
| `test/test_parent_assembly.py:140` | 断言 `_rerank_candidate_k() == 5` → `11` | 同步（:138 显式传参 5×2=10 不需改） |

连带自动生效（无需改码）：`_rerank_candidate_k()` 变 11×2=22（rerank 窗口 10→22，
`retriever.py:129-134`）；最终截断 5→11（`retriever.py:294`）；同父去重/分组逻辑不变
（仍是「11 个不同父块」）。

### 3.2 验证（dev_100 多跳 35 条，2026-09-10 实测，`scripts/diag_topk_recall.py`）

| 指标 | 内部 top5 | 内部 top11 | Δ |

| hit_rate | 0.9714 | 0.9714 | 0 |
| recall | 0.6714 | 0.7000 | +2.9pp |
| **双段全中** | 0.3714 | **0.4286** | **+5.7pp** |

复现 E5 对照 A 结论；全量 pytest 无回归（1014 passed / 9 skipped 基线）。

3. **引用护栏**：块数翻倍后 `citations_meta` 与 R1~R7 校验需回归

## 4. Layer 1：knowledge_qa 检索层「轻量补检」（路线 B 最小闭环）— ✅ S2 已实测（2026-09-10）

### 4.1 落点

`agent/nodes/knowledge_qa/subgraph.py` 的 `_retrieve_node`（subgraph.py:146-177）：
在 `kb_search(question)`（:161）之后插入「子句补检」，结果并集后进 `generate`。
这是知识问答的唯一实现（subgraph.py:1-5），改一处覆盖全部入口。

子图状态加一个子图独有键（同 `qa_retrieval` 边界，不污染 AgentState）：
`qa_extra_retrieval`（subgraph.py:107-130）。

### 4.2 S2 实测结论（dev_100 全量，`scripts/diag_layer1_signal.py`）

**① 信号 A/B 判别力不足，放弃「按需」判定**：

| 信号 | multi 触发 | single 触发（误伤） | 结论 |
|---|---|---|---|
| A 子句-区域散布 | 94.3%（33/35） | 80.0%（52/65） | 弱判别，不够 |
| B 父块 doc 多样性 | 100%（35/35） | 98.5%（64/65） | 无判别力，弃 |

根因：**检索跨文档召回是正常现象**（一个主题在多个文档有不同章节），区域多样性
≠「答案缺第二块」。B 实质恒真，A 的 80% 误伤使其失去「按需」意义。

**② 补检机制有效，且对 single 检索层完全无害**：

| 方案（multi 35 条，正文口径） | recall | 双段全中 | MRR |
|---|---|---|---|
| 基线 top-11 | 0.7000 | 0.4286 | 0.8524 |
| 纯放大 top-20 | 0.7000 | 0.4286 | 0.8524 |
| **A∨B 触发补检** | 0.8000 | **0.6286** | 0.8524 |

single（65 条）补检前后指标**一字不差**（hit 0.969 / recall 0.969 / mrr 0.895）——
补检是「基线原序 + 新块追加」，single 答案第一块即命中，追加不影响。

**③ 关键发现：纯放大 top-20 与 top-11 完全相同**——主查询第 12~20 块全是无关块，
多跳第二块**靠主查询放大永远捞不到，必须换查询**（子句/分解）。直接坐实路线 B 前提。

### 4.3 选型变更：统一轻量补检（无判别信号）— ✅ S3 已落地（2026-09-10）

因「补检对 single 检索无害 + 信号判别力差」，**放弃按需判定，改为对全部知识问答统一
做「基线 top-11 + 子句补检取并集」**（实现 `public_kb/tools.py::kb_search_expanded`）：

- **补检动作**：问题按标点切子句（≥8 字，平均 2.6 句）→ **每子句检索只取高分 top-5**
  （取全量 docs 会按子句顺序保留低相关度首遇版本被截断，S3 实测 5 题因此漏）→
  与基线 top-11 并集去重（**基线原序保持 + 新块按 score 全局降序追加**，MRR 不摊薄
  ——与 `diag_clause_split_recall` 无序并集 MRR 崩 0.6406 的本质区别）。
- **渲染上限**：`max_chunks=20`（**16 实测仅双段全中 0.4857，20 复现 0.6286**；
  实测平均 17.7 块）。上下文 10.4→17.7（+70%），生成侧由 S1 Ragas 把关。
- **开关**：`kb_light_decompose`（settings，默认关）；`subgraph._retrieve_node`
  按开关路由 `kb_search` / `kb_search_expanded`。
- **真实复现验证**（dev_100 multi 35 条，真实 Milvus）：recall **0.8000**、
  双段全中 **0.6286**、MRR **0.8524**——与 S2 实验一字不差；全量 **1020 passed**。

**与 deep_agent 的关系**：本方案是 deep_agent 分解的**零 LLM 廉价版**——子句拆解
代替 LLM 规划，基线原序保持解决 deep_agent 的 MRR 下降（0.7660→0.8524），适用全部
知识问答而非只多原子。

**风险（S1 必须验证）**：上下文 +60% 对生成侧的影响（稀释/引用护栏），由 E2-2 Ragas
把关；延迟 +2~3s/题（零 LLM，纯检索）。

**可选收紧（若生成侧不容忍 +60% 上下文）**：加「问题长度 ≥80 字」等**廉价前置条件**
降低触发面。注意与 E5「长度判据」的用途不同——此处只影响**延迟**（补检无害），
不漏 quality，只牺牲约 12% 的 multi 增益。

## 5. Layer 2：deep_agent EXECUTE 并行化 + 成本闸门

### 5.1 并行化（🚧 代码已实现，待端到端耗时验证）

`deep_agent.py::_execute_steps`（ThreadPoolExecutor，≤4 worker；轨迹按 `step_id` 排序
保持 `core/contracts/trace.py` 契约稳定）：

```python
def _execute_steps(plan, tool_map):
    with ThreadPoolExecutor(max_workers=min(max(1, len(plan)), 4)) as ex:
        records = list(ex.map(lambda st: _execute_step(st, tool_map), plan))
    return sorted(records, key=lambda r: r.step_id)
```

步间无数据依赖、工具调用 I/O 主导，故并发安全。收益：15.8s/题中的 EXECUTE 部分按步数
近似并行压缩（2.23 步平均 → 接近单步耗时）。**待办：端到端耗时实测（对比顺序执行）。**

### 5.2 触发收窄

deep_agent 不再靠文本判据路由（判据天花板 ~73%）；普通知识问答已由 Layer 1 的统一
轻量补检覆盖（零 LLM、MRR 不降），deep_agent 只保留给「确认重/多源」的问题（如
complex_20 类长复合题、需数据+法规组合），避免「白跑 3 次 LLM」的 6.8% 误入。

### 5.3 成本闸门（E5-4 顺延）

在 `run_deep_agent` 轨迹（`AgentTrace`）与 Langfuse 侧对齐度量：LLM 调用数 / token /
延迟，输出与单查询链路的成本对比报告。
