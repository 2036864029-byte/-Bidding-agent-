01

三条线各司其职

评测栈最容易犯的错是重复建设。三个组件各有边界，互不替代。

Langfuse
OTel span 树、trace 持久化查询、dataset 管理、score 仓库、judge 与 code evaluator 编排。
不提供 RAG / Agent 现成指标库
Ragas
RAG 生成层指标计算：faithfulness、answer_relevancy、context_precision、context_recall。
不做观测，不存结果——算完推 score 给 Langfuse
自研 trajectory
Agent 指标：工具选择、参数正确性、规划步数、轨迹效率。输入是已落地的 data.trace。
不重造 RAG 指标
02

关键决策：不需要独立环境

依赖试算实测 · uv pip install --dry-run

"Ragas 与主环境不能并存"是伪命题——三次试算证明冲突只是版本取舍，而且可解。

试算结果
langfuse 零降级，仅新增 10 个包（langfuse 4.15.1 + OTel SDK 1.44 + backoff）
ragas 解出 0.4.3，但降级 4 个：openai 3.9→3.3、jiter、rich、fsspec；引入 langchain-classic / instructor
ragas "openai>=3.9.0" 解出 ragas 0.3.1，openai / jiter / rich 降级全部消失——根因是 0.4.x 依赖 instructor 锁死 openai

采用方案 A：uv add --dev ragas "openai>=3.9.0"。 运行时 LLM 通路（DeepSeek 经 langchain-openai）零改动，970 测试基线不受影响；Ragas 标为 dev 依赖，生产 uv sync --no-dev 不携带。

03

五层指标

每个指标写明口径、计算方式、数据源与门禁类型。基线在 E1/E2 首次跑通后回填——无基线不设阈值。 确定性指标进硬门禁，LLM-judge 指标只做趋势，避免 judge 波动让 CI 抖动。

层指标口径数据源门禁
检索hit_rate@k top-k 是否命中任一金标块 ground_truth_chunk_ids vs data.sources 硬门禁
检索recall@k Σ命中金标数 / Σ金标总数 同上 硬门禁
检索multi_hop_recall@k 双金标块问题的双命中率（350 条子集） 同上 硬门禁
检索mrr 首个命中的排名倒数 同上 趋势
生成faithfulness 回答是否忠于检索上下文（无幻觉） Ragas + 智谱 judge 趋势
生成answer_relevancy 回答与问题相关度 Ragas（LLM + BGE-m3） 趋势
生成context_precision / recall 上下文精排质量 / 金标覆盖度 Ragas 趋势
引用R1–R7 通过率 引用溯源规则全通过 data.citation_validation 硬门禁
路由路由准确率 intent 与金标一致 router 金标集 硬门禁
轨迹tool_selection_acc steps[].tool 与金标工具序列一致 data.trace 硬门禁
轨迹task_success 终态答案正确 金标 / 人工抽样 硬门禁
轨迹plan_adequacy 复杂问题 ≥2 步、简单问题 ≤2 步 data.trace.plan 趋势
系统首 token P95 流式端点首帧延迟 Langfuse span 硬门禁
系统错误率 / 熔断率 异常与降级占比 Prometheus /metrics 硬门禁
系统token 成本 每请求 prompt / completion LLMCallback 趋势
04

阶段路线 E0 – E4

顺序不是随意的：底座 → 标尺 → 度量 → 门禁 → 闭环。前一阶段的准出是后一阶段的入口条件。

E0
底座2–3 天
  • 依赖 spike（必做）：先 uv add langfuse 跑全量测试与 live 冒烟，再加 --dev ragas "openai>=3.9.0" 复跑
  • Langfuse 自托管：官方 compose 六服务，MinIO 复用现有实例，数据用 named volume
  • OTel 埋点：用 @observe() 而非 LangChain callback，规避版本依赖；专项验证 SSE daemon 线程的上下文传播
  • 依赖隔离守卫：运行时包禁止 import eval/
准出　970 测试全绿 + live 冒烟 7/7；一条请求在 Langfuse 展开完整 span 树
E1
标尺3–5 天
  • RAG 金标集工程化：EvalSample schema + 分层抽样（65:35，先 100 条）固定种子并落盘
  • 切分 holdout（约 200 条，调 prompt / 阈值时不可见）
  • router / price 金标补齐至 ≥50 条
  • agent 金标初版：用 350 条 multi_hop 构造多源用例，人工标注 ≥30 条工具序列
准出　四套金标齐备、schema 统一、可复现、含 holdout
E2
度量1–2 周
  • 检索层先做：零 LLM、纯确定性，直接对 Milvus chunk_id 比对
  • Ragas 生成层：llm_factory 指向智谱 OpenAI 兼容端点，embedding 复用 BGE-m3，judge 结果缓存
  • Agent 轨迹指标：从 data.trace 直接算，确定性为主
  • 统一报告：双写 Langfuse score + 本地 JSONL，报告携带金标版本 / judge 模型 / 抽样种子 / git commit
准出　五层指标全部可产出，报告含完整元数据
E3
门禁2–3 天
  • 基线回填与阈值定稿（硬门禁按基线留 5–10% 余量）
  • golden marker + CI：需真实服务的用例手动 / 定时触发，unit or integration 进 PR 门禁
  • 指标不降判定：任一硬指标跌破即阻断合并
准出　人为造一次回归，CI 正确拦截
E4
闭环1 周
  • 线上 trace 采样回灌：低分 / 异常 trace → 人工标注 → 追加金标集
  • 轨迹评估：接 run_deep_agent_eval + data.trace，用 E1 的 agent 金标
  • Langfuse 看板：指标趋势 + 成本 + 延迟
  • 迁移云服务器：Langfuse 上 Linux 更省事，评测批处理离 Milvus / LLM 更近
准出　闭环跑通一轮，评测转为持续运营

06

风险登记

高 langchain-core 1.x 与 Ragas / Langfuse 集成不兼容
E0-1 spike 先验；Langfuse 用 @observe() 绕开 callback；Ragas 钉 openai 走 0.3.1
中 openai 降级影响 DeepSeek 通路
钉版本规避；970 测试 + live 冒烟兜底
中 judge 模型偏差 / 漂移
judge 用智谱、生成用 DeepSeek；人工校准 10–20 条；跨模型分数不比较
中 评测集过拟合
划 holdout，调优只看 dev 集
中 LLM-judge 成本超预算
分层抽样 + judge 结果缓存，先 100 条
中 SSE daemon 线程丢失 trace 上下文
E0-3 专项验证；必要时显式传递 trace_id
