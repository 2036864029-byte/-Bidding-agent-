## 1. 目标与边界

**评什么**
- **RAG 链路**：检索召回质量 → 生成忠实度 → 引用合规性，三层独立可归因。
- **Agent 整体**：路由准确性 → 工具选择与参数 → 轨迹合理性 → 端到端任务成功率。

**不评什么（边界）**
- PDF 解析 / 入库质量：已有独立门禁（`run_clean_text_metrics.py`、`test_layout_metrics_gate.py`），本计划不重复。
- UI / 前端：不涉及。

**三条线各司其职（不重复建设）**

| 线 | 职责 | 不做什么 |
|---|---|---|
| **Langfuse** | OTel span 树、trace 持久化查询、dataset 管理、**score 仓库**、judge / code evaluator 编排 | 不提供 RAG / Agent 现成指标库 |
| **Ragas** | RAG 生成层指标计算（faithfulness 等） | 不做观测、不存结果（算完推 score 给 Langfuse） |
| **自研 trajectory** | Agent 指标（输入 `data.trace`，确定性断言为主） | 不重造 RAG 指标 |

## 2. 架构与分层契约

```
                    ┌──────────────────────────────────────────┐
  用户问题 ──► AgentGraph(supervisor) ──► 节点 ──► LLM / 检索  │
                    └──────────────┬───────────────────────────┘
                                   │ OTel span（E0 接入）
                                   ▼
                         ┌──────────────────┐
                         │    Langfuse      │◄──── score 双写 ────┐
                         │ (自托管，6 服务) │                     │
                         └──────────────────┘                     │
                                   ▲                              │
  离线跑批 ────────────────────────┼──────────────────────────────┘
  ┌────────────────────────────────┴───────────────────────────────┐
  │ eval/  (离线评测包，运行时不得 import)                          │
  │  datasets → runners → metrics{retrieval, ragas, agent_trace}    │
  │                            → gates → report(JSONL + markdown)   │
  └────────────────────────────────────────────────────────────────┘
```

**硬约束（用测试守卫）**
1. **运行时不得 import `eval/`**（`core` / `agent` / `orchestration` / `api` / `price_engine` / `public_kb` 全部禁止）——新增守卫测试。
2. **`ragas` 为 dev 依赖**，生产 `uv sync --no-dev` 不携带。
3. **指标双写**：Langfuse score（在线看板）+ 本地 JSONL（离线可复现、可 git 归档）。
4. **确定性指标进硬门禁，LLM-judge 指标进趋势监控**——judge 有波动，不得让 CI 抖动。

## 3. 指标定义（工程化标准核心）

> 每个指标必须写明：**口径 / 计算方式 / 数据源 / 门禁类型**。基线值在 E1/E2 首次跑通后回填（**无基线不设阈值**）。

### 3.1 检索层（确定性，零 LLM 成本）

| 指标 | 口径 | 计算方式 | 数据源 | 门禁 |
|---|---|---|---|---|
| `hit_rate@k` | top-k 是否命中任一金标块 | 命中样本数 / 总样本数 | `ground_truth_chunk_ids` vs `data.sources` | **硬** |
| `recall@k` | 金标块覆盖率 | Σ命中金标数 / Σ金标总数 | 同上 | **硬** |
| `mrr` | 首个命中的排名倒数 | `mean(1/rank_first_hit)` | 同上 | 趋势 |
| `multi_hop_recall@k` | 双金标块问题的**双命中**率 | 两条金标都进 top-k 的比例 | 350 条 multi_hop 子集 | **硬** |

### 3.2 生成层（Ragas + 智谱 judge）

| 指标 | 口径 | 数据源 | 门禁 |
|---|---|---|---|
| `faithfulness` | 回答是否忠于检索上下文（无幻觉） | Ragas（LLM-judge） | 趋势 |
| `answer_relevancy` | 回答与问题相关度 | Ragas（LLM + embedding） | 趋势 |
| `context_precision` | 检索上下文精排质量 | Ragas（LLM） | 趋势 |
| `context_recall` | 金标答案覆盖度 | Ragas（LLM） | 趋势 |

**约定**：生成用 DeepSeek、judge 用**智谱 GLM**（避免自评偏差）；judge 模型与版本写入报告元数据；**跨 judge 模型的分数不可直接比较**。

### 3.3 引用层（确定性，已有能力）

| 指标 | 口径 | 数据源 | 门禁 |
|---|---|---|---|
| R1~R7 通过率 | 引用溯源规则全通过 | `data.citation_validation` | **硬** |
| 拒答正确率 | 无答案样本正确拒答 | 金标 `expect_refusal` 标记 | **硬** |

### 3.4 Agent 轨迹层（自研，输入 `data.trace`）

| 指标 | 口径 | 计算方式 | 门禁 |
|---|---|---|---|
| `tool_selection_acc` | 工具选择与金标一致 | `steps[].tool` vs 金标工具序列 | **硬** |
| `param_correctness` | 参数含关键实体 | 确定性匹配 + 可选 LLM-judge | 趋势 |
| `task_success` | 终态答案正确 | 金标 / 人工抽样 | **硬** |
| `plan_adequacy` | 复杂问题 ≥2 步、简单问题 ≤2 步 | `plan` 长度 vs `query_type` | 趋势 |
| `trajectory_efficiency` | 步数 / 耗时 / token | `data.trace` + 观测 | 趋势 |

### 3.5 系统层（观测）

| 指标 | 口径 | 数据源 | 门禁 |
|---|---|---|---|
| 首 token 延迟 P50/P95 | 流式端点 | Langfuse span / metrics | **硬**（< 2s） |
| 端到端延迟 P95 | 全链路 | 同上 | 趋势 |
| LLM token 成本 | 每请求 prompt/completion | `LLMCallback` | 趋势 |
| 错误率 / 召回熔断率 | 异常与降级占比 | Prometheus `/metrics` | **硬** |

## 5. 工程化标准

**目录结构（建议）**

```
eval/                          # 离线评测包（运行时禁止 import）
├── datasets/                  # 金标集 schema / 加载 / 分层抽样 / 版本号
├── metrics/                   # retrieval.py / ragas_metrics.py / agent_trace.py / system.py
├── runners/                   # rag_runner / agent_runner / router_runner
├── report/                    # 双写（Langfuse score + JSONL）+ markdown 报告
└── gates.py                   # 阈值与判定
```

**标准清单**

| 维度 | 标准 |
|---|---|
| 测试分层 | 新增 marker `eval`（需真实 LLM/Milvus）；沿用 `unit` / `integration` / `e2e` / `golden` |
| 可复现 | 抽样种子固定并落盘；金标集版本号；judge 模型+版本；报告携带 git commit |
| 成本控制 | 分层抽样（100~200 条起步）；judge 结果缓存；批量调用 |
| 版本管理 | 金标集进 git；评测产物 gitignore；报告归档到 `test_report/` |
| 数据隔离 | 生产 `uv sync --no-dev` 不带 ragas；运行时不得 import `eval/`（守卫测试） |
| 报告规范 | 每份报告必含：样本量 / 抽样方式 / 金标版本 / judge 模型 / 指标值 / 与基线差值 |

## 7. 风险登记

| 风险 | 等级 | 应对 |
|---|---|---|
| `langchain-core 1.x` 与 Ragas/Langfuse 集成不兼容 | 高 | **E0-1 spike 先验**；Langfuse 用 `@observe()` 绕开 LangChain callback；Ragas 钉 `openai>=3.9` 走 0.3.1 |
| `openai` 降级影响 DeepSeek 通路 | 中 | 钉 openai 版本规避；970 测试 + live 冒烟兜底 |
| judge 模型偏差 / 漂移 | 中 | judge 用智谱、生成用 DeepSeek；人工校准 10~20 条；分数跨模型不比较 |
| 评测集过拟合（调 prompt 时看到全量） | 中 | 划 holdout（E1-2），调优只看 dev 集 |
| LLM-judge 成本超预算 | 中 | 分层抽样 + 结果缓存 + 先 100 条 |
| Langfuse 自托管运维负担（6 容器） | 中 | MinIO 复用；named volume；必要时用官方 compose 保持可升级 |
| SSE daemon 线程丢失 trace 上下文 | 中 | E0-3 专项验证；必要时显式传递 trace_id |

## 附录 C：接入要点

**Ragas（0.3.1 路径）**
- 自定义 judge：`LangchainLLMWrapper(ChatOpenAI(model="glm-4-plus", base_url="https://open.bigmodel.cn/api/paas/v4/", api_key=...))`
- embedding：复用现有 BGE-m3（SiliconFlow），仅 `answer_relevancy` 需要
- 字段映射：`question → user_input`、`reference → reference`、检索结果 → `retrieved_contexts`、生成答案 → `response`
- **依赖约束（E0-1 实测）**：`langchain-community==0.3.31` + `pillow>=12.3.0` 是 ragas 能 import 的前提，写在 `[dependency-groups] dev`，升级 langchain-community 前必查

**Langfuse（自托管）**
- 部署文件：`deploy/langfuse/docker-compose.yml`（官方 compose 原样，6 服务）+ `.env.example`
- **偏离计划**：不复用 Milvus 的 MinIO，改用 Langfuse 自带 MinIO——避免 `docker compose down -v`
  连带清空 Langfuse blob；代价约 100MB 内存
- 端口（均已核实空闲）：web `3000`、worker `3030`（本机）、clickhouse `8123`/`9000`（本机）、
  minio `9090`/`9091`、redis `6379`（本机）、postgres `5432`（本机）
- 数据全部用 **named volume**（不用 bind mount，规避 WSL2 跨文件系统 I/O）
- `.env` 由 `LANGFUSE_INIT_*` 首次启动自动建组织/项目/用户并下发固定 API Key，免手工配置

**Langfuse**
- 自托管 6 服务；MinIO 复用现有实例（独立 bucket）
- 埋点优先 `@observe()` / OTel SDK，**不依赖 LangChain callback 版本**
- score 写入：Ragas 指标、自研轨迹指标、系统指标统一落 score，便于看板聚合

**智谱 judge**
- OpenAI 兼容端点 `https://open.bigmodel.cn/api/paas/v4/`
- 生成（DeepSeek）与 judge（智谱）分离，避免自评偏差
- 换 judge 后分数尺度变化，需人工校准
