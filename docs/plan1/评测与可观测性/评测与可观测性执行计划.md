## 1. 目标与边界

**评什么**
- **RAG 链路**：检索召回质量 → 生成忠实度 → 引用合规性，三层独立可归因。
- **Agent 整体**：路由准确性 → 工具选择与参数 → 轨迹合理性 → 端到端任务成功率。

**不评什么（边界）**
- PDF 解析 / 入库质量：已有独立门禁（`run_clean_text_metrics.py`、`test_layout_metrics_gate.py`），本计划不重复。
- UI / 前端：不涉及。

**三条线各司其职（不重复建设）**

| 线 | 职责 | 不做什么 |
|---|---|---|
| **Langfuse** | OTel span 树、trace 持久化查询、dataset 管理、**score 仓库**、judge / code evaluator 编排 | 不提供 RAG / Agent 现成指标库 |
| **Ragas** | RAG 生成层指标计算（faithfulness 等） | 不做观测、不存结果（算完推 score 给 Langfuse） |
| **自研 trajectory** | Agent 指标（输入 `data.trace`，确定性断言为主） | 不重造 RAG 指标 |

```

  用户问题 ──► AgentGraph(supervisor) ──► 节点 ──► LLM / 检索  │

                                   ▼

  ┌────────────────────────────────┴───────────────────────────────┐
  │ eval/  (离线评测包，运行时不得 import)                          │

  │                            → gates → report(JSONL + markdown)   │
```

**硬约束（用测试守卫）**
1. **运行时不得 import `eval/`**（`core` / `agent` / `orchestration` / `api` / `price_engine` / `public_kb` 全部禁止）——新增守卫测试。
2. **`ragas` 为 dev 依赖**，生产 `uv sync --no-dev` 不携带。
3. **指标双写**：Langfuse score（在线看板）+ 本地 JSONL（离线可复现、可 git 归档）。
4. **确定性指标进硬门禁，LLM-judge 指标进趋势监控**——judge 有波动，不得让 CI 抖动。

## 3. 指标定义（工程化标准核心）

> 每个指标必须写明：**口径 / 计算方式 / 数据源 / 门禁类型**。基线值在 E1/E2 首次跑通后回填（**无基线不设阈值**）。

### 3.1 检索层（确定性，零 LLM 成本）

| 指标 | 口径 | 计算方式 | 数据源 | 门禁 |
|---|---|---|---|---|
| `hit_rate@k` | top-k 是否命中任一金标块 | 命中样本数 / 总样本数 | `ground_truth_chunk_ids` vs `data.sources` | **硬** |
| `recall@k` | 金标块覆盖率 | Σ命中金标数 / Σ金标总数 | 同上 | **硬** |
| `mrr` | 首个命中的排名倒数 | `mean(1/rank_first_hit)` | 同上 | 趋势 |
| `multi_hop_recall@k` | 双金标块问题的**双命中**率 | 两条金标都进 top-k 的比例 | 350 条 multi_hop 子集 | **硬** |

### 3.2 生成层（Ragas + 智谱 judge）

| 指标 | 口径 | 数据源 | 门禁 |
|---|---|---|---|
| `faithfulness` | 回答是否忠于检索上下文（无幻觉） | Ragas（LLM-judge） | 趋势 |
| `answer_relevancy` | 回答与问题相关度 | Ragas（LLM + embedding） | 趋势 |
| `context_precision` | 检索上下文精排质量 | Ragas（LLM） | 趋势 |
| `context_recall` | 金标答案覆盖度 | Ragas（LLM） | 趋势 |

**约定**：生成用 DeepSeek、judge 用**智谱 GLM**（避免自评偏差）；judge 模型与版本写入报告元数据；**跨 judge 模型的分数不可直接比较**。

### 3.3 引用层（确定性，已有能力）

| 指标 | 口径 | 数据源 | 门禁 |
|---|---|---|---|
| R1~R7 通过率 | 引用溯源规则全通过 | `data.citation_validation` | **硬** |
| 拒答正确率 | 无答案样本正确拒答 | 金标 `expect_refusal` 标记 | **硬** |

### 3.4 Agent 轨迹层（自研，输入 `data.trace`）

| 指标 | 口径 | 计算方式 | 门禁 |
|---|---|---|---|
| `tool_selection_acc` | 工具选择与金标一致 | `steps[].tool` vs 金标工具序列 | **硬** |
| `param_correctness` | 参数含关键实体 | 确定性匹配 + 可选 LLM-judge | 趋势 |
| `task_success` | 终态答案正确 | 金标 / 人工抽样 | **硬** |
| `plan_adequacy` | 复杂问题 ≥2 步、简单问题 ≤2 步 | `plan` 长度 vs `query_type` | 趋势 |
| `trajectory_efficiency` | 步数 / 耗时 / token | `data.trace` + 观测 | 趋势 |

### 3.5 系统层（观测）

| 指标 | 口径 | 数据源 | 门禁 |
|---|---|---|---|
| 首 token 延迟 P50/P95 | 流式端点 | Langfuse span / metrics | **硬**（< 2s） |
| 端到端延迟 P95 | 全链路 | 同上 | 趋势 |
| LLM token 成本 | 每请求 prompt/completion | `LLMCallback` | 趋势 |
| 错误率 / 召回熔断率 | 异常与降级占比 | Prometheus `/metrics` | **硬** |

### E5：复杂问题路由（原子性判定）— 预估 3-5 天

> **来源**：E2-1 基线暴露「多跳双段全中 0.371」；四组实验（见 §9 多跳归因实验）定位到
> **单跳链路把长/复合问题当作单一查询向量**——长问题召回腰斩至 0.35，而**分解可翻倍至
> 0.70**。判定与执行职责分离，故修复点放在**路由层**而非 knowledge_qa（后者会造成跨域
> 功能耦合）。

| # | 任务 | 关键点 | 验收 |
|---|---|---|---|
| E5-1 | 原子性判据改写 | `agent/registry.py` 的 `_seed_deep_agent`：`route_desc` / `route_tool_doc` 改为「问题含**多个需分别查证**的子问题（多原子）」判据，补 2~3 条复合 `examples`。**不新增 LLM 调用**——复用 L3 同一提示词 | 判据文本定稿 |
| E5-2 | 路由准确率回归 | 用 **650 single_hop + 350 multi_hop**（`testset_1000_local.jsonl`）+ **20 complex**（`complex_20.jsonl`）量准确率；期望 single_hop→knowledge_qa、multi_hop/complex→deep_agent | single_hop 误入 deep_agent **< 5%**；multi_hop/complex 命中 **≥ 80%** |
| E5-3 | 端到端效果验证 | 路由打通后用 multi_hop/complex 子集跑 **deep_agent 全链路**（plan→execute→synthesize→reflect），对比 knowledge_qa 的段落召回与答案质量 | 段落召回显著优于单跳基线（参考分解实验 0.371→0.85 / 0.15→0.55） |
| E5-4 | 成本闸门与观测 | 记录两条链路 LLM 调用数 / token / 延迟；误入率高或成本超预期则退化为「L1 确定性预判（复合连词/多问号）+ L3」两级；Langfuse 看板加两链路对比 | 成本与延迟有数、可回退 |

**E5 准出**：原子性判定路由准确率达标 + 端到端召回提升有数 + 成本可观测可回退。

> **⚠️ 执行结果（2026-09-09/10，详见 §9 E5 记录）**：E5-1/E5-2/E5-3 已执行，
> **E5-2 门禁未达标**——single_hop 误入 6.77%、multi_hop 命中 65.43%、complex 命中 100%。
> 根因已定位：金标 single/multi 的实质是「答案落在 1 块还是 2 块」（语料切分决定），
> **问题文本不可分**（LLM 二分类上限整体准确率 ~73%）。故本阶段**停在决策点**：
> ① 接受实测值启用；② 表层规则换召回（拟合措辞，不推荐）；③ 分解下沉共享检索层 /
> 调大 `retrieval_top_k`（不依赖路由判定）。E5-4 待路线确定后执行。

**E5 风险**：
- 判定并入 L3 可能拉低原意图分类准确率 → E5-2 同时回归 33 条意图集；若拉低，改独立判定节点（+1 次 LLM）。
  **实测：36 条逐题零漂移**，此风险未发生。
- deep_agent 的 `synthesize` / `reflect` 对纯知识问答的增益**尚未验证**（目前只验证了 `plan` 的检索分解收益）→ E5-3 一并量。

## 5. 工程化标准

**目录结构（建议）**

```
eval/                          # 离线评测包（运行时禁止 import）
├── datasets/                  # 金标集 schema / 加载 / 分层抽样 / 版本号
├── metrics/                   # retrieval.py / ragas_metrics.py / agent_trace.py / system.py
├── runners/                   # rag_runner / agent_runner / router_runner
├── report/                    # 双写（Langfuse score + JSONL）+ markdown 报告
└── gates.py                   # 阈值与判定
```

**标准清单**

| 维度 | 标准 |
|---|---|
| 测试分层 | 新增 marker `eval`（需真实 LLM/Milvus）；沿用 `unit` / `integration` / `e2e` / `golden` |
| 可复现 | 抽样种子固定并落盘；金标集版本号；judge 模型+版本；报告携带 git commit |
| 成本控制 | 分层抽样（100~200 条起步）；judge 结果缓存；批量调用 |
| 版本管理 | 金标集进 git；评测产物 gitignore；报告归档到 `test_report/` |
| 数据隔离 | 生产 `uv sync --no-dev` 不带 ragas；运行时不得 import `eval/`（守卫测试） |
| 报告规范 | 每份报告必含：样本量 / 抽样方式 / 金标版本 / judge 模型 / 指标值 / 与基线差值 |

## 7. 风险登记

| 风险 | 等级 | 应对 |
|---|---|---|
| `langchain-core 1.x` 与 Ragas/Langfuse 集成不兼容 | 高 | **E0-1 spike 先验**；Langfuse 用 `@observe()` 绕开 LangChain callback；Ragas 钉 `openai>=3.9` 走 0.3.1 |

| **多跳知识题归属** | ❌ **10/10 全部路由到 knowledge_qa，零条进 deep_agent** |

**实验 4 · 分解机制有效性**（绕过路由，直接调 `deep_agent._plan_question` 拆子问题后
分别检索、取并集）：段落召回 **0.700 → 0.850（+15pp）**，4 题从 1/2 升到 2/2，0 题退化。

**结论（重要）**：**单纯启用 deep_agent 解决不了多跳**——deep_agent 的触发面是
「跨源（结构化数据 + 法规）」，而多跳知识题不在其路由范围内；但**查询分解这一机制
确实有效（+15pp）**。因此多跳的正确修复点是**把分解能力引入 knowledge_qa**（多查询
检索），或在路由层增加多跳识别，而不是把问题改道 deep_agent。

**方案定稿（2026-09-09）：采用「原子性判定」**——主控 agent 在路由时判断「问题是否包含
多个独立子问题（多原子）」，多原子 → `deep_agent`，单原子 → 既有能力。落地见 §4 E5。

| 备选方案 | 结论 |
|---|---|
| knowledge_qa 多查询检索 | **否**——把跨域的「查询理解」塞进单一能力，造成功能耦合：price_inquiry / doc_qa 拿不到、将来要复制一份 |
| 长度门禁（≥N 字 → deep_agent） | **否**——350 条多跳题最长仅 249 字，长度闸门抓不到它们 |
| **原子性判定（采用）** | 判定属**路由层**、执行属 **deep_agent**，职责不混；可并入 L3 同一提示词（**零额外 LLM 调用**）；不依赖字数；有 650/350 + 20 条现成标注可直接量准确率 |

### 复杂/长问题集与「复杂度触发」验证（2026-09-09）— 结论：单跳链路在长问题上崩了

**动机**：原金标最长 249 字、无 ≥300 字样本，而真实用户会出现 600 字级复合模糊提问；
且 deep_agent 的触发面写的是「跨源（数据+法规）」，多跳知识题零触发——触发维度应从
「跨源」改为「复杂度」。

**产物**：`DATA/eval_rag/complex_20.jsonl`（`scripts/build_complex_question_set.py`）
——以多跳金标的两段正文为种子，LLM 反推真实用户口吻的长复合问题，均长 **498 字**
（416~668），全部 `expected_route=deep_agent`，答案必然在库、召回可量化。

**实测对比**（同一批 20 条）：

| 指标 | dev_100（常规，中位 78 字） | **complex_20（均长 498 字）** |
|---|---|---|
| `hit_rate@5` | 0.96 | **0.55** |
| `recall@5` | 0.8074 | **0.35** |
| 双段全中 | 0.3714 | **3/20（15%）** |

**分解效果**（绕过路由，`_plan_question` 拆子问题后分别检索取并集）：

| | 单查询 | 分解后 |
|---|---|---|
| 段落召回 | 14/40 = **0.350** | 28/40 = **0.700** |
| 双段全中 | 3/20（15%） | **11/20（55%）** |

**结论**：长/复合问题下，单跳链路（整段问题作单一查询向量）召回**腰斩**；分解使其
**翻倍**。因此「复杂度」是比「跨源」正确的触发维度，且 deep_agent 的 `route_desc`
与成本闸门应据此重写（下一步）。
