## 4. 关键教训（本会话踩坑，写进代码注释的不再重复）

1. **lark-oapi 业务失败不抛异常，必须看响应码** —— `im.v1.message.reply()` 返回对象 `.code`，非 0 是业务拒绝（如卡片格式非法），不检查就"静默没回复"。已修：handler 现在打 `回复被飞书拒绝: code=... msg=...`。
2. **飞书消息 API 的 interactive 卡片用 v1 格式**（`{"config":{"wide_screen_mode":true},"elements":[...]}`），**schema 2.0 新格式会被静默拒收**（2026-09-23 实测）。markdown 元素 `**` 渲染加粗；引用用 `hr` + `div/lark_md` 分隔。
3. **飞书长连接在 ≠ 事件会来** —— 必须先在后台「事件与回调」订阅 `im.message.receive_v1`（长连接模式），否则连接建立但零事件。
4. **测试/配置不得依赖本机 `.env`** —— 09-22 已踩（FEISHU_FRONTEND_URL 读 .env 导致测试红）；本次又踩 `EMBEDDING_BASE_URL` 漂移到死隧道没人发现（"知识库中没有答案"隔了很久才定位）。**改 .env 后重启后端是铁律**。
5. **Windows 日志文件是 GBK 编码** —— 用 grep 盯通道日志时中文 pattern 匹配不上（本会话 Monitor 漏报），要用 ASCII pattern（`message_id=`、`code=`）。
6. **前端真实端口以 netstat 为准，但残留进程会骗人** —— 5199 是残留、5173 才是活的；改 FEISHU_FRONTEND_URL 前先确认哪个进程在跑。
