## 2. 执行计划

### Phase A — 让"上传→提问"真正生效（P0，建议先做）

> 目标：用户上传文件后提问，**系统一定用上那份文件**。

#### A1. `file_store` 搬到 Redis（修 B1，同时为 A3/A5 铺路）

**为什么必须**：现在多 worker 下上传功能随机失效；且 A3（自动附着）与 B5（临时文档索引）都需要跨进程可见。

**改法**：
- 复用现成的 `core/cache/redis_backend.py::RedisBackedCache`（**pickle + TTL + 连接管理已做好**，注释明说"缓存对象为检索结果（含 langchain Document）"）
- `api/file_store.py` 改为后端可切换：`FILE_STORE_BACKEND=memory|redis`（与 C4/C5 同一模式）
- 新增 `list_by_session(session_id)`：维护 `session → [file_id]` 索引（A3 需要）
- Redis 不可用时 fail-open 到 memory（本地开发便利）

**工作量**：小（约 100 行 + 测试）
**验收**：`API_WORKERS=2` 下，worker A 上传 → worker B 提问能取到文件

#### A2. 路由感知"本轮有文件"（修 B2）

**改法**：在 supervisor 路由**之前**判断本轮是否带 `file_ids`（或会话有附着文件）：
- 有 → **直接走 `doc_qa`**（作为 L0 前置规则，不参与 L1/L2 竞争）
- 理由：用户明确带了文件，是最强的意图信号，不该被关键词规则推翻

**工作量**：小（路由前置判断 + 测试）
**验收**：带 `file_ids` 问"政府采购工程建设项目…应适用什么法律？" → `intent=doc_qa`（现在错走 knowledge_qa）

#### A3. 会话文件自动附着（修 B3）

**改法**：`/chat` 在 `file_ids` 为空时，自动附着本会话**最近 N 个**已上传且未过期的文件（N 可配，建议 1~3）。
- 需要 A1 的 `list_by_session`
- 显式传 `file_ids` 时以客户端为准（向后兼容）

**待定产品问题**：一个会话传了多个文件，全附着吗？→ 建议默认最近 1 个 + 可配；或前端显式选择。

**工作量**：小
**验收**：上传后**不带** `file_ids` 直接提问 → 能答出文件内容

### Phase B — 容量扩展至 100 并发（P0，配置为主）

> 目标：100 并发提问 + 5~10 并发上传解析。

#### B1. C2：显式设置 anyio 线程池上限（修 B7）

```python
# api/server.py：在 lifespan 内（必须事件循环中执行）
import anyio
anyio.to_thread.current_default_thread_limiter().total_tokens = settings.chat_thread_limit
```
新增 `Settings.chat_thread_limit`（默认建议 128）。
**为什么必须**：闸门一旦调到 >40，线程池（默认 40）就会先卡住。

**工作量**：**5 行 + 1 个配置**

#### B2. 调整限流/池配置（修 B6、B10）

| 配置 | 当前 | 建议 | 依据 |
|---|---|---|---|
| `MAX_INFLIGHT_REQUESTS` | 32 | **128** | DeepSeek 2500 并发，本机不该卡在 32 |
| `chat_thread_limit` | （新） | **128** | ≥ 闸门，避免线程池先卡 |
| `QUERY_POOL_MAX_WORKERS` | 8 | **32** | price 分支 |
| `SQL_POOL_MAX_WORKERS` | 8 | **32** | 与 query 池对齐 |

> ⚠️ 保守起步：先设 128 压测，观察 DeepSeek 实际响应与延迟，再按需上调。

**工作量**：**纯配置**

#### B3. 解析进程池扩容（修 B8）

```bash
CPU_POOL_WORKERS=8        # 当前 2
```
服务器 16 核，8 个解析进程无压力。
**工作量**：**纯配置**
**验收**：5~10 个并发上传（电子版 PDF）→ 都在合理时间内完成，不长时间排队

#### B4. 保护 MinerU：限制 Tier C 并发（修 B9）

**问题**：扫描件/复杂页走 Tier C → 远程 MinerU 每次 `subprocess` 重载 GPU 模型。8 并发会爆显存。

**改法（小）**：给 Tier C 调用加一个**独立信号量**（如 `MINERU_MAX_CONCURRENCY=2`），超出排队。
- 电子版 PDF 走 Tier A（本地）→ 不受此限 ✓
- 扫描件排队但**不崩** ✓

**工作量**：小（复现 `core/concurrency/limits.py` 的模式）
**验收**：并发 8 个扫描件上传 → MinerU 侧串行/小并发执行，无显存溢出、无失败

#### B5. 100 并发压测验证

用 `scripts/load_test_chat.py`（已就绪）：
```bash
python scripts/load_test_chat.py --concurrency 100 --total 300 --clients 300
```
**验收**：无 5xx 雪崩；503 为 0 或极少；p95 在可接受范围。

**注意**：会真实消耗 DeepSeek 配额（300 次请求）。

### Phase C — 长文档问答质量（P0，架构改进）

> 目标：100 页招标文件提问，问前段/后段/中间都能答准。

#### C1. `doc_qa` 改「检索模式」（修 B4/B5）

**这是本次最核心的架构改进。**

**现状**：全文塞入 + 16000 字符硬截断 → 截断 + lost-in-the-middle。

**改法（选项乙，复用度最高）**：
```
上传 → 解析 → 清洗 → 分块（chunk_markdown，已存在）
     → 向量化（get_embeddings，已指向自建服务）
     → 存入 Redis 临时文档索引（RedisBackedCache，已存在；key=会话+文件，TTL 1h）
提问 → 在该文档的 chunks 内检索（余弦 + BM25）
     → top-K 块喂给 LLM（几千字符，恒定）→ 带引用作答
```

**复用**：`chunk_markdown` ✓ / `get_embeddings` ✓ / `RedisBackedCache`（pickle+TTL）✓ / RRF 融合逻辑可参照 `core/retrieval`
**新增**：存/取 + 一次小规模检索（百页 ≈ 200 块，毫秒级）
**基础设施**：**零新增**（Redis 已在跑）

**收益**：① 不再截断 ② 中部内容靠检索命中，不受 lost-in-the-middle 影响 ③ 成本/延迟恒定
**工作量**：中（约 300~400 行 + 测试）

#### C2. 兜底：超限时明确告知

即便做了 C1，仍应有兜底：文件超大或检索命中不足时，明确告知"已依据文档中 N 个相关段落作答"而非默默答错。

**工作量**：小
