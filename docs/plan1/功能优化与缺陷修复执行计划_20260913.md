## 2. 执行计划

### Phase A — 让"上传→提问"真正生效（P0，建议先做）

> 目标：用户上传文件后提问，**系统一定用上那份文件**。

#### A1. `file_store` 搬到 Redis（修 B1，同时为 A3/A5 铺路）

**为什么必须**：现在多 worker 下上传功能随机失效；且 A3（自动附着）与 B5（临时文档索引）都需要跨进程可见。

**改法**：
- 复用现成的 `core/cache/redis_backend.py::RedisBackedCache`（**pickle + TTL + 连接管理已做好**，注释明说"缓存对象为检索结果（含 langchain Document）"）
- `core/filestore.py`（`f13bbd2` 前为 `api/file_store.py`）改为后端可切换：`FILE_STORE_BACKEND=memory|redis`（与 C4/C5 同一模式）
- 新增 `list_by_session(session_id)`：维护 `session → [file_id]` 索引（A3 需要）
- Redis 不可用时 fail-open 到 memory（本地开发便利）

**工作量**：小（约 100 行 + 测试）
**验收**：`API_WORKERS=2` 下，worker A 上传 → worker B 提问能取到文件

#### A2. 路由感知"本轮有文件"（修 B2）

**改法**：在 supervisor 路由**之前**判断本轮是否带 `file_ids`（或会话有附着文件）：
- 有 → **直接走 `doc_qa`**（作为 L0 前置规则，不参与 L1/L2 竞争）
- 理由：用户明确带了文件，是最强的意图信号，不该被关键词规则推翻

**工作量**：小（路由前置判断 + 测试）
**验收**：带 `file_ids` 问"政府采购工程建设项目…应适用什么法律？" → `intent=doc_qa`（现在错走 knowledge_qa）

#### A3. 会话文件自动附着（修 B3）

**改法**：`/chat` 在 `file_ids` 为空时，自动附着本会话**最近 N 个**已上传且未过期的文件（N 可配，建议 1~3）。
- 需要 A1 的 `list_by_session`
- 显式传 `file_ids` 时以客户端为准（向后兼容）

**待定产品问题**：一个会话传了多个文件，全附着吗？→ 建议默认最近 1 个 + 可配；或前端显式选择。

**工作量**：小
**验收**：上传后**不带** `file_ids` 直接提问 → 能答出文件内容

#### B1. C2：显式设置 anyio 线程池上限（修 B7）

**验收**：5~10 个并发上传（电子版 PDF）→ 都在合理时间内完成，不长时间排队

#### B4. 保护 MinerU：限制 Tier C 并发（修 B9）

**问题**：扫描件/复杂页走 Tier C → 远程 MinerU 每次 `subprocess` 重载 GPU 模型。8 并发会爆显存。

**改法（小）**：给 Tier C 调用加一个**独立信号量**（如 `MINERU_MAX_CONCURRENCY=2`），超出排队。
- 电子版 PDF 走 Tier A（本地）→ 不受此限 ✓
- 扫描件排队但**不崩** ✓

**工作量**：小（复现 `core/concurrency/limits.py` 的模式）
**验收**：并发 8 个扫描件上传 → MinerU 侧串行/小并发执行，无显存溢出、无失败

> **⚠️ 2026-09-13 实测结论：本项前提不成立，已并入 Phase E2。**
> ① 服务端 `uvicorn --workers 1` 且 handler 内 `subprocess.run` 是**阻塞调用写在
> `async def` 里** → 卡住事件循环 → **单进程天然串行**，不可能同时跑 8 份 magic-pdf
> （线上容器 PID 1 已确认）。② 客户端加信号量**无效** —— 解析跑在 CPU 进程池的
> 子进程里，进程内信号量限不住全局（每个子进程各持一把锁，最坏 8 子进程 × 2）。
> ③ 真正需要显式信号量的是**服务端**，且需先做常驻化（见 E2）。
> ④ 顺带发现并已修：解析期间 `/health` 不可达 → 客户端每次探测空等 5s
> （`MINERU_VERSION_MEMO_TTL`，见 E2）。

### Phase C — 长文档问答质量（P0，架构改进）✅ 2026-09-13 完成（`2539be4`）

> 目标：100 页招标文件提问，问前段/后段/中间都能答准。

#### C1. `doc_qa` 改「检索模式」（修 B4/B5）✅

**原现状**：全文塞入 + 16000 字符硬截断 → 截断 + lost-in-the-middle。

**落地实现**（选项乙，复用度最高）：

| 新增/改动 | 文件 | 说明 |
|---|---|---|
| 索引引擎（新） | `core/doc_index.py` | 分块 → 向量化 → 落**与会话文件同源**的存储（`file_store_backend`：memory\|redis，TTL 1h）；检索 = 稠密余弦 + BM25 → RRF(k=60) |
| 胶水层（新） | `agent/doc_context.py`（`f13bbd2` 前在 `api/`） | markdown → 索引 / 上下文渲染 + `read_file` 工具。**分层**：`core` 不得反向 import `public_kb`，且工具要被 agent 调用，故放在 agent 层（api → agent 是既有方向） |
| 上传建索引 | `api/server.py` | 同步 + 异步两条路径；异步必须**先于 done** 落库 |
| 节点解析 | `agent/nodes/doc_qa.py` | 解析块标记 → `data.sources`（对齐 knowledge_qa `{doc,chapter,chunk_index,content_snippet,score}`） |

**关键设计决策（与一处偏离原计划）**：

1. **BM25 不做倒排存储**：tf/df 用 `str.count` / `in` 在检索时现算（C 层扫描，60 块
   约 20~40ms）。原计划设想"存 tf"——实测算下来存 tf 字典会让 pickle 体积涨到
   十几 MB/blok，不划算。
2. **阈值只用于告知，不用于丢弃命中**：低于 `doc_index_min_score` 仍把 top-K 喂给
   LLM，只是**明确告知**相关度低。避免阈值误设导致"答不出来"（比"答得不够准"更糟）。
3. **零信号块补齐到 top_k**：上下文规模恒定，不因"只有一块匹配"而塌缩。
4. **小文档不走检索**（≤ `doc_index_full_context_max_chunks`=12 块）：全文本来就装得
   下，检索反而可能漏，且省一次向量化。
5. **fail-open 全链**：向量化失败 / 缓存不可用 / 检索异常 → 一律回退全文模式（旧行为），
   绝不让上传或提问失败。

**实测（2026-09-13，自建 bge-m3，60 块合成标书，关键事实只在文末第 55 章）**：

| | 上下文 | 延迟 | 结果 |
|---|---|---|---|
| 旧行为（全文截断） | 16000 字符 | 1.5s | ❌ "文档中没有任何..." |
| **C1（检索模式）** | **2450 字符** | **0.5s** | ✅ "捌拾万元整，依据：第55章 条款55" |

命中验证：问第 3 / 17 / 28 / 41 / 55 章均**命中正确章节**（前/中/后段），检索 110~130ms。

**阈值标定**（同一实测，`doc_index_min_score` 默认取 **0.45**）：

| 问题类型 | 最高余弦 | 0.45 判定 |
|---|---|---|
| 文档内（含同义改写） | 0.562 ~ 0.730 | 不告警 ✅ |
| 完全无关（天气/餐厅/编程） | 0.295 ~ 0.371 | 告警 ✅ |
| **域内但文档没有**（已知局限） | 0.484 ~ 0.571 | 与真问题重叠 → **分不开** |
| 寒暄（你好/谢谢） | 0.376 ~ 0.457 | 临界，不稳定 |

⚠️ **已知局限**：第 3 类（问的是本领域但文档里没有答案，如"投标文件递交截止时间"）
原理上分不出来——纯相似度判据无法区分"话题相关"与"答案在此"。缓解：块标记里的
分数一并进入 prompt，LLM 可自行判断。彻底解决需 reranker / LLM 复核（未做）。

**成本**：建索引 60 块 ≈ **3.7s**（自建 bge-m3，一次/上传）；同步上传端点因此多付
一次该成本（长文档应优先走 async 端点，索引在 done 前建好）。

#### C2. 兜底：超限时明确告知 ✅

三种情形显式入 `data.retrieval.notes` 并附加在回答末尾（同时走流式 sink，客户端累积
的 token 与终态 answer 一致）：

1. **命中相关度不足** → 「⚠️ 在《X》中未检索到与问题高度相关的段落（最高相关度 0.12），
   以下回答仅供参考。」
2. **全文模式被截断** → 「⚠️ 文档内容较长（共 N 字符），本次仅使用了前 M 字符，后文可能
   未纳入作答。」

### Phase E — 检索链路真实瓶颈（2026-09-13 实测修订）

> 目标：降低「100 并发提问」的延迟。**这一层与 Phase A~C 无关**，瓶颈在
> **rerank 吞吐**，不在应用。

#### 实测一：一次冷检索的耗时构成（顺序执行、客户端已热）

| 问题 | 总计 | embed | **rerank** | Milvus+父块拼装 |
|---|---|---|---|---|
| 招标方式有哪些？ | 0.36s | 0.11s（1 次） | **0.23s（1 次）** | 0.02s |
| 评标委员会成员人数有什么要求？ | 1.09s | 0.09s（2 次） | **0.97s（2 次）** | 0.03s |

**rerank 占检索耗时 ~89%，embedding 仅 ~8%。** 且每个 kb 问题会做 **2 次检索**
（基线 + 子句补检）→ **2 次 rerank**。

#### 实测二：rerank 服务端真实吞吐（34 条长候选，≈228 token/条）

| 并发 | 吞吐 | 均摊 |
|---|---|---|
| 1 | 9.1 次/s | 110ms |
| 10 | 10.5 次/s | 95ms |
| 50 | 10.4 次/s | 96ms |

**并发 1/10/50 吞吐相同 → 已饱和，天花板 ≈ 10 次/s。**

#### 实测三：100 并发下检索被拖垮（服务日志）

100 并发 / 100 请求时，**120 次检索全部走完整路径**（缓存未命中），单次
**20~25s**（顺序只要 0.36~1.09s）。

- 算得上：200 次 rerank ÷ 10 次/s ≈ **20s** —— 与日志完全吻合
- 缓存为何没兜住：100 个请求**同一瞬间**到达，全部同时未命中（无 single-flight
  防击穿），各自重算一遍；顺序/重复提问命中缓存时只要 **0.004s**

#### ❌ 已作废：原「E1 应用侧向量请求攒批」

原判断基于"每次模型调用约 20ms"的探测 —— 那个探测用的是 **20 条短文档**，
不代表真实负载（真实候选 34 条长文本，单次 rerank ~96ms）。
按实测重算：embedding 攒批只能省 **约 4%**（0.09s / 1.09s），
**不值得为此改动检索链**。原 E1 撤销。

#### ✅ 杠杆验证（2026-09-13 在 L20 容器内实测，非推算）

对「同样 16 个请求 × 34 条候选」做四组对照：

| 方案 | 吞吐 | 相对现网 | GPU 利用率 |
|---|---|---|---|
| **现网 fp32 逐请求** | 377 对/s（10.9 请求/s） | 1× | **82% 均值 / 95% 峰值** |
| fp32 + 攒批（4/16 个请求合并） | 389 / 388 对/s | **1.03×（无效）** | — |
| **fp16 逐请求** | **979 对/s（28.8 请求/s）** | **2.63×** | 64% 均值 |
| fp16 + 攒 16 个请求 | 1279 对/s（37.6 请求/s） | 3.4× | — |
| fp32 候选 17 条 | 378 对/s，**22.3 请求/s** | 请求数 2× | 87% |

**结论（三条，都推翻了先前的判断）**：

1. **攒批对 rerank 无效（1.03×）** —— fp32 下 GPU 已 82% 饱和，是**计算受限**，
   不是调用开销受限。（embedding 攒批有 12× 是因为那边每次只算 1 条短文本，开销占大头；
   rerank 每次本就带 34 条长候选，GPU 在真干活。）
2. **多开进程也无效** —— GPU 已饱和，多进程只会互相抢显存与算力。
   **原 E3（扩进程数）撤销。**
3. **✅ fp16 是真正的杠杆：2.63×，且是一行配置改动**，不需改架构。
   fp16 下 GPU 利用率降到 64%，说明还有余量 —— 此时再叠加攒批才有额外 1.29×
   （总 3.4×），但攒批要重构服务，性价比不高。

#### 修正后的执行项

| 编号 | 动作 | 收益 | 代价 |
|---|---|---|---|
| **E-1（推荐先做）** | `ztb-models` 用 **fp16** 加载 rerank（并同样处理 embedding） | **2.63×** | 一行改动 + 重部署共享服务；须验证排序结果与 fp32 一致 |
| E-2 | 降候选数（`hybrid_fusion_limit` 34→17） | 请求吞吐 2× | **召回/精排质量会降，须金标评测** |
| E-3 | 砍掉子句补检那次 rerank | 约 2× | 同上，且 S2/S3 曾测得明确召回收益 |
| ~~攒批 / 多进程~~ | 已实测无效，不做 | — | — |

**建议顺序**：**先做 E-1（fp16）**——收益最大、风险最小；E-2/E-3 属"拿质量换延迟"，
必须先用金标集跑出降幅再定。

### Phase F — 工程化差距登记（低于业界标准，**暂不改**，附触发条件）

> 2026-09-13 评估。这些**不是 bug**，是"离业界标准还差一截"的地方。
> **决策：不提前优化，但每条都写明触发条件** —— 达到条件再做，避免拍脑袋投入。

#### 决策依据：50 并发的延迟几乎完全由缓存命中率决定（实测）

| 50 并发场景 | p50 | p95 | 成功率 |
|---|---|---|---|
| **缓存命中**（常见 / 重复问题） | **3.9s** | 4.8s | 75/75 |
| **缓存未命中**（各问各的，全要现算） | **26.4s** | 40.9s | 75/75 |

同样并发，**差 6.7 倍**；两次都是零失败、零 5xx（**慢，但不崩**）。
→ 因此"要不要优化"取决于**真实流量形态**，不是一个拍板的并发数。
→ 判断方法：看线上**缓存命中率**（`/metrics` 命中计数 / Langfuse 检索耗时分布）。

#### F-1. GPU 推理服务形态（属**容量**，非缺陷）

| 现状 | 业界标准 |
|---|---|
| `ztb-models` 单进程、fp32、无动态批处理 | TEI / Triton 类推理服务：动态批处理 + fp16 |
| 实测 rerank 376 对/s（10.4 请求/s），GPU 利用率 82% | — |

**已实测的三条边界**（避免走弯路，勿重复尝试）：
- 攒批**无效（1.03×）** —— fp32 下 GPU 已 82% 饱和，是**计算受限**，不是调用开销受限
- **多开进程无效** —— GPU 已饱和，多进程只会互相抢显存与算力
- **fp16 有效（2.63×）** —— 实测排序 34/34 一致、分数最大差 0.06%；建议**只用于 rerank**，
  不动 embedding（查询向量要与已建索引比对，且 embedding 仅占检索耗时 8%）

**触发条件**：线上 p95 > 8s（连续 3 天）**或** 缓存命中率 < 60% → 执行 E-1（fp16）

#### F-2. 缓存无防击穿（single-flight）—— 唯一我认为算**缺陷**的一条

100 并发时服务日志显示 **120 次检索全部走完整路径**：同一瞬间到达的请求各自重算
（本该算 1 次、其余等结果）。典型 thundering herd，当前**无任何保护**。

**触发条件**：出现"热点问题"（同一问题短时间内被大量提问）**或** 命中率剧烈波动

**背景诉求**：所有工具应交由 agent 调用，否则工具只是形式。但**纯工具驱动**（上传后不解析、
提问时现场解析）会砸体验 —— 解析实测：**1 页 9.94s / 2 页 10.99s**（固定开销 ~8.9s/次）；
扫描件多层 PDF **推算** 60~70s（**该值为外推，非实测**）。

**决策：同一个工具，两个触发者**

```
上传时（系统触发，预热缓存）          提问时（agent 触发，自主调用）
        │                                      │
        └──────────►  read_file(file_id)  ◄────┘
                            │
                   ┌────────┴────────┐
                   ▼                 ▼
              索引命中→秒回     未命中→现场建索引
```

- **工具始终是唯一入口**：系统在上传时调它（预热），agent 在需要时调它（自主）
- **重活放在用户等待窗口内异步完成**：上传可异步（实测提交响应 0.12s），提问时秒回
- 属业界标准分工（RAG 的"离线入库 + 在线检索"、ChatGPT 文件的"上传后台解析 + 模型读取"）

**「一切交给 agent」的边界** —— 判断标准是 **"何时调用是否需要语义理解"**：

| 需要语义 → 交给 agent | 触发条件确定 → 走流水线 |
|---|---|
| 要不要查价格？要不要查法规？要不要读文件？ | 文件上传了 → 就该解析（无歧义） |

把"要不要解析"交给 LLM 决定，只会多一次 LLM 调用与不确定性，换不来智能；
但它**仍应是工具** —— agent 需要能**主动**读（多文件挑选、回看历史文件等）。

**触发用确定性信号**（不用已证撞墙的文本判据）：
`带文件` 且（`问题长度 > 阈值` 或 `子句数 ≥ 2` 或 `含结构化实体`）—— 全部可确定性计算。
**门禁**：构造"文件 + 跨模块提问"场景集，测命中率 / 误入率 / LLM 调用数 / 延迟。

#### G-8. `read_file` 工具落地（2026-09-13，`db79fea`）

**G-5 的两条前置阻断均已解除**：

| 阻断 | 解除方式 |
|---|---|
| ① 无任何读文件工具 | `agent/doc_context.read_file_as_tool()` 挂进 `deep_agent._default_tools()` |
| ② 只看 `messages[-1]`，看不到注入的文档上下文 | 节点把**文件名清单**（不含正文）补进问题，规划器据此才可能选 read_file |

**三处实现决策**（与 G-6 示意图的偏差及原因）：

1. **参数是 `file_name` 而不是 `file_id`**：agent 看到的是注入上下文里的 `[文件：名]`，
   拿不到 id。文件名在当前会话内可确定性解析；**多义即报错**（列候选让 LLM 用全名
   重试）——静默挑一个会让 agent 读到错误的文件却不自知。
2. **主参数固定为 `question`**：`_execute_step` 对所有工具统一注入 `question=step.query`
   （见 `deep_agent.py:217`），新工具必须遵守这个约定，否则一调用就 TypeError。
3. **返回 `chunks` 形状**（与 kb_search 同字段）：deep_agent 现成的
   `_summarize_result` / `_count_records` 直接可用，**执行器零改动**；
   若自创 `blocks` 字段，轨迹里 `records_count=0`、观察为空 → agent 会以为没查到。

**不现场建索引的分界**（重要）：
`render_for_record`（提问链路，`/chat` 请求路径）**只读**索引，避免 p50/p95 尖刺；
现场建只允许在工具里做——agent 路径本就慢，且那是索引缺失后**唯一的自愈机会**。

**真机验证**（自建 bge-m3 + 真 LLM，25 块标书，<u>上传时刻意不建索引</u>）：

| 提问 | 规划器选择 | 结果 |
|---|---|---|
| "这份标书要求的投标保证金金额是多少？" | `read_file` 单步 | 390ms（**含现场建索引**），答对并引用"第三章 投标保证金" |
| "保证金比例与评标委员会构成是否符合招标投标法？" | **`read_file` + `kb_search_tool` 两步** | read_file 47ms（走缓存命中）、kb_search 1313ms，产出逐项合规分析 |

第二问正是 G-6 设想的「文件 + 跨模块」场景，且**两条触发路径共用同一判定链**
（`_read_record`）——上传预热与 agent 自主调用不会分叉。

**顺带发现（留给第 3 项）**：真机跑出一处**既有**脆弱点 ——
`deep_agent 反思解析失败: Expecting ',' delimiter`（LLM 输出的审校 JSON 含未转义引号）。
当前**优雅降级**（采纳草稿，不影响答案），但意味着"答案没被审校"。
属 deep_agent 自身的健壮性问题，**非本条引入**；第 3 项启用前应处理
（`_extract_json` 加修复/重试，或让反思改用 tool-call 结构化输出）。
