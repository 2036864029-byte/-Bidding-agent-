## 🔴 现存问题（实证复现，优先级最高）

### #1 同一父块的兄弟子块重复召回，挤占 top-K（待用户定方向后修复）

**现象**：检索「什么是政府采购？」top-5 全部是《1200问》同一条长答案拆出的 5 个兄弟子块（chunk_idx 1/2/5/6/7，每块带相同前缀「问：什么是政府采购？」），dense/BM25/RRF/rerank 后依旧如此（分数 0.9955~0.9988）。

**为什么**：每个子块正文都以完整问题开头 → (a) BM25 对每个子块全命中；(b) bge-m3 向量被问题前缀主导、全高相似；(c) 双通道经 RRF 叠加抬升；(d) **bge-reranker 是逐条打分，不知道这 5 条是同源碎片、不扣冗余分**。所以"单条看它们就是最相似的"——打分正确，问题是它们是同一条答案的碎片。

**影响**：top-5 预算被单源碎片占满，多样性丢失（挤掉法律条文/其他书的不同角度），引用变 5 条同源。只在"长答案被 OversizeSplitter 拆成多个 child"的问题形态下出现（短答案/法条问题不受影响）。

**根因**：一期不落 parent 行（child 的 `parent_chunk_id` = `{doc_id}|sec_{start_index}` 合成标识），但**检索端完全不使用已入库的 `parent_chunk_id` / `chunk_type` / `sequence_in_parent`**（`retriever.py` rerank 后无 sibling 处理）。

**用户原设计意图**：子块不作为独立条目，命中时**拼回一整个父块再返回**（检索粒度=子块精细匹配，上下文粒度=父块完整）。此"拼回"步骤未实现。

**修复方案（用户 2026-09-08 待确认方向，未动手）**：
- **方案 A（最轻）**：rerank 后按 `parent_chunk_id` 去重，同父保留最高分子块，从融合候选补位其他父块凑 top-5。
- **方案 B（贴合原意，建议）**：检索命中同父多个子块时按 `sequence_in_parent` 排序拼接为一整块（前缀「问：xxx？」只留一次），以父块粒度进上下文、引用算一条；需控父块全文长度上限（bge-m3 8192 token 内）。**建议 A 兜底 + B 主**。
- **方案 C（MMR）**：候选选择加多样性惩罚，通用但实现重。

**涉及文件**：`public_kb/retrieval/retriever.py`（rerank 后处理）、可能 `public_kb/retrieval/entities.py`（拼接/引用元数据）、`core/contracts/`（引用上下文契约）。

## 🟡 潜在风险（代码层，当前数据未触发，重分块/新数据时才变现实）

### #2 [高] 表格原子块无超限保护
- `public_kb/ingestion/transforms/typed_chunker.py:388-394`：`split_table_blocks` 产出的 table 直接 `_make_atom`，不查长度不进 OversizeSplitter。
- 影响：超长表格（>2000 字符）被 `core/embeddings/bge_m3.py:41-44` `_SafeEmbeddings` 静默截断 → 向量只代表表格前段，dense 检索后半失准；>65535 字符时 `milvus_client._build_records` 不截断 text → insert 直接报错。
- 当前数据 0 表格块（content_type 全为 text），但后续 PDF 含大表会踩。
- 建议：table atom 超类型阈值按行组细分，或入库前校验 text 长度。

### #3 [中] chunk_uid 依赖位置敏感的 chunk_index
- `core/contracts/chunk_ids.py:61-78`：uid = md5(doc_name|chapter|chunk_index|md5(normalize(text))[:16])，含全局递增 chunk_index。
- 影响：分块阈值/算法版本/文件枚举顺序变化后重分块 → 同一文档全部 uid 漂移，判重失效、新旧两版并存（行数翻倍）。
- 建议：uid 剔除 chunk_index（doc_id + text hash 已够）；或 schema_version 变更时强制换集合。

### #4 [中] 5 个"结构化"字段实落动态字段，effective_date 过滤有风险
- `core/vectorstore/milvus_client.py:367-372` vs schema `:134-140`：chunk_type/parent_chunk_id/sequence_in_parent/effective_date/status 写在 record 顶层但 schema 未声明 → 全进 `$meta` 动态 JSON。
- 影响：(a) `build_effective_expr`（`core/contracts/contracts.py:199-206`）对动态 key 过滤，无标量索引且 `IS NULL` 语法对 JSON 子键依赖 Milvus 版本（需在 v2.6.23 实测）；(b) 二期按 chunk_type/parent_chunk_id 过滤将无索引。
- 建议：这 5 个字段升为显式声明，或明确动态过滤风险。

### #5 [中] langchain 兜底降级路径丢 effective_date 过滤
- `public_kb/retrieval/fallback.py:72-78`：`similarity_search_with_score` 不支持 filter，`expr` 静默丢弃。
- 影响：hybrid 异常降级时已施行法条过滤失效，未施行法规可能混入。低频路径。建议至少打日志声明过滤失效。

### #6 [低] defer-flush 崩溃窗口 + 幂等声明不完整
- `public_kb/ingestion/sinks/jsonl_ingest_runner.py:64-141` + `milvus_client.py:396-398`：`--defer-flush` 时进度文件逐批推进但 flush 最后统一做，Milvus 中途崩溃丢 growing segment 时重跑被进度跳过（chunk_uid 判重能救回未 flush 行，但"重跑被人工跳过"组合会丢）。
- 建议：文档明确 defer 模式恢复动作 = 删进度文件重跑，靠 uid 判重。

### #7 [低] 显式 VARCHAR 字段无截断保护
- `milvus_client.py:138-139`：chapter/hierarchy_path VARCHAR(512) 超长会直接 insert 失败整批报错。建议入库前校验/截断。

### #8 [低] `_extract_insert_count` 解析失败回退 len(data)
- `milvus_client.py:493-505`：服务端返回异常时按"全部成功"计，掩盖部分写入失败。建议改为告警日志。

### #9 [低] output_fields 回退时 chunk_uid 失真
- `public_kb/retrieval/entities.py:59-65` + `milvus_search.py:15`：回退字段列表 `["text","id","doc_name","chapter","chunk_index"]` 不含 chunk_uid，`entity_to_doc` 用兜底值重算 uid → 与入库 uid 不一致，下游按 uid 关联测评对不上。建议回退列表补 chunk_uid。

### #10~#14 [提示级]
- #10 `typed_chunker.py:435-440` vs `:248-254`：QA atom 正文含原始问题行（无"问："前缀）、child 统一加"问：{question}\n\n"，同文档两种格式，向量分布轻微不一致；`_extract_question`（`:142-149`）对非问题标题也返回标题文本，question 语义偏宽。
- #11 `typed_chunker.py:447-457`：QA 问题标题极长（>900）时 `budget=max(1,...)` 产出大量 1 字符子块仍带完整长前缀、实际超阈值（极端输入触发）。
- #12 `milvus_client.py:263-279`：`_batch_insert` 先全批次 embedding 再做判重查询——幂等重跑时已存在行也白耗 embedding API 费用；可先判重后 embedding。
- #13 `core/embeddings/__init__.py:27-38`：`get_embeddings(settings)` 单例忽略后续调用传入的不同 Settings（首调用者决定配置）。
- #14 `milvus_client.py:187-220`：`_validate_collection_contract` 不校验 7 个通用标量字段与 chunk_uid/doc_type 的 INVERTED 索引；旧 schema 集合下 chunk_uid 静默落动态字段、判重退化为无索引扫描。
