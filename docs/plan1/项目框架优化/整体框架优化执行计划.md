# 整体框架优化执行计划

> **依据**：对 `agent/`、`core/`、`price_engine/`、`public_kb/`、`api/`、`orchestration/` 全部核心代码的逐文件通读与交叉核对（不含任何既有计划文档的结论）。
> **原则**：先修缺陷 → 再收口 → 再补底座 → 最后叠功能。每一波独立可发布，任何一波的验收点都是可运行状态。
> **环境**：Python 3.11（uv 托管）+ `uv` 0.11.32；一律使用项目 `.venv`，禁用 conda / 系统 Python。

## 1. 审计结论：问题总表

> 每条均带代码证据。**严重度**：🔴 会直接导致错误结果或不可用；🟡 影响可靠性/可维护性；🟢 技术债。

### A. 并发与资源（🔴 优先修）

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| A1 | 线程池嵌套：子图把 `query_fn` 提交进 `_sql_executor`，`query_fn` 内部又把每条 SQL 提交进**同一个** 4-worker 池并阻塞等待 | `agent/nodes/price_inquiry/subgraph.py:373`；`price_engine/recall.py:152,172` | 并发 price 请求 ≥4 时 4 个 worker 全被外层占住 → 内层永不调度 → **全部超时返回空**（有效并发上限 ≈3） |
| A2 | SQL 超时后不取消 future，调用方 `finally` 把同一连接释放回池 | `price_engine/recall.py:176-181`；`recall.py:376,423` | 孤儿线程与新请求共用同一 pymysql 连接 → 协议错乱 / 串结果 |
| A3 | Reranker 的 `last_status`/`retry_count` 是实例属性，reranker 随检索单例进程级共享 | `public_kb/retrieval/reranker.py:56-57,104,108`；`public_kb/retrieval/retriever.py:238` | 并发下读到别的请求状态 → 静默走错降级分支、诊断失真 |
| A4 | 语义集合自举 check-then-set 无锁，重建第一步是 `drop_collection` | `price_engine/semantic.py:366-375,398-401,261-262` | 并发首请求可能启动两次重建，互删集合 |
| A5 | MySQL 池在持锁期间做网络 `ping()`；无上限；失效连接置 `None` 留永久空洞；`setdefault` 延长超时是空操作 | `core/rdb/mysql_pool.py:69-102,58-60,90-92` | 全部 DB 访问被一把锁串行化；池无限增长；超时配置与注释不符 |
| A6 | 多处无锁惰性单例（registry / node 存储 / 两个子图 / legacy RAG） | `agent/registry.py:178-190`；`agent/nodes/base.py:63-68`；`knowledge_qa/subgraph.py:260-268`；`price_inquiry/subgraph.py:714-722`；`knowledge_qa/legacy.py:21-33` | 并发首请求重复初始化（幂等但非原子），legacy 会重复建 MilvusClient |
| A7 | 上传端点是 `async def` 却同步执行解析 | `api/server.py:112,123` | 阻塞事件循环，期间所有请求停摆 |
| A8 | Milvus 写入去重"查了再写"非原子 + 判重失败按"未命中"继续 | `core/vectorstore/milvus_client.py:328-339,375-377` | 并发/多实例产生重复行，且静默 |

**分层契约（硬约束，用测试守卫）**

1. `core` → 不 import `agent` / `orchestration` / `price_engine` / `public_kb`。
2. `public_kb` / `price_engine` → 不 import `agent` / `orchestration`；对外只经 `tools.py`、`guardrails/`、`rendering/`。
3. `agent` → 不 import `orchestration`（`AgentGraph` 的模式分发移到 `api/deps.py` 或独立 `bootstrap.py`）。
4. `orchestration` → 只经 registry + `agent.nodes.*.subgraph` + 门面，不 import 引擎内部。
5. 每个域的**业务逻辑只有一份实现**（子图为准；引擎提供能力与可复用守卫函数）。

## 4. 分波执行计划

> 每项 = 一个 commit 粒度。**验收**栏未全部满足不得进入下一波。

### Wave 0：缺陷止血（预估 2-4 天，零架构改动）

| # | 任务 | 改法 | 验收 |
|---|---|---|---|
| W0-1 | 消除线程池嵌套（A1） | `core/concurrency/pools.py` 定义 `SQL_POOL`（供外层 query_fn）与 `SQL_INNER_POOL`（供单条 SQL），或在 `price_inquiry/subgraph.py:373` 改为调用线程直接执行 + 依赖每-SQL 超时 | 新增并发测试：4 个并发 price 请求全部正常返回（当前全空）；`pytest` 全绿 |
| W0-2 | SQL 超时不残留连接（A2） | `recall.py:172-181` 超时后 `future.cancel()`，并把该连接**标记为不可复用**（`_release_connection(conn, discard=True)`），池内移除 | 单测：模拟超时后该 conn 不再被复用；集成：连续超时后池无空洞 |
| W0-3 | Reranker 去状态化（A3） | `rerank()` 返回 `(results, status)` 或写入传入的 result 对象；`retriever.py:238` 改用返回值 | 单测：并发两次不同结果，互不影响 |
| W0-4 | 消除每请求 LLM 探测（C4） | `build_supervisor_node` 构造时构建一次 router 并缓存（`llm_router` 注入），`route_question` 不再每轮现建 | 单测：`route_question` 两次调用只触发 1 次探测 |
| W0-5 | fallback 不读陈旧状态（B5） | `fallback.py` 仅在**本轮** `_with_fallback` 写入时复用（用 `messages` 末条关联或新增 `business_result` 的轮次标记），否则一律返回引导语 | 单测：连续两轮（第一轮异常、第二轮 fallback）返回引导语而非旧错误文案 |
| W0-6 | 会话默认值（D） | `api/server.py:35-36`：无 `session_id` 时生成随机 id（或 400 要求传入）；`file_store` 读取时校验 `session_id` 归属 | 单测：两个无 session 的请求不共享历史 |
