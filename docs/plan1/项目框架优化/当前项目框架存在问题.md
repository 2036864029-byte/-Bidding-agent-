## 当前项目框架存在问题

### （一）架构设计缺陷：边界模糊与能力缺失（高优先级）

#### 1. 两层编排职责重叠，状态管理不统一

- 现状：`orchestration/` 顶层编排 + `agent/graph.py` 领域编排，两层都有图、状态、节点的概念，但没有明确的分层契约
- 风险：
  - 业务复杂后会出现编排逻辑冗余、重复开发
  - 会话状态、检查点、错误处理在两层各管一套，极易出现状态不一致
  - 新增业务时，开发人员无法判断逻辑该放在哪一层
- 企业级标准：必须明确分层契约 ——**原子能力节点 → 单 Agent（领域内流程编排）→ 多 Agent（跨领域协作与监督）**，每一层的生命周期、状态范围、错误处理边界清晰。

#### 2. 领域引擎与 Agent 节点耦合方式混乱

- 现状：`price_engine`、`public_kb` 自身是完整引擎，同时 `agent/nodes/` 下又有对应的 `subgraph.py` 做二次编排，出现「两套业务逻辑」
- 问题：领域逻辑同时存在下沉（引擎内）和上浮（Agent 节点内），后续迭代会出现逻辑分叉，维护成本指数级上升
- 最佳实践：领域引擎只暴露标准工具接口，Agent 层只做流程编排、意图路由、工具调度，不承载任何业务计算逻辑。

#### 3. 会话状态模型过于单薄，无法支撑企业级多轮对话

- 现状：`AgentState` 仅包含 `messages / router_intent / business_result` 三个字段
- 缺失企业级必备能力：
  - 会话元数据：租户 ID、用户 ID、会话 ID、渠道、时间戳
  - 对话状态机：澄清、确认、终止、超时等生命周期管理
  - 上下文窗口治理：长会话截断、压缩、摘要机制
  - 用户 / 会话级持久化策略：状态归档、合并、过期清理

#### 4. 缺乏统一故障模型与容错体系

- 现状：仅节点级有 fallback，没有全局错误处理框架
- 缺失：
  - 统一错误码体系（业务错误 / 系统错误分级）
  - 通用重试策略（指数退避、幂等控制）
  - 熔断降级机制（LLM 超时、向量库不可用、数据库故障的降级路径）
  - 全局异常处理器，保障错误口径一致、用户体验统一

### （二）基础设施缺口：生产级硬性指标不达标（中高优先级）

#### 1. 可观测性严重不足，无法支撑运维排障

这是企业级项目最核心的门槛，当前框架几乎空白：

- **日志**：无统一结构化日志格式，无请求 ID 全链路透传，无法串联一次请求的完整调用路径
- **指标**：仅 `metrics.py` 占位，缺失 LLM 调用指标（耗时、Token 消耗、成功率）、检索指标（召回率、召回条数、耗时）、Agent 指标（路由准确率、节点耗时、Fallback 触发率）
- **链路追踪**：未集成 OpenTelemetry，无法定位性能瓶颈与故障点
- 后果：线上出问题无法排查，效果劣化无法感知，完全不具备大规模运维能力。

#### 2. 安全与合规体系缺失，敏感业务场景风险极高

针对招投标、价格这类敏感业务，当前安全能力完全不足：

- **身份鉴权**：API 层无认证（API Key/OAuth2），无用户权限隔离
- **工具调用安全**：价格引擎存在 SQL 构造逻辑，无 SQL 注入防护与执行沙箱，风险极高；文件操作、系统调用无权限管控
- **数据安全**：无敏感数据脱敏、无内容审核分级、无数据驻留合规设计
- **审计合规**：无完整操作审计日志，无法追溯谁在何时调用了什么、输入输出是什么

#### 3. 配置管理与缓存体系缺失

- **配置**：仅支持静态 `.env` 文件，无动态配置、多环境配置隔离、配置版本与回滚能力，运行时调参必须重启服务
- **缓存**：完全没有缓存设计，包括语义缓存、LLM 结果缓存、检索结果缓存、热点数据缓存。企业场景下重复问题占比高，无缓存会导致成本高、延迟大，资源浪费严重。

### （三）工程化与可伸缩性隐患（中优先级）

#### 1. 测试体系不完整，质量保障不足

- 仅有效果评测金标集，缺失工程质量保障体系：
  - 无单元测试、集成测试、端到端测试目录结构
  - 无自动化测试流水线，无法保障代码变更的回归质量
  - 无压力测试、混沌测试，性能与稳定性无基线

#### 2. 无水平扩展与异步化设计

- 单体同步架构，所有逻辑在 HTTP 线程内完成，复杂 RAG/Agent 任务耗时久，极易打满 Worker 导致雪崩
- 无消息队列解耦，无任务排队与削峰填谷机制
- 各模块无法独立扩缩容（比如检索密集型、LLM 密集型无法分开扩容）

#### 3. 依赖与文档管理粗放

- 单 `requirements.txt` 未按模块 / 环境拆分依赖，生产镜像包含开发工具，体积大、攻击面大
- 文档体系不完善：缺少架构设计图、数据流说明、开发指南、运维手册，团队协作与交接成本高

### （四）长期演进能力缺口（低优先级）

- 无多租户隔离设计，无法支持多客户场景
- 无数据生命周期与版本管理，知识库更新全链路追踪能力弱
- 无工具调用事务补偿机制，多步骤操作失败无法回滚
- 无限流熔断与资源隔离，高并发下稳定性无保障

## 三、改进优先级建议

### P0（生产上线前必须完成）

1. 搭建**结构化日志 + 全链路追踪**体系，补齐可观测性基础
2. 建立**统一错误处理与容错框架**，明确错误分级、重试、熔断、降级规范
3. 补齐 API 鉴权与**工具调用安全沙箱**，尤其是 SQL 执行权限管控
4. 梳理编排分层边界，统一状态管理，消除两层编排的职责重叠

### P1

1. 引入**多级缓存体系**（语义缓存 + 检索缓存 + LLM 结果缓存）
2. 优化配置管理，支持多环境隔离与热加载
3. 搭建自动化测试体系，补充单元测试与集成测试
4. 核心路径异步化，引入消息队列解耦长耗时任务

### P2

1. 多租户架构改造，支持数据与配置隔离

2. 服务化拆分，支持各模块独立水平扩展

3. 建设动态配置中心与完整运维监控大盘

4. 完善数据治理与知识库全生命周期管理
