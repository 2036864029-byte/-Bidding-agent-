> 依据：2026-09-12 会话的代码实测审查（解析性能基准 + 并发模型审查 + 部署缺口盘点）。
> 目标：把「解析性能、并发容量、上云迁移」三件事排成一条**不返工**的执行链。
> 前置阅读：`docs/plan1/项目框架优化/整体框架优化执行计划.md`（W0~W4 已完成项）、`docs/plan1/评测与可观测性/评测与可观测性执行计划.md`（E 线）。

## 0. 核心结论（先看这个）

1. **单本 PDF 解析实际耗时 6 秒 ~ 8 分钟，不是 1~1.5 小时**（`settings.py:239-246` 的注释是修复①之前的过时数据，见 P3）。
2. **「80% 本地处理」的设计已实现且超额**：书1 本地 540/546（98.9%）、书2 756/757（99.9%）、书3 476/493（86%）。
3. **那本 8 分钟的书（书1，扫描 OCR）慢在本地**：`get_text("dict")` 对它耗时 **198ms/页**，且每页被调了**两次**（P1）。
4. **并发撑不住 100 用户，不是因为改造失败**——W0~W4 修的是「并发正确性」（死锁/竞态），验收标准是 **4 并发（W0）/ 20 并发（W2-5）**，100 从来不在范围内；W4-4「独立扩缩容」那一项**没做**。
5. **对话链路是纯 IO 密集**（embedding/rerank/LLM 全是远端 API，无本地重计算）→ **本机足以完成并发改造与压测，可本地调完再迁**。
6. **主程序没有 Dockerfile**（只有 `deploy/mineru`、`deploy/langfuse` 有）→ 上云前必须先容器化。

### 执行顺序（一句话）

```
① 解析性能修复（本地，独立）
      ↓
② 本地并发容量改造 + 压测 100 并发（与机器无关）
      ↓            ↘ 并行启动
③ 主程序容器化            GPU 服务上云（MinerU/PaddleX/Langfuse）
      ↓            ↙
④ 主程序上云 + 复测（配置原样搬）
      ↓
⑤ 前端
```

**铁律：主程序在 ② 完成后才上云**——并发改造会改变部署形态（多 worker/多副本），提前迁 = 迁两次。

## 3. 分步执行方案

### Step ① 解析性能修复（本地，立即可做，不依赖任何外部条件）

#### P1 — 消除 `_extract_fonts` 的 `get_text("dict")` 遍历【✅ 已完成 2026-09-12】

**证据**：`_extract_fonts`（`pdf_page_profile.py:212-224`）为收集字体名做了一次完整 `get_text("dict")`，实测 **198ms/页**（OCR 书）；而 `page.get_fonts()` 返回同样信息只要 **0.26ms/页**。

**改法**：
```python
# public_kb/ingestion/normalizers/pdf/pdf_page_profile.py
def _extract_fonts(page: Any) -> Tuple[str, ...]:
    """页面字体名 — 用 get_fonts()（页级字体表），不再遍历 get_text("dict")。
    OCR 书实测 198ms/页 → 0.26ms/页。"""
    try:
        return tuple(sorted({str(f[3]) for f in (page.get_fonts() or []) if len(f) > 3}))
    except Exception:
        return ()
```
> 注意：`get_fonts()` 返回页内**使用到的字体表**（basefont），与原实现"文本 span 里出现的字体名"语义一致，`formula_hint`（math/symbol 判断）不受影响。

**附加（次要）**：`build_page_profile` 内 `get_text("text")`（:71）与 `get_text("blocks")`（:117）可合并为一次 `get_text("dict")` 派生，省 ~9ms/页。建议先只做 `_extract_fonts`（改动最小、收益最大），观察后再决定。

**✅ 实测结果（2026-09-12，书1，`PDF_PARSE_PAGE_LIMIT=100` 避开 Tier C、不入库）**：

| 指标 | 修复前 | 修复后 | 提升 |
|---|---|---|---|
| `build_page_profile` | 137.1 ms/页 | **12.19 ms/页** | **11.2×** |
| 端到端 `PdfRouter.parse` | 189.9 s | **55.2 s** | **3.4×** |
| Markdown 输出长度 | 124948 字符 | 124948 字符 | 完全一致 |

- 全量 `pytest test/`：**exit 0，全绿**（1136 collected）
- 输出长度逐字节一致 → 纯性能修复，零行为变更
- 原 manifest（486.775s）未被覆盖，基准跑在临时目录

> 注：`build_page_profile` 内部仍保留一次 `get_text("text")`（8.4ms）与一次 `get_text("blocks")`（0.4ms）+ `iter_lines` 的一次 `get_text("dict")`（135~198ms）。画像侧的大头已消除；**`iter_lines` 的那次 dict 仍在**（Tier A 抽行必需），是这条链路的下一个可选优化点。

#### P2 — Tier C 批量化（可选，中优先级）

**现状**：`pdf_mineru_router.py:116` 逐 range 调用；远程 `app.py:113` 每次 `subprocess.run` 重载模型 → ~80s/range。**但 manifest 显示 Tier C 命中缓存时为零成本**，只有**首次冷解析**才付代价（书3 17 ranges ≈ 20min，一次性）。

**两个选项（择一，或先不做）**：
- **a（小改）**：把该书全部 Tier C 页按顺序合并为**一个子 PDF**，一次调用送回，产出 Markdown 后按页分隔标记切回。
  - 风险：需要 magic-pdf 输出保留页边界（`auto/{stem}.md` 默认合并），需验证可行性。
- **b（大改）**：远程服务改**常驻模型进程**（MinerU 2.x 的 `mineru-api`，或自建 uvicorn 常驻 + 模型只加载一次），彻底去掉 subprocess 重载。
  - 收益最大，但依赖 MinerU 升级，工期大。

**建议**：先不做，除非你要频繁重处理整本书。若做，选 a。

#### P5 — 【新发现】MinerU 服务不可达时，**本地缓存也一并失效**（✅ 已修复 2026-09-12）

**证据链**（2026-09-12 实测）：
- `pdf_router.py:527-533` `_probe_parser_version()` 探测失败时返回**空串** `""`。
- 而缓存键含该版本号：`compute_cache_key(..., parser_version, ...)`（`pdf_mineru_router.py:35-49`）与 `MinerUApiParser._cache_key`（`mineru_api_parser.py:150-154`）。
- 服务在线时缓存写入的键用 `"magic-pdf, version 1.3.12"`；服务下线时探测得 `""` → **键不匹配 → 本地 604 个缓存全部 miss** → 转 HTTP → 不可达 → `RuntimeError`；`pdf_tiered_allow_partial` 默认 `false` → **整本解析失败**。

**实测**：`PDF_PARSE_BASE_URL` 指向的旧服务器（`8.153.82.13:8002`）已 **ConnectTimeout**（到期 + 安全组未放行）。

**影响**：云服务器一挂/一换，**所有含 Tier C 的书都无法重跑**，即使本地缓存其实是完整的。这正是「换服务器」场景下的直接障碍。

**✅ 实现**（`public_kb/services/mineru_api_parser.py` + `pdf_router.py:527`）：
- 新增 `resolve_parser_version()`：探测成功 → **持久化**到 `_mineru_api_cache/_parser_version.txt`；探测失败 → **回退上次已知版本**，来源优先级 `_parser_version.txt` → 任一缓存 sidecar `.json` 的 `parser_version` 字段（缓存写入时记录）→ 空串。
- 探测改用**短超时**（`_PROBE_TIMEOUT_SEC = 5s`），否则服务不可达时会挂满默认解析超时（1800s）。
- `pdf_router._probe_parser_version()` 改为委托该方法（假 parser 无此方法时退回 `health()`，兼容测试注入）。
- 新增 6 项单测（`test/test_mineru_api_parser.py`），含「在线落缓存 → 服务下线 → 重跑命中缓存、零 POST」端到端用例。

**✅ 实测验收**（书1 整本，模拟服务不可达）：

| 检查项 | 结果 |
|---|---|
| 解析成功 | ✅（云不可达下） |
| 离线期间 POST | **0**（仅 2 次探测 GET 失败） |
| ranges / 页集 | 6 段，与原 manifest **逐一对齐** |
| Tier C warnings | `{'cache_hit'}` — 6 段全命中本地缓存 |
| `_parser_version.txt` | 自动恢复为 `magic-pdf, version 1.3.12` |

全量 `pytest test/` exit 0。

### Step ② 本地并发容量改造 + 压测（与机器无关，本机即可完成）

> 前提：压测必须对着**生产同款上游端点**（同一 DeepSeek / SiliconFlow），因为限流在天上。

#### C1 — 全局并发闸门【✅ 已完成 2026-09-12，commit `842a05e`】

新增 `core/concurrency/limits.py::InflightGate`（进程级 `BoundedSemaphore` + 等待超时；
`limit<=0` 关闭；`snapshot()` 供指标）。与入口限流**分工互补**：
限流按**客户端**算速率（429），闸门按**全局**算在飞数（503）。

- 接入 `api/server.py` 两条路径：`/chat`（`_invoke_response`）与 `/chat/stream`（`_sse_stream`）
- 取不到槽位 → `ServiceBusyError`（**503 + Retry-After**，新增错误码 `sys_2004`），不无限排队
- `Settings.max_inflight_requests`（默认 32）/ `inflight_wait_timeout_seconds`（默认 5）
- **⚠️ 默认 32 是估值，须按上游限流实测标定**（见 C8）

#### C2 — 同步端点线程池上限显式化【评估后：暂不做】

C1 闸门默认 32 < anyio 线程池默认 40 → **闸门先于线程池成为约束**，C2 不构成瓶颈。
仅当 `max_inflight_requests` 被调到 > 40 时才需显式设 `anyio` 线程池上限。保留为配置纪律项。

#### C3 — SSE 工作线程纳入闸门【✅ 已完成 2026-09-12，commit `842a05e`】

`_sse_stream` 改为**先取闸门再建线程**——否则 100 并发会先开出 100 个线程再排队，
线程本身就把资源吃光了。取不到 → 流内 `error` 事件（`sys_2004`）+ `done` 收尾；
闸门由工作线程在 `_run_stream_worker` 的 `finally` 释放（图执行完即还）。

测试：`test/core/test_inflight_gate.py`(8) + `test/api/test_inflight_gate_api.py`(3)。

#### ⚠️ 容量的真正天花板在**上游**（实测，动手前须认清）

`public_kb/retrieval/reranker.py:40` `SiliconFlowReranker` 是**远端 HTTP 客户端**，
而实测 SiliconFlow rerank **8 并发即 429**（E 线记忆：8 并发 765 次 / 4 并发 965 次 429，
两轮数据作废）。**知识问答每次都要 rerank** → 即使本机并发控制完美，上游也会先崩。

→「服务 100 并发用户」不是纯代码问题，需产品/架构决策，三选一：

| 选项 | 做法 | 代价 |
|---|---|---|
| **a. 换本地 reranker** | `sentence-transformers` 已在依赖里（`requirements.txt:28`）但**零引用**——用 `CrossEncoder(reranker_model)` 本地推理，彻底去掉上游瓶颈 | CPU 密集，容量 = 核数；需实测精度不降 |
| **b. 提高上游配额** | 找 SiliconFlow 加套餐 | 花钱 |
| **c. 接受降级** | rerank 失败已回退 RRF（`RERANKER_MAX_RETRIES=2`）；把「429 → 降级」当常态，用 C1 闸门把并发压在配额内 | 高峰期答案质量下降 |

**推荐 a**（依赖已就位、零新增成本、彻底解决），但需跑一次检索金标确认精度不降。

#### C8 — 压测脚本【✅ 已完成 2026-09-12】

**⚠️ 关键设计点（踩坑）—— 必须区分客户端，否则测的是限流器不是容量**：
入口限流（`api/middleware/rate_limit.py`）按**客户端键**限流（`X-Tenant-ID` → `X-Forwarded-For`
首跳 → 直连 IP，默认 burst=20 / 60 每分钟）。同机压测所有请求同键 → **并发一高全是 429**。
因此脚本默认 `--clients 100`，给每个合成客户端发不同的 `X-Forwarded-For`。

**✅ 实测（本地，经 SSH 隧道调远端模型；绝对延迟含隧道开销，横向对比才有意义）**：

| 场景 | 结果 |
|---|---|
| 并发 16 / 32 请求，**不分客户端** | 21/32 成功，**11 × 429**（`sys_2003`）—— 印证上面的坑 |
| 并发 16 / 32 请求，`--clients 100` | **32/32 成功**，p50 2.23s / p95 3.21s，吞吐 5.8 req/s |
| 并发 40 / 40 请求，`--clients 100` | **40/40 成功、无 503**，p95 4.62s，吞吐 7.4 req/s —— 闸门**吸收了突发**（等待超时 5s > 单请求 2.5s，排队的都在超时前拿到槽位） |
| 闸门调小验证（`MAX_INFLIGHT_REQUESTS=4` + `INFLIGHT_WAIT_TIMEOUT_SECONDS=0`，并发 10） | **正好 6 × 503**（`sys_2004`），被拒请求 **p50 延迟 0.05s**（瞬时返回，不排队雪崩）；4 个拿到槽位的正常完成 → **C1 端到端验证通过** |

**结论**：C1 行为符合设计（突发排队吸收、超出等待窗口则快速失败）。默认
`max_inflight_requests=32` 在并发 40 下仍从容，**维持现状**；待上游 LLM 配额成为瓶颈时再用本脚本复测标定。

**注意**：`--clients` 只解决**入口限流**的客户端区分；**应用内部**的查询池（8）/SQL 池（8）仍是进程级共享，
高并发下 price 链路会在内层池排队——这是 Step ③ 上 Redis/多副本时要一并看的。
