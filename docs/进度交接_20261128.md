## 2. 现在的实际拓扑

```
公网 443 ── nginx 1.24.0
   ├─ ztb.openagent-lab.top   → /var/www/ztb（dist）  + /api/ → 127.0.0.1:8000
   └─ openagent-lab.top       → /var/www/openagent-lab.top（原有官网，未动）

docker：
  ztb-api    (127.0.0.1:8000)  ← 挂在 api_default + ztb_network 两张网
  ztb-feishu (无入站端口)      ← 飞书长连接（出站 WebSocket），经 http://api:8000 调后端
  ztb_mysql  (127.0.0.1:3306)  ← ztb_network，api 用容器名 ztb_mysql 连
  ztb_redis  (127.0.0.1:6380)  ← ztb_network，api 用容器名 ztb_redis 连
```

**飞书**：`channels.feishu` 走**出站长连接**（不需要公网地址、不需要开放端口）。
⚠️ **同一应用同一时刻只允许一个实例收消息** —— 本机的 `python -m channels.feishu`
必须停掉，否则两边抢连接、消息随机落到不同环境（2026-11-28 切换时已停掉本机进程）。
服务器侧 `FEISHU_ENABLED` 由 compose 覆盖为 `true`，`.env` 里的 `false` 不影响。

**证书**：`/etc/letsencrypt/live/ztb.openagent-lab.top/`（webroot 方式，续期钩子已写进 renewal conf）。

## 3. 今天新踩的坑（4 个，都值得记住）

| 坑 | 现象 | 结论 |
|---|---|---|
| **① `host.docker.internal` 打不到只绑回环的发布端口** | 容器内 `Can't connect to MySQL server on 'host.docker.internal' (timed out)`；三个模块全 500，而知识问答正常（问答只走云向量库） | MySQL/Redis 发布在 **宿主 127.0.0.1**，而 `host.docker.internal` = `172.17.0.1`（默认网桥网关）。**正解：把 api 接到数据库所在的 `ztb_network`，用容器名直连**（已写进 `docker-compose.prod.yml`），不要为了图省事把 3306 绑到 0.0.0.0 |
| **② MySQL 口令与 `.env` 不一致** | 同样表现为"连不上"，但根因是 `Access denied` | 容器实际 root 口令 27 位，`.env` 里是 28 位。**以容器实际口令为准**，改 `.env`（已备份为 `.env.bak.<时间戳>`） |
| **③ compose 改了 `env_file` 不会触发重建** | `up -d` 输出 `Container ztb-api Running`，配置没生效 | 必须 `--force-recreate`。`docker restart` 同样不重读环境变量 |
| **④ nginx 1.24 不认 `http2 on;`** | `unknown directive "http2"`，`nginx -t` 直接失败 | `http2 on;` 是 **1.25.1+** 语法；1.24 必须写 `listen 443 ssl http2;`。另外 `listen [::]:443` 与主站 vhost 重复声明会报 `protocol options redefined` 警告 → 本项目 ztb 只有 A 记录，直接不写 IPv6 监听 |

**运维层面还有两条：**

- **ACME 校验路径不能删**：`80` 端口的 `location /.well-known/acme-challenge/ { root /var/www/certbot; }`
  是 90 天后自动续期唯一依赖，删掉则续期静默失败（`certbot renew --dry-run` 可验）。
- **PowerShell 往 ssh 管道传脚本会被破坏**（追加 CRLF、非 ASCII 乱码 → `command not found` / `tail: ...\r`）。
  本项目服务器操作一律走 **本地写文件 → `scp` → `ssh bash <file>`**。

**下午新增的两个坑：**

| 坑 | 现象 | 结论 |
|---|---|---|
| **正则 location 只写 allow/deny 会 404** | 加完 `location ~ ^/api/(metrics\|docs…)$ { allow 127.0.0.1; deny all; }` 后，回环访问也返回 **404** | 该 location 没有内容处理器，nginx 去 `root` 里找文件了。必须自己带 `proxy_pass`；正则 location 里 `proxy_pass .../;`（带 URI）行为不直观，用 `rewrite ^/api/(.*)$ /$1 break;` 再 `proxy_pass http://ztb_api;`（不带 URI） |
| **L2 语义路由会绕过追问消解** | 飞书里「具体一点有什么适用的条例吗」被判 `deep_agent(score=0.561)` → 答非所问；前后两轮自包含问题都正常 | L2 命中即短路返回 `RouteResult(intent=...)`，`resolved_question` **恒为 None**（代码注释原文：L0/L1/L2 快路径恒 None），而**独立 `rewrite` 节点在 `understand_merged=true`（默认）时根本没接进图**。阈值 0.5 太低，灰区问句（0.5~0.7）被误判。已提到 0.7 并改为 `SUPERVISOR_SEMANTIC_THRESHOLD` 可覆盖 |

## 4.5 镜像与发版（2026-11-28 下午补齐）

**之前的问题**：11-27 的镜像是手工 `docker build` + `docker push`，**镜像对不上任何 commit**，
出问题说不清"线上跑的是哪版代码"；而且线上那次还是直接在服务器上 build 的，连仓库产物都没有。

**现在的链路**：

```
本机 commit → git push → CI（lint / test / contract / frontend 四门禁）
                            │
                            └─（需要发版时手动触发 .github/workflows/cd.yml）
                                 buildx 构建 linux/amd64 → 推华为 SWR，tag = :<commit sha>
                                        │
                                        └─（production environment 人工批准）
                                             服务器：git reset --hard <sha> → docker pull → retag
                                                     → --force-recreate api feishu → 健康检查
```

**当前线上对应关系**（核对时照这张表）：

| 项 | 值 |
|---|---|
| 线上 commit | `089f34d` |
| 镜像 ID | `80daf8d2c22c` |
| SWR 标签 | `swr.cn-north-4.myhuaweicloud.com/ztb-agent/ztb-api:089f34d` |
| 服务器工作树 | 干净，`HEAD = 089f34d` |

核对命令（服务器上）：

```bash
docker inspect ztb-api --format '{{.Image}}'      # 应与 SWR tag 的 image id 一致
docker inspect swr.cn-north-4.myhuaweicloud.com/ztb-agent/ztb-api:089f34d --format '{{.Id}}'
git -C /root/ztb_demo status --short              # 空 = 无漂移
```

**首次跑 cd.yml 前要配的东西**（详见 `.github/workflows/cd.yml` 文件头）：

| 类型 | 名称 | 说明 |
|---|---|---|
| Secret | `SWR_USERNAME` | 形如 `cn-north-4@<AK>` |
| Secret | `SWR_PASSWORD` | 长期登录密钥（**不是** AK/SK 本身） |
| Secret | `DEPLOY_HOST` / `DEPLOY_USER` / `DEPLOY_SSH_KEY` | 仅自动部署需要 |
| Variable | `CD_DEPLOY_ENABLED = true` | 打开自动部署 job；**默认关**——打开等于把服务器私钥交给 GitHub，需人工拍板 |
| Environment | `production` | 配 Required reviewers，「手动批准」就是它 |

未打开自动部署时，cd.yml 只做「构建 + 推 SWR」，服务器上手工 pull 一次即可（也安全）。

**下午新踩的两个坑：**

| 坑 | 现象 | 结论 |
|---|---|---|
| **GHA 的 `env` 上下文不能用在 job 级 `env:`** | `Invalid workflow file: .github/workflows/cd.yml#L1 (Line: 128, Col: 14): Unrecognized named-value: 'env'`，工作流被判无效，push 后立刻出现一条以文件名为 title 的失败 run | `jobs.<id>.env` 正在定义的就是 env，不能引用自己。改成 step 内用 shell 变量拼；workflow 级 `env` 会自动注入 step 的运行环境 |
| **服务器出网只有 ~6 Mbps，推 1.2GB 镜像要半小时** | `docker push` 日志长时间停在最后几个 layer，`ss` 看到发送队列积压 24MB，进程 CPU 时间 0 | 实测 60 秒发 49MB ≈ **6.5 Mbps**。**大镜像的构建/推送要放 CI（runner 带宽好）或本机**，别在 2C4G 轻量服务器上推——这次 8 分钟构建 + 约 30 分钟推送 |
