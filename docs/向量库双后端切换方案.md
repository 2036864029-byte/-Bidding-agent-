# 向量库双后端切换方案（本地自建 ⇄ 云托管）

> 目标：**同一份代码**，官网部署连云向量库、本地开发连本地容器；切换只动配置，不动业务代码。
> 前提结论：**不需要重新向量化入库**，现有数据可以整体搬到云端（见 §2）。

---

## 0. 一句话结论

| 问题 | 答案 |
|---|---|
| 要把 10 万条向量重新算一遍吗 | **不用**。用 `milvus-backup` 出备份 → Zilliz 控制台「数据迁移 → 备份文件」导入 |
| 迁移会丢 BM25 / 全文检索吗 | **不会**。源集合启用了 Full Text Search 时，Zilliz 会保留目标集合的 Function 设置（且此后不可修改） |
| 迁移会保留 HNSW 索引参数吗 | **不会**。迁移过程自动创建 **AUTOINDEX**，`M`/`efConstruction` 等参数不迁移 |
| 迁移完能直接搜吗 | **不能直接搜**，必须先 Load Collection。**应用侧已覆盖**：`public_kb/engine.py:130` 调 `load_existing()` → `MilvusClient.load_collection()` |
| 免费额度够吗 | 够。免费集群 5 GB / 5 个 Collection / 250 万 vCU 每月；本项目 2 个集合、裸向量约 0.5 GB |

### 云端能力实测（Zilliz Serverless · ali-cn-hangzhou · 兼容 Milvus 3.0）

| 能力 | 结果 |
|---|---|
| 混合检索（dense + sparse + `RRFRanker`） | ✅ 可用，5 条结果 / 94 ms，RRF 分数正常 |
| 建 HNSW 索引 | ✅ 可建（实测建成功，`index_type=HNSW`） |
| 建 IVF_FLAT 索引 | ✅ 可建 |
| 建 AUTOINDEX | ✅ 可建 |
| AUTOINDEX 收到 HNSW 的 `ef` 参数 | 静默忽略，**不报错**（所以配置错配很难发现） |

> ⚠️ 一个曾经写错的判断：**"云端不支持 HNSW"是错的**。那条结论源自 Zilliz 迁移文档的
> 「迁移过程中会自动为迁移的 Collection 创建 AUTOINDEX」——那是**迁移流程的默认行为**，
> 不是平台能力限制。实测云上 HNSW / IVF_FLAT / AUTOINDEX 都能建。
> 现有两个集合是 AUTOINDEX，是因为它们由脚本按 `VECTOR_BACKEND=cloud` 的默认值建的，
> 不是被逼的。想要 HNSW 可以 `drop_index` 后重建，但没必要（AUTOINDEX 由平台托管优化，
> 召回已经与本地 5/5 一致）。

## 1. 为什么不是「插件注册表」而是「后端档位」

两个后端**说的是同一种协议（Milvus gRPC/REST）**，区别只有四样：

| 差异项 | 本地自建 | 云托管 |
|---|---|---|
| 连接 | `http://host:19551` | `https://xxx.zillizcloud.com` + token |
| dense 索引 | HNSW（M=16 / efConstruction=128） | AUTOINDEX（迁移默认产物；云上其实也支持 HNSW/IVF_FLAT） |
| 检索参数 | `{"ef": 64}` | 不传额外参数 |
| 超时 | 30s 够 | 跨公网，建议放宽 |

所以「插件化」要做的事，本质是**把这四项打包成一个具名档位**，而不是引入一层 Protocol + 注册表：

| 方案 | 切换成本 | 新增后端成本 | 代价 |
|---|---|---|---|
| A. 各变量散着配 | 记 4 个变量，漏一个就是半切换状态 | 低 | **漏配无报错**，只有召回变差（最糟的失败模式） |
| **B. 具名档位（本方案，已实现）** | **一个 `VECTOR_BACKEND`** | 加一个档位分支 | 无 |
| C. Protocol + 注册表 | 一个变量 | 实现一个类 | 现在只有一个协议，多出来的抽象没有第二实现可验证 |

选 B。将来真要接**非 Milvus** 后端（pgvector / Qdrant），再上 C——那时才有第二种协议可测。

### 已实现的开关

```ini
# 服务器（官网）
VECTOR_BACKEND=cloud
MILVUS_URI=https://in03-xxxxxxxx.serverless.<region>.zillizcloud.com
MILVUS_TOKEN=<只读角色的 API Key>

# 本地（开发）
VECTOR_BACKEND=            # 留空 = local，走 MILVUS_HOST:MILVUS_PORT
MILVUS_HOST=127.0.0.1
MILVUS_PORT=19531
```

代码落点（三处，均不影响默认行为）：

| 文件 | 改动 |
|---|---|
| `core/config/settings.py` | 新增 `vector_backend`（读 `VECTOR_BACKEND`）；`milvus_dense_index_type` / `milvus_sparse_index_type` 改为可被环境变量覆盖，且 `cloud` 时 dense 默认 **AUTOINDEX** |
| `core/vectorstore/milvus_client.py` | 初始化打一行日志：`向量后端=cloud \| uri=... \| dense_index=AUTOINDEX \| bm25=true`（不打 token） |
| `price_engine/semantic.py` | 价格语义召回改用 `resolved_milvus_uri` 并透传 token（原先硬编码 `http://host:port`，云上会**静默降级**为 `None`） |

> 为什么 dense 索引类型要跟档位联动：它同时被**建索引**和**检索**两处读取（`core/vectorstore/index_params.py`）。云端集合是 AUTOINDEX，若检索仍按 HNSW 发 `ef`，轻则被忽略、重则报错——而这类不匹配不会在启动时暴露，只会在检索质量上体现。

## 2. 数据迁移（不重新向量化）

### 2.1 在本地出备份

```bash
# 1) 下载 milvus-backup（用与本地 Milvus 同大版本的 release）
#    https://github.com/zilliztech/milvus-backup/releases
# 2) 同级目录建 configs/，放 backup.yaml
# 3) 关键配置：milvus 与 minio 必须与本地 Milvus 实例一致
#    docker compose 装的默认值是：
#      minio.bucketName = a-bucket
#      minio.rootPath   = files
#      milvus.address   = 127.0.0.1 / port = 19531（本机 v2.6 栈的宿主端口）
./milvus-backup --config configs/backup.yaml create -n ztb_kb
./milvus-backup --config configs/backup.yaml get -n ztb_kb
```

备份文件会落在本地 MinIO 的 `a-bucket` 里，用 MinIO 控制台（`http://127.0.0.1:9004`）或 `mc` 下载：

```bash
mc alias set local_minio http://127.0.0.1:9003 minioadmin minioadmin
mc cp --recursive local_minio/a-bucket/<backup-root>/ztb_kb ./ztb_kb
```

### 2.2 在 Zilliz 控制台导入

1. 左侧导航 → **数据迁移** → Milvus 迁移源区域点 **备份文件**
2. 选 **上传本地文件** → 上传 `ztb_kb` 文件夹（**上传文件夹本身**，不是它的父目录 `<backup-root>`）
3. 选目标集群与 Database → 勾选要迁的 Collection（`public_kb`、`mysql_price_semantic`）
4. 提交，到 **任务中心** 看进度

迁移完成后：

- 自动为每个 Collection 建 **AUTOINDEX**
- 对每个 Collection 执行一次 **Load**（应用侧 `load_existing()` 也会做，见 §0）
- 校验 entity 数：迁移后控制台显示的数量必须与本地 `num_entities` 一致；不一致就删掉重建迁移

### 2.3 迁移后必须验的三件事

```bash
# ① 集合与行数（本地 / 云端各跑一次，数字必须一致）
python -c "
import os, pymilvus
from core.config.settings import Settings
s = Settings()
c = pymilvus.MilvusClient(uri=s.resolved_milvus_uri, token=s.milvus_token or None)
for name in ('public_kb', 'mysql_price_semantic'):
    print(name, c.get_collection_stats(name))
"

# ② schema 契约（本项目会校验字段与 max_length，迁移如果改了字段会在这里炸）
python -c "
from core.config.settings import Settings; from core.vectorstore.milvus_client import MilvusStoreManager
"   # 或用 scripts/diag_retrieval_smoke.py，它会调 load_existing() 触发契约校验

# ③ 一次真实检索（要看到带【来源N】的回答，而不是降级话术）
```

> ② 有个更省事的入口：`python scripts/diag_retrieval_smoke.py` —— 它会 `load_existing()`，
> 契约不符直接抛异常，不会让你带着坏 schema 上线。

## 4. 官网只读：用凭据管，不用代码开关

双后端最容易出的事故是「官网那一份被误写/误删」——项目里有重建集合与清空的接口（`initialize_collection(recreate=True)` / `clear_collection()`），一旦指到云端，数据没了且没有便宜的恢复路径。

**正确做法是给凭据分权，而不是在代码里加开关**：在 Zilliz 控制台为官网单独建一个**只读角色**的 API Key，写权限的 Key 只在本地 `.env` 里。

比代码开关强在：即使你手滑调了管理接口、甚至把整个应用打穿，服务端也会拒绝写入。

> 若你的套餐不支持自定义角色，退而求其次：生产 `.env` 里不放写权限 Key，并确认 nginx 挡住了 `/ingest`、`/admin` 一类管理端点。

## 5. 两个后端必须一致的几件事（否则结果不可比）

| 项 | 说明 |
|---|---|
| `MILVUS_COLLECTION` | 集合名不一致 → 云端查不到（会按「集合未初始化」报错，相对容易发现） |
| Schema 字段与 `max_length` | 迁移会保留源 schema；本地若改过 schema，两份就**不是同一个库**了 |
| `ENABLE_MILVUS_BM25` | 与集合 schema 绑定。云端迁移会保留 Function，本地是 `true` 时云端也是 `true`；本地若关掉，两边召回不可比 |
| Embedding 模型 | 必须都是 `BAAI/bge-m3`（1024 维）。换模型 = 两边向量空间不同，交叉查询没有意义 |

判断当前连的是哪边：看启动日志的 `向量后端=...` 行（本次新增），别靠「感觉它变慢了」猜。

## 6. 坑清单

1. **备份时 `minio.bucketName` / `rootPath` 写错** → `create` 报「找不到 collection」，实际是连错了对象存储。
2. **上传了父目录而不是备份子目录** → 控制台识别不到备份集。
3. **迁移后没 Load 就压测** → 全量 search 失败，误判成「云上性能不行」。
4. **以为 HNSW 参数会迁过去** → 云端是 AUTOINDEX；`milvus_dense_index_type` 留在 `HNSW` 会让检索参数与实际索引不符。
5. **免费额度用满才停** → vCU 月额度按读/写操作扣，作品站被爬一次就得等下月。要盯控制台用量面板。
6. **`MILVUS_TOKEN` 进了日志或仓库** → `.env` 已被 gitignore，但排查时别 `print(settings)`。
7. **容器里连云端要出网** → `deploy/api/docker-compose.yml` 的 `MILVUS_HOST: host.docker.internal` 仍然存在，但 `MILVUS_URI` 非空时它不生效（`resolved_milvus_uri` 优先 URI）。**不用改 compose**，只要 `.env` 里有 `MILVUS_URI`。
