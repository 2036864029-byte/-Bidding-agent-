## 0. 先给结论：这句话里哪些能扛追问

| 模块                | 强度              | 说明                                                        |
| ----------------- | --------------- | --------------------------------------------------------- |
| Supervisor + 业务子图 | **强（能扛 3 层）**   | 子图经适配器挂为父图节点，config 透传与字段收窄都有取舍可讲                    |

| 中断续跑              | **强（改造后）**      | `interrupt()` → `Command(resume=)` → `/chat/resume`，整条链跑通 |

## 1. 一次请求的完整链路（先记住这张图，追问都从这里展开）

```
POST /chat  (thread_id = session_id)
  │
  ├─ 上传文件？ → POST /files/upload → filestore（只进会话缓存，不入向量库）
  │
  └─ 图入口 → supervisor 节点
       │
       ├─ L0 文档上下文  _doc_context_kind()        显式 file_ids 压过一切
       │                                            自动附着让过 L1 强规则
       ├─ L1 正则规则    classify_rules()           routing_rules.yaml，0 成本
       ├─ L2 语义相似    classify_semantic()        示例向量余弦，阈值 0.5
       └─ L3 LLM 结构化  build_router_node()        intent + resolved_question 一次出
                    │
                    ├─ 能力节点（编译子图 + 适配器挂为节点）
                    │     knowledge_qa / price_inquiry / doc_qa / deep_agent / general_chat
                    │     内部：检索 → 规划 → 工具执行（受 ToolPolicy 约束）→ 生成
                    │
                    ├─ clarify（低置信）→ 同步反问 / interrupt() 挂起 → /chat/resume
                    │
                    └─ handoff_decider → 规则命中则转下一个 Agent → 合并终态答案
```

## 2. 逐句拆解

### 2.1 "主从式多 Agent 编排（Supervisor + 业务子图）"

**代码落点**

- `orchestration/main_graph.py:143` `build_supervisor_graph()` —— 父图 `StateGraph(SupervisorState)`
- `orchestration/main_graph.py:230` 每个能力 `graph.add_node(name, _stamped_agent(...))`，节点主体是**包装过的适配器**（`:112` `_as_agent_callable`）
- `orchestration/main_graph.py:112` `_as_agent_callable()` —— 把 `CompiledStateGraph` 投影成父图可调用的节点
- `agent/nodes/knowledge_qa/subgraph.py`、`price_inquiry/subgraph.py` —— 各自 `compile()` 成子图
- `orchestration/main_graph.py:276` `graph.compile(checkpointer=checkpointer)` —— 父子共用同一个 checkpointer

**30 秒讲法**

> 父图只做三件事：理解、路由、收口。业务逻辑全在子图里，子图有自己的 State 和内部边。子图编译成一个对象，被父图当成一个节点用——中间隔了一层适配器（`_as_agent_callable`），因为要套兜底和输出形状校验，还要把子图的私有键挡在父图终态外面。父子 state 靠同名字段自动对接：父图的 `SupervisorState` 继承 `AgentState` 再加 4 个编排字段，子图只声明 3 个，所以子图看不见 `handoff`、`last_agent` 这些。

**追问 1：为什么是包一层适配器调 `invoke()`，而不是把编译子图直接 `add_node`？**

> 三个原因：① 要套三层包装——`with_output_guardrails(_with_fallback(_as_agent_callable(...)))`，兜底和输出校验只能包在函数上；② 要**收窄回写字段**，只放行 `business_result` 和 `messages`，子图内部的 `qa_*` / `pg_*` 中间键不进父图终态；③ 当前 langgraph 1.2.11 的 `CompiledStateGraph` 不能直接当可调用节点，只有 `.invoke`。
> **代价要主动说**：包一层之后，子图内部的模型 token 不会冒泡到父图，官方 `stream_mode="messages"` 在默认链路拿不到——这正是 `core/streaming/sink.py` 存在的原因（contextvar 旁路 StreamSink）。另外 `config` 必须显式透传（`target.invoke(state, config=config)`），漏了 `thread_id` 就断。

**追问 2：父子 State 怎么合并？会不会互相覆盖？**

> `SupervisorState` 和子图的 `AgentState` 是字段名对齐的：`messages` 用 `add_messages` reducer 累积（不是覆盖），`business_result` 是后写覆盖（一次请求只有一个业务结果），`pending_context` 由 handoff 时显式写入。子图返回的 dict 只包含它声明要写的键，不用全量返回，所以不会把父图其它 channel 冲掉。

**追问 3：为什么不用官方 `langgraph-supervisor` 或 `create_react_agent`？**

> 官方 supervisor 是"每次由 LLM 决定下一个 worker"，我的业务里 6 个能力是固定的，而且强规则命中的场景（问候语、项目编号）根本不该花一次 LLM 调用。另外能力要能靠注册表热插拔——新增一个能力只改注册表，不改图。所以路由是"规则优先、LLM 兜底"的确定性级联，Supervisor 只负责调度不负责决策。

### 2.2 "主图串联查询改写 → 三级降级路由（正则 / 语义 / LLM）"

**代码落点**

- 改写：`orchestration/supervisor.py` L3 的 `build_router_node` —— 一次结构化调用同时输出 `intent` + `resolved_question`，`resolved_question` 以**同 id 原位替换** `messages[-1]`，下游检索拿到归一化问题
- 独立改写节点（回退路径）：`orchestration/main_graph.py:257` `build_rewrite_node()`，受 `Settings().understand_merged` 控制，默认 true 时入口直连 supervisor
- L0：`orchestration/supervisor.py:108` `_doc_context_kind()`
- L1：`orchestration/supervisor.py:125` `classify_rules()` → `orchestration/routing_rules.yaml`
- L2：`orchestration/supervisor.py:165` `classify_semantic()`，阈值 `:50` 0.5
- L3：`orchestration/supervisor.py:207` `_build_llm_router()`，`temperature=0` 结构化输出
- 级联总装：`orchestration/supervisor.py:291` `route_question_full()`

**30 秒讲法**

> 我做的是四级降级，成本从低到高排：文档上下文 → 正则规则 → 语义相似 → LLM 结构化。前面三级都是"零 LLM 调用"，只有兜不住才落到 LLM。改写不是独立节点，是并进 L3 那一次结构化调用里的——一次调用同时出意图和自包含问题，省一次往返。

**追问 1：为什么 L2 语义层一开始是关的？现在为什么能开？**

> 因为原实现是每个请求把 6 个能力的示例（每个 2~3 条）逐条重新 embed，一次请求十几次 API 调用，比直接走 LLM 还贵。改成**进程内预计算**：按 registry 签名（能力 id + 示例集合的哈希）缓存示例向量，registry 一变签名就变、自动失效；进程内加锁防并发重复算。单请求只剩 1 次 embed（只嵌用户问题）。嵌入失败捕获异常降级到 L3，不让路由因为依赖故障整体失败。

**追问 2：阈值 0.5 怎么定的？**

> 在 49 条带文件的金标集上调的，取的是"宁可漏到 L3，也不要错路由"的保守值。因为漏到 L3 的代价是多一次 LLM 调用（几百毫秒），错路由的代价是答非所问、用户直接失去信任。**短板我也清楚**：这个阈值没有真实流量的回归集，只有合成题，这是当前最该补的一块。

**追问 3：为什么 L3 要把改写和意图合并成一次调用？**

> 两件事依赖同一个输入（用户问题 + 历史），拆成两次调用就是两次往返、两份 token，且改写结果和意图可能不一致（改写后问题变了，意图却按原问题判的）。合并后一次输出两个字段，还天然保证一致。代价是 prompt 更复杂、结构化输出 schema 更大，所以留了 `understand_merged=false` 的回退开关。

**追问 4：L0 为什么分"显式"和"自动附着"两档？**

> 这是踩坑改出来的。原来只要会话里有文件就走 doc_qa，结果用户传完文件后问"这个项目编号是多少"，被强行拉进文档问答，明明该走业务查询。所以拆两档：客户端**显式**传 `file_ids` 是强意图，压过一切；服务端**自动附着**的文件是弱信号，必须先让过 L1 强规则。`supervisor.py:325` 的注释里就写着这个 bug。

### 2.3 "handoff 跨 Agent 转交 → 终态"

**代码落点**

- `orchestration/supervisor.py:388` `decide_handoff()` —— 按 `routing_rules.yaml` 的 `handoff` 段判定
- `orchestration/routing_rules.yaml:25` 唯一一条规则：`price_inquiry → knowledge_qa`（关键词：法规/依据/为什么/合规…）
- `orchestration/main_graph.py:65` `_handoff_decider_node()` —— 注入子问题 + `pending_context`
- `orchestration/main_graph.py:213` `_route_after_decider()` —— 目标必须在 `allowed` 集合内
- `orchestration/main_graph.py:56` `_compose_handoff_answer()` —— 两段答案组合成终态

**30 秒讲法**

> Agent 跑完之后不是直接结束，先过 `handoff_decider`：命中规则就把"还需要解释什么"作为子问题交给下一个 Agent，同时把上一段答案放进 `pending_context`；目标 Agent 完成后，用 `_compose_handoff_answer` 把两段拼成终态。转交是**单跳**的，目标必须在白名单里。

**追问 1：怎么防死循环？**

> 两道：① `_route_after_decider` 里目标必须在 `allowed` 集合内，不在就结束；② 设计上只允许单跳，不给自己转回自己留口子。要做多跳我会加转交计数和 A→B→A 检测。

**追问 2：为什么是规则触发，不是让 LLM 自己决定要不要转交？**

> 场景很窄：价格查询结果需要法规解释时才转，这是个确定性业务判断，用 LLM 判反而引入不确定性。规则在 yaml 里，运营可以自己改关键词，不用发版。**但这也是短板**——只有 1 条规则，谈不上通用 handoff 框架，我是按真实业务需求做的，不是按"支持任意编排"做的。

### 2.4 "固化 Thread 会话、Upload 文件上下文"

**Thread 会话**

- `core/session/store.py:49` `SessionRegistry` —— session 元数据（tenant、创建时间、最后活跃）
- `core/session/store.py:97` `cleanup()` —— TTL 惰性清理，删 session 时联动删检查点
- `agent/checkpointer.py:136` —— **从检查点源头枚举线程**，不是靠进程内 dict，多副本一致

**Upload 文件上下文**

- `api/server.py:530` `POST /files/upload`
- `api/server.py:129` `_resolve_context_docs()` —— 显式 `file_ids` 优先
- `api/server.py:110` `_session_context_docs()` —— 没带 `file_ids` 时自动附着本会话最近 N 个未过期文件（`SESSION_FILE_AUTOLOAD_N`）

**30 秒讲法**

> 会话以 thread_id 为唯一键，检查点按 thread 隔离落盘，元数据另存一份带 TTL 的注册表；清理是惰性的——访问时顺带扫过期项，避免定时任务和检查点的生命周期打架。线程列表从检查点枚举而不是内存 dict，多副本下也能拿到全量。上传文件只进会话缓存、**不入向量库**，避免临时文件污染公共知识库。

**追问 1：为什么不入向量库？**

> 三个原因：① 用户传的招标文件是一次性的，入公共库会污染检索结果、且无法按租户隔离；② 解析+切分+入库是异步链路，用户等不起，问答需要秒级可用；③ 删除不可靠——会话过期后向量库里的残留没法保证清干净。所以改成会话私有索引，会话结束即释放。

**追问 2：多副本下会话一致吗？**

> 元数据在注册表（默认内存，切 SQLite 后共享），线程从检查点枚举（一致）。但 **SSE 还是单 worker**，多副本要换 Redis pub/sub——这块我没做完，会直说。

### 2.5 "Memory 状态合并"（建议改口）

**代码事实**

- 多轮：`messages` 走 `add_messages` reducer 累积，检查点按 thread 持久化
- 跨 Agent：handoff 时 `pending_context` 合并上一段答案
- **没有**：摘要压缩、token 预算裁剪、长期记忆（用户偏好/画像）

**建议表述**

> 改成「多轮记忆按 thread 隔离持久化，跨 Agent 交接时合并上下文」

**为什么改**

> "状态合并"听着像有独立的 Memory 模块（摘要 + 蒸馏 + 长期存储）。面试官只要问一句"你什么时候触发摘要、阈值多少、摘要丢了原始信息怎么回捞"，这里就空了。改成上面那句，反而能讲细节：reducer 语义、`pending_context` 什么时候写、检查点怎么按 thread 隔离。

### 2.6 "Tool Policy 能力绑定"

**代码落点**

- `agent/policy.py:46` `ToolPolicy` —— `allowed_names` / `is_allowed()` / `filter()` / `deny_message()`
- `agent/policy.py:98` `policy_for()` —— 按能力 id 取白名单，**未登记能力 → 空白名单（fail-closed）**
- `agent/policy.py:124` `bind_capability_tools()` —— 装配期返回 `BoundTools(tools, policy)`
- `agent/nodes/deep_agent.py:753` 装配期：只 bind 白名单工具
- `agent/nodes/deep_agent.py:435` 执行期：`policy.is_allowed()` 不通过 → 不执行，`status="denied"`
- `agent/tool_agent.py:65` / `:89` 同样的两道闸
- `agent/nodes/deep_agent.py:687` `_tool_catalog()` —— 声明名 → 工具工厂映射

**30 秒讲法**

> 白名单的唯一来源是能力注册表，`CapabilitySpec.tools` 写的是声明名，装配期通过工厂映射成真实工具。两道闸：装配期只把白名单工具 bind 给模型（模型看不到就调不了），执行期再校验一次（因为模型可能凭记忆拼工具名，或者历史消息里带着旧工具名）。越权的不执行、回一句"工具未授权"，在轨迹里标 `denied`，可以接告警。

**追问 1：为什么两道闸不合并成一道？**

> 只做装配期，模型在多轮里看到历史 `tool_call` 就会尝试复现；只做执行期，等于把非法工具塞进 context，白烧 token 还诱导幻觉。两道闸成本不一样：装配期是"少给"，几乎零成本；执行期是一次 set 查找，可以忽略。

**追问 2：为什么 fail-closed 而不是 fail-open？**

> 工具是能力边界。未登记的能力拿不到白名单，默认全拒——宁可这个能力跑不了工具，也不能让它拿到全量工具。安全默认值必须是关，不是开。

**追问 3：声明名和实现名为什么要解耦？**

> 注册表是数据（yaml/代码声明），工具是代码。直接写实现名会让注册表依赖具体实现，改个工具函数名要改注册表；解耦后注册表写 `kb_search`，工厂把它映射到 `kb_search_tool()`，还能按能力注入不同的参数预设。

### 2.7 "Clarification 澄清反问" + "支持中断续跑"

**代码落点**

- `agent/nodes/clarify.py:70` `node_clarify()` —— 双模式
  - 默认（`HITL_CLARIFY=false`）：直接返回反问文案 + 候选，同步终态，无状态
  - 开启：`clarify.py:93` `interrupt({...})` 挂起整图
- `agent/nodes/clarify.py:51` `_resume_text()` —— 把 resume 载荷归一成答复文本，空答复按放弃处理
- `agent/graph.py:293` `resume()` → `:307` `Command(resume=value)`
- `agent/graph.py:315` 从 `__interrupt__` 提取挂起信息
- `orchestration/main_graph.py:219` `_route_after_clarify()` —— 拿到答复回 supervisor 重路由，取消则 END
- `api/server.py:797` `POST /chat/resume`
- `api/schemas.py` 响应新增 `interrupted` / `interrupt` 字段

**30 秒讲法**

> 路由低置信但候选非空时，不硬答也不硬拒，先反问。默认是同步终态——返回反问文案和候选，前端渲染后用户重新发问，无状态。开启 HITL 后走 `interrupt()`：整个图在 clarify 节点内挂起，断点随 checkpoint 落盘，接口返回 `interrupted=true` 和候选；客户端带答复打 `/chat/resume`，`Command(resume=...)` 从断点继续，本节点在 `interrupt()` 处拿回答复，作为新的用户消息交回 supervisor 重新路由。

**追问 1：这和"前端再问一次"有本质区别吗？**

> 有。重新发问是全新一轮，路由、检索、已完成的子图全要重跑，上下文只能靠 messages 拼；`interrupt()` 是同一轮挂起，**断点之前的执行不重跑**，服务端明确知道"我在等哪个问题的答复"，答复能精确落回挂起点，不会串到别的问题上。

**追问 2：resume 到底传什么？**

> `Command(resume=value)`，`value` 就是 `interrupt()` 的返回值，这里传用户选的候选文本。节点里 `_resume_text` 归一化——兼容字符串、dict（`{"answer": ...}`）、None，空值按放弃处理，避免挂起状态永远悬着。同一轮最多挂 1 次，防止连环追问把用户绕死。

**追问 3：挂起期间进程重启会怎样？**

> checkpoint 落到 SQLite/Postgres 就没问题，thread_id 不变直接续；`MemorySaver` 会丢——这也是我把默认后端设成 SQLite 的原因之一。

**SSE**

- `core/streaming/sink.py:33-36` 事件类型：`token` / `result` / `error` / `done`
- `core/streaming/sink.py:43` 线程安全队列，生成节点写、SSE 端点读
- `core/streaming/sink.py:81` `emit_token()` 从 contextvar 取当前请求的 sink
- `api/server.py:310` `_sse_stream()`，`:791` `StreamingResponse`，`Cache-Control: no-cache` + `X-Accel-Buffering: no`

**30 秒讲法**

> 三种后端按配置切换，默认 SQLite——因为它既持久化又没有外部依赖。SSE 没用官方 `stream_mode="messages"`，因为它只在**当前图运行内**捕获 token，子图里的模型 token 不会冒泡到父图；我的知识问答和价格查询都是编译子图，默认链路下拿不到。所以做了 contextvar 的 StreamSink 旁路：生成节点从 `.invoke()` 改成 `.stream()`，每个 chunk 写队列，端点逐帧转 SSE。协议固定四个事件，`result` 是权威终态，`done` 兜底关闭。

**追问 1：踩过什么坑？**

> `from_conn_string()` 返回的是**上下文管理器**，`with` 退出连接就关了，检查点写不进去。SQLite 和 Postgres 都栽在这，改成自建连接再传进去。SQLite 还要 `check_same_thread=False`，因为图跑在线程池里。这两条在 `checkpointer.py:9-11` 的注释里有记录。

**追问 2：多 worker 下 SSE 怎么办？**

> 现在是单 worker：图跑在独立线程，`copy_context()` 把 contextvar（sink、request_id、session_id）带过去，端点从队列读。多副本要换 Redis pub/sub，每个副本订阅自己的 channel。**这块我没做完，不会说已经支持**。

## 6. 附：deep_agent 算不算 subagent（编排范式定位）

### 6.1 市场上 "subagent" 有三种混用含义

| 含义 | 判据 | 代表 |
|---|---|---|
| 运行时派生的隔离实例 | 父 Agent 在运行中调工具生成，独立上下文窗口、独立 prompt/工具/权限，只回最终结论，可嵌套 | Claude Code 子 Agent、Anthropic 多 Agent 研究系统 |
| 编排拓扑里的下位 worker | 图里预先声明的节点或子图，由 supervisor 调度 | LangGraph subagents / supervisor |
| 权限与职责边界 | 受限工具集 + 专用 system prompt | 各类"专家 Agent" |

**四问快速判定**：谁创建的（代码写死 / 运行时生成）→ 上下文是否独立 → 能否并发 → 能否嵌套。

### 6.2 本项目的 deep_agent 逐条对照

| 判据 | 现状 | 代码依据 |
|---|---|---|
| 谁创建 | 注册表预先声明，supervisor 路由进图，**非运行时派生** | `agent/registry.py` `_seed_deep_agent()`；触发面是 `routing_rules.yaml` 的 `agent_gate`（带文件 + 跨源关键词） |
| 上下文 | plan / 步骤 / 反思都在局部变量与 `business_result.data.trace`，父 `messages` 只收一条 `AIMessage` | `agent/nodes/deep_agent.py:816` |
| 并发 | 计划内多步骤用线程池并行，不是多个子 Agent 并行 | `_execute_steps()` |
| 嵌套 | 不能派生下一代 | — |
| 权限 | 有自己的工具白名单（ToolPolicy 按能力 id 取） | `_bound_tools("deep_agent")`；`agent/policy.py` |
| 生命周期 | 与父图共用 thread / checkpoint，plan 跑到一半失败不能从第 N 步续 | 无独立 checkpointer 命名空间 |

**结论**：它是 **worker 节点**，不是严格意义的 subagent；准确说法是"具备 subagent 的上下文隔离效果，但没有独立生命周期"。另注：`knowledge_qa` / `price_inquiry` 是编译子图，`deep_agent` 是过程式函数 + 内部循环，项目里有两种 worker 形态。

### 6.3 面试口径（三句）

> ① 我这套是中心调度（manager 模式），不是运行时派生的子 Agent：agent 集合在注册表里预先声明，由规则 + LLM 路由决定谁上场，不是父 Agent 运行时 spawn。
> ② `deep_agent` 是这批 worker 里最像 agent 的一个：自己规划步骤、并行调工具、自我反思后重规划；但中间过程只留在 trace，父图 `messages` 只收一条最终答案，所以上下文是隔离的。
> ③ 不做动态派生是成本决策：Anthropic 实测多 Agent 的 token 约为单 Agent 的 15 倍（单 Agent 约为普通对话 4 倍），他们早期还给简单问题开过 50 个子 Agent。我的场景只有 6 个固定能力，路由的确定性比弹性值钱。

### 6.4 追问"怎么改成真 subagent"（四条改动，能说明你知道边界）

1. **独立 messages**：子 Agent 自己维护对话，只回 `{answer, citations}`，不写父 `messages`；
2. **独立 thread / checkpoint**：`thread_id = f"{parent}:{step_id}"`，崩溃能从第 N 步续跑；
3. **派生入口**：做成工具（`spawn_agent(task, tools)`）或用 LangGraph `Send` 动态 fan-out；
4. **配额**：最大子 Agent 数、最大步数、总 token 上限——否则就是无限递归。

当前设计的收益是"可审计、可复现、成本可控"，代价是"不能按问题难度动态扩缩"。

## 7. 附：handoff 是通用概念吗？和 LangGraph 的 Command 什么关系

### 7.1 先说结论：概念通用，实现原语不同

`handoff` 不是 OpenAI 专属词，它是多 Agent 领域的通用术语，LangGraph 官方文档章节标题就写作「如何在代理之间实现切换（Handoffs）」。证据链：

- **LangGraph 官方**：agent 节点 return `Command(goto=..., update=...)` 实现切换；跨子图时用 `graph=Command.PARENT`。
- **LangChain 官方博客**原话：OpenAI 的 swarm 框架在这一点上做得相当好，Command 类型让我们很容易实现 handoff。
- **langgraph-supervisor / langgraph-swarm**：内部就是生成 `transfer_to_<agent>` 工具，本质是 handoff。
- **生产案例**：Lyft 用 router 模式，meta agent 用 `Command(goto=...)` 派发，intent agent 用 `Command(goto=..., graph=Command.PARENT)` 交回父图重路由。

所以面试里说 handoff 没问题，但要能补一句"LangGraph 里的原语是 Command"。

### 7.2 但本项目的 handoff ≠ LangGraph 的 handoff

| 维度 | 本项目 `handoff_decider` | LangGraph `Command(goto)` |
|---|---|---|
| 时机 | 上一棒**答完之后**再判定 | 作答**之前/过程中**就转移 |
| 控制权 | **不转移**，目标跑完回到 decider | 转移，目标成为 active |
| 载荷 | `business_result` + `pending_context` | 通常是共享 `messages` 全量历史 |
| 终态 | 两段答案**合并**成一段 | 目标自己的回答就是终态，原 agent 退出 |
| 实现 | 节点 + 条件边（`main_graph.py:239` / `:268`） | `Command(goto=...)` |
| 决策来源 | yaml 规则关键词（可运营配置） | 通常由 LLM 调 `transfer_to_*` 工具 |

按"控制权是否转移"这条判据，本项目严格说**不是** handoff，更准确是「中心调度下的跨 Agent 二次派发 + 终态合并」。有意思的是项目里确实用了 `Command`，但只用了 `Command(resume=)` 做 HITL 续跑（`agent/graph.py:307`），没有用 `goto`——这个细节能证明分得清两者。

### 7.3 追问"为什么不用 LangGraph 的 Command 做转交"（四点）

1. **语义不匹配**：我要的是"A 的结果 + B 的解释"拼成一段；`Command` 是换人接着说，转移后 A 那段要么丢，要么塞进 messages 让 B 复述——用更绕的方式实现同一个效果。
2. **可测性**：`decide_handoff()` 是纯函数，单测直接断言输入输出；`Command` 写在节点里，测一次得把图跑起来。
3. **决策来源**：规则在 yaml，运营能改；`transfer_to_*` 工具通常由模型决定，引入不确定性，而我的场景只需要一条确定性规则。
4. **环控制**：条件边天然把目标限制在 `allowed` 集合内（`main_graph.py:213`），`Command` 要在每个节点里自己保证目标合法。

**什么时候我会换**：需要多跳、跨父子图跳转、或运行中动态决定目标时，`Command(goto=..., graph=Command.PARENT)` 是唯一顺手的原语，那时就用它。

### 7.4 说法建议

简历/面试统一说「**规则触发的跨 Agent 二次派发（handoff 语义）+ 终态合并**」，并主动补一句"不是 Command 那种控制权转移"。提前把差异说清，比被追问时才发现名不副实强得多。

## 8. 附：到底算不算"多 Agent"？企业级到什么程度

### 8.1 supervisor 是不是 agent：拆成三要素看

| 要素 | supervisor 节点 | 业务 worker（如 deep_agent） |
|---|---|---|
| model | 有（L3 结构化输出，temperature=0） | 有 |
| harness | 有（图状态、规则、兜底、护栏） | 有（计划/执行/反思循环、ToolPolicy、trace） |
| 决策空间 | **一个枚举**（6 个能力 id + clarify），无工具、无循环 | 开放（自己规划步骤、自己选工具） |

结论：supervisor **不是 agent，是 LLM 支撑的路由决策节点**。判断标准不是"有没有调模型"，而是"有没有工具 + 能不能自己决定下一步做几轮"。

### 8.2 但系统仍是多 Agent——看工作单元，不看协调者

启用的能力共 6 个：`knowledge_qa`、`price_inquiry`、`general_chat`、`doc_qa`、`deep_agent`、`fallback`。其中
- 4 个有 LLM、3 个有工具（`knowledge_qa: kb_search`、`price_inquiry: price_query`、`deep_agent: 三个工具`）；
- `knowledge_qa` / `price_inquiry` 是编译子图，`deep_agent` 是过程式 agent 循环；
- 各自有独立 system prompt、独立模型槽位、独立工具白名单。

判定多 Agent 的关键是「**工作单元是否多个且各自自治**」，不是「协调者是否也是 agent」。反例：一个 agent 挂 10 个工具仍是单 Agent；本项目是 6 个各有边界的工作单元 + 1 个确定性协调者。

### 8.3 自治度分级（用来定位自己的位置）

| 级别 | 协调者 | 典型形态 | 本项目 |
|---|---|---|---|
| L0 | 无 | 单 agent + 多工具 | — |
| **L1** | 路由节点（无工具、无循环） | router 模式 | **在这里** |
| L2 | 协调者本身是 agent（有工具、能循环、能决定派发几个） | supervisor / orchestrator-worker | deep_agent 内部循环摸到边缘，协调层仍在 L1 |
| L3 | 多层协调或任意转交 | 层级团队 / network | 没有 |

LangGraph 官方把 router、supervisor、handoffs、network 列为**不同**架构；Lyft 的 meta agent 也只是「路由 + Command 派发」，业界同样称其为 multi-agent。所以讲"多 Agent 编排"成立，准确说法是「**router 模式的多 Agent**」。

### 8.4 企业级自评（七维）

| 维度 | 现状证据 | 缺口 |
|---|---|---|
| 可靠性 | 每个节点 `_with_fallback` 兜底、统一错误码、LLM `max_retries`、SSE 以 `result` 为权威终态 | 无端到端超时预算（SLO）、无熔断 |
| 安全 | 鉴权中间件、限流（进程内/Redis 双后端 + 全局限流）、safety 前置闸门、输出护栏 | 无用户体系（tenant 仅 session 命名空间）、无 PII 脱敏 |
| 可观测 | OTel → Langfuse、Prometheus 指标（分支延迟/LLM token/缓存命中/召回降级/护栏失败）、审计日志 | 告警规则未落在仓库里 |
| 可测试 | 154 个测试文件、本地 4 道门禁 + 覆盖率棘轮、评测脚本 | CI 休眠（无远端）；路由阈值无真实流量回归集 |
| 可运维 | 配置集中在 Settings、能力开关 `CAPABILITY_ENABLED/DISABLED`、检查点多后端、注册表热插拔 | 无灰度/AB、无 prompt 版本管理、redis 后端未验证 |
| 成本 | 语义路由示例向量预计算、结果缓存、token 指标 | 无单请求 token 预算/熔断 |
| 演进 | `CapabilitySpec` 单一事实源、节点契约、registry 单一 chokepoint、`core/contracts` 契约层 | 能力间共享逻辑仍有重复 |

**结论**：达到「单租户、可上小规模生产」，未达到「大企业多租户平台」。差的不是架构范式，是四件平台化的事：用户/租户体系、灰度与回滚、真实流量回归、多副本一致性（SSE 单 worker、redis 未验证）。

### 8.5 面试口径

> ① 我的协调层是**路由节点**，不是自主 agent：它调模型，但只输出一个能力 id，没有工具也没有循环。所以严格说是 router 模式，不是 supervisor 模式——supervisor 的协调者本身得是 agent。
> ② 但系统是多 Agent：6 个工作单元，各自有 prompt、模型槽位和工具白名单，两个是编译子图。判多 Agent 看工作单元的数量和自治度，不看协调者是不是 agent。
> ③ 企业级我只敢说到"单租户小规模生产"：可观测、兜底、限流、测试门禁这些是齐的；缺的是用户体系、灰度回滚和真实流量回归，这三块一上多租户就会暴露。
